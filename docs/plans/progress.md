# Mini Redis 진행 현황

- 문서 상태: 현황 기록 중 — 1단계 확인 완료, 2단계 요구사항 초안
- 확인일: 2026-11-17 (KST)
- 목적: 사용자와 에이전트가 전체 진행 흐름, 현재 작업, 막힌 결정과 검증 근거를 함께 확인한다. 일정표나 완료 예상표가 아니다.
- 기준: [과제 원문](../assignment.md), [구현 단위 가이드](implementation-units.md), [사용자 주도 진행 원칙](../decisions/0001-project-workflow.md)

## 현재 위치

- **완료로 확인된 것:** Redis 이론 학습(사용자 확인), 공유 구현 단위 가이드 작성. 학습과 가이드 작성은 구현·테스트 완료가 아니다.
- **현재 작업 단위:** [1단계 범위·공유 계약](../iterations/01-scope-and-contract/overview.md)은 사용자 확인으로 완료했다(구현 완료 아님). [2단계 해시 테이블 저장소](../iterations/02-hash-table/overview.md)에 들어가 요구사항 초안을 검토한다.
- **다음 확인 지점:** [2단계 진행 체크리스트](../iterations/02-hash-table/overview.md#진행-체크리스트)의 첫 항목인 기본 연산·충돌·경계 테스트 범위를 사용자와 확인하고, 그 범위에 필요한 충돌 처리·확장 정책 등 설계를 정한다. 키의 URL 표현, TTL 설정·내부 만료 처리는 후속 해당 단위에서 구체화한다.
- **구현·테스트 근거:** 아직 없음. 현재 브랜치에서 구현 코드나 테스트 실행 결과를 확인하지 못했다.

## 전체 흐름

`전체 경계·공유 계약 확인` → `각 단위에서 요구사항 정의 → 설계·검토 → 구현 → 단위 테스트 → 기존 부분과 연결 확인` 반복 → `전체 기능·통합 테스트와 성능 비교`

전체 설계를 처음에 완성하지 않는다. 외부 인터페이스, 저장소 연산의 의미, 책임 경계와 만료·동시성의 영향만 먼저 드러내고, 내부 설계는 해당 단위에서 구체화한다. 단위 사이의 연결 확인을 마지막까지 미루지 않되, 마지막에 전체 흐름을 다시 검증한다. 실패가 나오면 해당 요구사항·설계·구현 단위로 돌아간다.

## 작업 단위 현황

| 단위 | 현재 상태 | 다음 확인할 결과 | 실제 근거 |
| --- | --- | --- | --- |
| 1. 최소 범위·공유 인터페이스 | 완료 — 과제 대응·최소 경계 사용자 확인 | 2단계에서 기본 계약 적용 | [1단계 범위·체크리스트](../iterations/01-scope-and-contract/overview.md), [D-0002](../decisions/0002-python-http-interface.md), [D-0003](../decisions/0003-http-response-contract.md); 구현·테스트 근거 없음 |
| 2. 해시 테이블 저장소 | 진행 중 — 요구사항 초안 확인 전, 구현 미착수 | 범위·설계 확인 후 저장·조회·삭제와 충돌·경계 단위 테스트 | [2단계 초안](../iterations/02-hash-table/overview.md); 실행 근거 없음 |
| 3. 외부 사용·API 응답 재사용 | 대기 — 1·2 선행 | 외부 호출 및 저장 후 재사용 기능 테스트 | 없음 |
| 4. 만료·무효화 | 대기 — 저장소·외부 계약 선행 | 만료/무효화 동작과 경계 테스트 | 없음 |
| 5. 동시성 점검·방어 | 대기 — 실행 구조·상태 변경 경로 확인 선행 | 위험 판단 근거, 필요한 방어와 기대 최종 상태 검증 | 없음 |
| 6. 전체 통합·성능 검증 | 대기 — 실행 가능한 사례 선행 | 전체 흐름의 실행 결과, 동일 조건의 비교 결과와 한계 | 없음 |

이 표의 ‘다음 확인할 결과’는 **완료 조건의 제안**이지 이미 얻은 결과가 아니다. 단위 2~5의 진행 중에도 새 연결부가 생기면 간단한 통합 확인을 하고, 실제 명령·조건·결과를 해당 단위의 기록에 남긴다. 영속성은 [과제 원문](../assignment.md)의 선택 항목으로, 현재 구현 범위에 넣지 않았다. 제외 확정도 아니다.

## 미결정 사항과 막힘

- **바로 필요한 확인:** 1단계의 목표·범위, Python·HTTP API, 기본 연산·응답 계약과 HTTP·저장소 책임 경계는 확인됐다. 현재는 2단계 요구사항 초안을 사용자와 확인한다.
- **해당 단위에서 구체화:** 해시 충돌 처리, 만료·무효화 정책, 동시성 대응, API 활용 사례와 성능 비교 조건.
- **현재 확인 지점:** 과제 대응과 최소 책임 경계는 사용자 확인을 마쳤다. 2단계의 충돌 처리·확장 정책, 키의 경로 표현, TTL 설정·제거, 무효화·동시성 구조·배포 형태는 아직 정하지 않았다.

## 갱신 방법

1. 작업 단위에 들어갈 때 [공통 진행 체크리스트](implementation-units.md#진행-체크리스트)를 바탕으로 해당 `overview.md`의 실행 체크리스트를 먼저 작성하고, 이번 단위의 범위·완료 조건을 사용자와 확인한다. 상태는 `착수 전/대기 → 진행 중 → 사용자 확인 대기 → 완료`로 관리하며 필요하면 `중단`을 표시한다.
2. 그 단위의 요구사항·설계·설계 검토·구현·테스트 결과를 짧게 남긴다. 필요할 때 [컨벤션의 단계별 문서 규칙](../conventions.md#단계별-문서의-최소-단위)에 따라 `docs/iterations/`의 한 문서로 묶어도 된다. 이 현황판에는 세부 내용을 복제하지 않고 근거 링크만 둔다.
3. 테스트가 있는 단위는 실제 실행 명령·조건·결과를 기록하고 실행 근거와 사용자 확인을 구분한다. 1단계처럼 구현 전인 단위는 계약 검토와 사용자 확인으로 판단하며, 테스트가 없는 것을 테스트 통과로 표현하지 않는다.
4. 새로운 결정은 사용자 확인 뒤 [결정 기록](../decisions/README.md)에 남긴다. 매 단위가 끝날 때 다음 단위의 선행 조건·막힘·우선순위를 재확인한다. 단순 수정에는 불필요한 문서를 늘리지 않는다.

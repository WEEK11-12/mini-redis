# Mini Redis 구현 단위 가이드

- 상태: 작업 순서 제안 — Python·HTTP API와 키·만료 응답 계약 채택
- 목적: 하루 안에 구현 결과물을 만드는 상황에서 참고할 작업 단위와 확인 지점 제시. 시간표나 완료 기록이 아니다.
- 근거: [과제 원문](../assignment.md), [프로젝트 진행 원칙](../decisions/0001-project-workflow.md), [컨벤션 초기안](../conventions.md)

## 진행 원칙

- 목표는 **가벼운 범용 인메모리 공유 캐시**다. 직접 구현한 해시 테이블 기반 저장소를 외부에서 사용하고, 동작을 실행으로 검증한다. [1단계 목표·범위](../iterations/01-scope-and-contract/overview.md)를 따른다.
- 아래 순서는 의존 관계를 보여 주는 권장 흐름이다. 각 단위에서 필요한 요구사항·설계 선택만 확인하고, 작은 구현과 테스트 결과를 본 뒤 다음 단위를 조정한다. 미래 단계의 세부 설계를 한꺼번에 확정하지 않는다.
- 과제의 요구와 이 문서의 작업 순서 제안을 구분한다. 언어·외부 통신 및 [기본 HTTP·캐시 계약](../decisions/0003-http-response-contract.md)(비어 있지 않은 문자열 키, 만료 시 미존재 응답 포함)은 정했다. 2단계의 충돌 처리 등 저장소 구조는 [설계 문서](../iterations/02-hash-table/design.md)에서 선택하고 문서 계약을 검토했다. 구현·실행 검증은 아직이다. 키의 경로 표현, 내부 만료·무효화, 동시성 대응 방식은 후속 단계에서 정한다.
- 테스트 실행 전의 계획을 완료로 표시하지 않는다. 문서 작성보다 실행 가능한 결과물과 핵심 로직의 이해를 우선한다.

## 진행 체크리스트

작업 단위를 시작할 때 **아래 순서로 해당 단위의 `overview.md`에 실제 체크리스트를 먼저 작성**하고, 그것을 따라 진행한다. 구현 단위의 요구사항은 ID·인수 조건을 가진 별도 `requirements.md`에 기록하고 [단계별 요구사항 색인](../iterations/README.md)에 연결한다. 구현 전 TC와 구현·검증 결과의 파일·형식은 [단계별 산출물 가이드](iteration-deliverables.md)를 따른다. 이 목록은 재사용할 절차이지 완료 현황이 아니다. 완료 표시는 해당 단위 문서에 근거와 함께 남기고, 전체 상태만 [진행 현황](progress.md)에 반영한다.

1. [ ] **목표·범위:** 과제와 이전 단위의 계약을 확인하고, 이번 단위의 포함·제외 사항과 관찰 가능한 완료 조건을 적는다. 범위 확정 전 초안은 확정으로 표시하지 않는다.
2. [ ] **설계:** 이번 단위에 필요한 구성 요소·입출력·실패 및 경계 처리와 미결정 선택을 정리한다. 다른 단위에 영향을 주는 계약을 확인하고, 중요 결정만 [결정 기록](../decisions/README.md)에 남긴다.
3. [ ] **설계 검토:** 요구사항 누락·충돌 및 연결부를 점검하고, 막는 쟁점을 해결한다.
4. [ ] **구현 전 TC:** 요구사항 ID별 관찰 가능한 TC와 필요한 경계·실패 사례를 `test-cases.md`에 적는다. 단위/통합 유형을 구분하고 실행 결과로 표시하지 않는다.
5. [ ] **구현:** TC별로 실패 확인 → 최소 구현 → 통과 확인을 반복한다. 실제 변경은 `implementation.md`에 기록한다. 계획이나 문서만으로 완료 표시하지 않는다.
6. [ ] **검증·연결:** 완료 조건에 해당하는 테스트를 실행하고, 새 연결부가 있으면 기존 부분과 함께 확인한다. 명령·조건·실제 결과를 `verification.md`에 기록한다.
7. [ ] **결과 확인·인계:** 남은 위험과 다음 단위의 선행 조건을 검토하고 진행 현황을 갱신한다.

1단계처럼 코드가 없는 범위·계약 단위는 구현·실행 검증 항목을 **해당 없음(이유 명시)**으로 두고 과제 대응·계약 검토 증거로 마무리한다. 항목을 건너뛰거나 확인 전 체크하지 않는다.

## 구현 단위

### 1. 최소 범위와 인터페이스 계약

- **할 일:** [정리된 목표·범위](../iterations/01-scope-and-contract/overview.md)를 바탕으로 Python HTTP API와 저장·조회·존재 확인·삭제의 입력·결과·오류를 정한다. 만료와 명시적 무효화가 계약에 미칠 영향과 검증할 동작을 적는다.
- **확인할 결과:** 첫 구현 단위에 필요한 계약과 비범위가 짧게 정리되어 있다. 구현 전에 모든 기능의 상세 요구사항을 확정할 필요는 없다.
- **선행 조건:** 과제 원문 확인. 결정이 필요한 항목은 대안을 비교해 선택한다.

### 2. 해시 테이블 기반 저장소

- **할 일:** 해시 계산, 충돌 처리, 키 비교를 포함한 저장·조회·존재 확인·삭제를 구현한다. 빈 값과 미존재를 구분하고, 경계 조건(없는 키, 같은 키 덮어쓰기, 충돌 등)을 단위 테스트로 확인한다.
- **확인할 결과:** 외부 API와 독립적으로 저장소 테스트가 실행되고, 해시 테이블의 설계와 주요 함수의 입력→처리→출력을 설명할 수 있다.
- **선행 조건:** 1의 키·값 및 연산 계약. 핵심 저장소를 기존 맵에 위임해 ‘직접 구현’ 요구를 놓치지 않는다.

### 3. 외부 사용 경로와 활용 사례

- **할 일:** 저장소 내부와 통신 처리를 분리해 외부 사용 인터페이스를 연결한다. 간단한 API 응답을 Mini Redis에 저장하고 재사용하는 기능 테스트 사례를 만든다.
- **확인할 결과:** 저장·조회·존재 확인·삭제를 외부 호출로 확인할 수 있고, API 응답의 최초 요청과 저장 후 재사용 경로가 실제로 동작한다.
- **선행 조건:** 1의 HTTP 세부 계약, 2의 저장소. 프레임워크와 엔드포인트·응답 형식은 설계에서 구체화한다.

### 4. 만료와 명시적 무효화

- **할 일:** 보관 기간이 지난 값을 요청했을 때의 동작과 제거 시점, 명시적 무효화 방식을 정해 구현한다. 만료 직전·직후, 없는 키, 무효화 후 재조회 등을 검증한다.
- **확인할 결과:** 만료된 값이 유효한 값처럼 반환되지 않고, 선택한 무효화 방식의 결과가 테스트로 확인된다.
- **선행 조건:** 2의 저장소와 3의 외부 계약에서 해당 동작이 어떻게 드러나는지 결정한다. 테스트에는 가능하면 제어 가능한 시간원을 사용한다.

### 5. 동시성 위험 점검과 필요한 방어

- **할 일:** 선택한 실행 구조에서 요청이 동시에 같은 저장소를 변경할 수 있는지 확인하고, 가능한 경쟁 상황에 필요한 보호 방식을 적용한다.
- **확인할 결과:** 동시 요청의 기대 최종 상태를 명시하고 실제 테스트한다. 구조상 위험이 없다고 판단했다면 그 근거를 남긴다. 단순히 오류가 없었다는 이유로 정합성이 확보됐다고 하지 않는다.
- **선행 조건:** 2~4의 상태 변경 경로와 3의 실행 구조 파악. 특정 락·스레드 구조를 미리 강제하지 않는다.

### 6. 최종 사용·성능 검증과 설명

- **할 일:** 저장·조회·삭제 단위 테스트, 외부 사용 기능 테스트, 선택한 정책의 경계 테스트를 실행한다. 동일한 요청·데이터·환경을 기준으로 캐시 미사용/미스/히트 조건을 구분해 비교한다. 해시 테이블 설계와 주요 함수, 만료·동시성 선택의 동작·이유를 설명할 수 있는지 확인한다.
- **확인할 결과:** 실제 실행 명령·조건·성공/실패 결과, 재현 가능한 사용 방법, 비교 결과와 한계, 남은 문제가 정리된다. 측정하지 않은 성능 향상은 주장하지 않는다.
- **선행 조건:** 비교할 API 사례와 실제 측정 환경. 검증 중 누락이 나오면 해당 구현 단위로 돌아간다.

## 범위가 빠듯할 때

- **비선택 항목:** 과제에 명시된 비선택 항목은 모두 구현·검증 대상으로 유지한다. 세부 구현 방식과 검증 사례를 간결하게 정해 범위를 관리한다. 시간 부족으로 빠진 항목이 있다면 실제 미완료로 표시한다.
- **선택 항목:** 서버 중단 시 데이터 보존을 위한 영속성은 과제 원문에서 Optional이다. 구현 채택 여부는 별도로 결정한다.
- **주의:** 테스트나 성능 비교를 문서상의 예상 결과로 대체하지 않는다. 못 마친 항목은 실제 결과와 분리해 남긴다.

## 지금 열려 있는 결정

- Python 실행 환경과 HTTP 키의 경로 인코딩·추가 제약, 상세 오류 코드
- TTL 설정·제거 방식과 무효화의 세부 계약
- 만료·무효화·동시성 대응 방식 (2단계 [설계 문서](../iterations/02-hash-table/design.md)의 구현·검증 상태는 [진행 현황](progress.md) 참조)
- 성능 비교에 사용할 API 사례와 측정 조건

이 문서는 착수 가이드이며 요구사항 확정이나 구현 완료를 뜻하지 않는다. 중요한 선택은 확정한 후 [결정 기록](../decisions/README.md)에 반영한다.

# Mini Redis 구현 단위 가이드

- 상태: 제안 — 사용자와 단계별 범위·기술 선택 확인 전
- 목적: 하루 안에 구현 결과물을 만드는 상황에서 사용자와 에이전트가 공유할 작업 단위와 확인 지점 제시. 시간표나 완료 기록이 아니다.
- 근거: [과제 원문](../assignment.md), [프로젝트 진행 원칙](../decisions/0001-project-workflow.md), [컨벤션 초기안](../conventions.md)

## 진행 원칙

- 목표는 Redis 전체 기능 재현이 아니라 **직접 구현한 해시 테이블 기반 저장소를 외부에서 사용하고, 동작을 실행으로 검증하는 것**이다.
- 아래 순서는 의존 관계를 보여 주는 권장 흐름이다. 각 단위에서 필요한 요구사항·설계 선택만 확인하고, 작은 구현과 테스트 결과를 본 뒤 다음 단위를 조정한다. 미래 단계의 세부 설계를 한꺼번에 확정하지 않는다.
- 과제의 요구와 이 문서의 제안을 구분한다. 언어, API 형태, 충돌 처리, 만료·무효화 정책, 동시성 대응 방식은 아직 사용자 결정이 아니다. 에이전트는 대안을 제시할 수 있지만 임의로 확정하지 않는다.
- 테스트 실행 전의 계획을 완료로 표시하지 않는다. 문서 작성보다 실행 가능한 결과물과 핵심 로직에 대한 사용자의 이해를 우선한다.

## 구현 단위

### 1. 최소 범위와 인터페이스 계약

- **할 일:** 사용자가 만들 저장소의 목표·범위를 먼저 정리한다. 언어·실행 방식, 외부에서 쓰는 방식, 저장·조회·삭제의 입력·결과·오류를 정한다. 만료와 명시적 무효화가 무엇을 뜻하는지, 검증할 수 있는 동작을 적는다.
- **확인할 결과:** 첫 구현 단위에 필요한 계약과 비범위가 짧게 정리되어 있다. 구현 전에 모든 기능의 상세 요구사항을 확정할 필요는 없다.
- **선행 조건:** 과제 원문 확인. 결정이 필요한 항목은 사용자에게 선택지를 제시한다.

### 2. 해시 테이블 기반 저장소

- **할 일:** 해시 계산, 충돌 처리, 키 비교를 포함한 저장·조회·삭제를 구현한다. 경계 조건(없는 키, 같은 키 덮어쓰기, 충돌 등)을 단위 테스트로 확인한다.
- **확인할 결과:** 외부 API와 독립적으로 저장소 테스트가 실행되고, 해시 테이블의 설계와 주요 함수의 입력→처리→출력을 설명할 수 있다.
- **선행 조건:** 1의 키·값 및 연산 계약. 핵심 저장소를 기존 맵에 위임해 ‘직접 구현’ 요구를 놓치지 않는다.

### 3. 외부 사용 경로와 활용 사례

- **할 일:** 저장소 내부와 통신 처리를 분리해 외부 사용 인터페이스를 연결한다. 간단한 API 응답을 Mini Redis에 저장하고 재사용하는 기능 테스트 사례를 만든다.
- **확인할 결과:** 저장·조회·삭제를 외부 호출로 확인할 수 있고, API 응답의 최초 요청과 저장 후 재사용 경로가 실제로 동작한다.
- **선행 조건:** 1의 외부 계약, 2의 저장소. 통신 방식과 API 형태는 선택 후 구체화한다.

### 4. 만료와 명시적 무효화

- **할 일:** 보관 기간이 지난 값을 요청했을 때의 동작과 제거 시점, 사용자가 값을 무효화하는 방식을 정해 구현한다. 만료 직전·직후, 없는 키, 무효화 후 재조회 등을 검증한다.
- **확인할 결과:** 만료된 값이 유효한 값처럼 반환되지 않고, 선택한 무효화 방식의 결과가 테스트로 확인된다.
- **선행 조건:** 2의 저장소와 3의 외부 계약에서 해당 동작이 어떻게 드러나는지 결정한다. 테스트에는 가능하면 제어 가능한 시간원을 사용한다.

### 5. 동시성 위험 점검과 필요한 방어

- **할 일:** 선택한 실행 구조에서 요청이 동시에 같은 저장소를 변경할 수 있는지 확인하고, 가능한 경쟁 상황에 필요한 보호 방식을 적용한다.
- **확인할 결과:** 동시 요청의 기대 최종 상태를 명시하고 실제 테스트한다. 구조상 위험이 없다고 판단했다면 그 근거를 남긴다. 단순히 오류가 없었다는 이유로 정합성이 확보됐다고 하지 않는다.
- **선행 조건:** 2~4의 상태 변경 경로와 3의 실행 구조 파악. 특정 락·스레드 구조를 미리 강제하지 않는다.

### 6. 최종 사용·성능 검증과 설명

- **할 일:** 저장·조회·삭제 단위 테스트, 외부 사용 기능 테스트, 선택한 정책의 경계 테스트를 실행한다. 동일한 요청·데이터·환경을 기준으로 캐시 미사용/미스/히트 조건을 구분해 비교한다. 해시 테이블 설계와 주요 함수, 만료·동시성 선택을 사용자가 설명해 본다.
- **확인할 결과:** 실제 실행 명령·조건·성공/실패 결과, 재현 가능한 사용 방법, 비교 결과와 한계, 남은 문제가 정리된다. 측정하지 않은 성능 향상은 주장하지 않는다.
- **선행 조건:** 비교할 API 사례와 실제 측정 환경. 검증 중 누락이 나오면 해당 구현 단위로 돌아간다.

## 범위가 빠듯할 때

- **우선 확보:** 직접 만든 해시 테이블, 외부 사용 경로, 저장·조회·삭제 테스트, API 응답 재사용 사례와 기능 테스트. 만료 시 조회 정책, 무효화 방식, 동시성 위험도 검토하고 선택한 범위에서 구현·검증한다.
- **선택 항목:** 서버 중단 시 데이터 보존을 위한 영속성은 과제 원문에서 Optional이다. 시간 제약이 있으면 구현을 미루고 미구현으로 명시한다.
- **주의:** 테스트나 성능 비교를 문서상의 예상 결과로 대체하지 않는다. 못 마친 항목은 실제 결과와 분리해 남긴다.

## 지금 열려 있는 결정

- 사용자 목표와 최소 기능 범위, 언어·실행 환경
- 외부 인터페이스 및 저장소 연산의 계약
- 충돌 처리·만료·무효화·동시성 대응 방식
- 성능 비교에 사용할 API 사례와 측정 조건

이 문서는 착수 가이드이며 요구사항 확정이나 구현 완료를 뜻하지 않는다. 중요한 선택은 사용자가 검토한 후 [결정 기록](../decisions/README.md)에 반영한다.

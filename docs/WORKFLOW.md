# 협업과 검증 기록

## 함께 작업할 때

- 두 사람 모두 Mini Redis와 Mini DBMS의 학습·구현 전 과정을 경험합니다. Redis와 DBMS는 별도 프로젝트로 관리하고, 공유할 인터페이스가 필요해지면 연결 전에 함께 정합니다.
- 각 구현 단위는 설계 이유와 필수 테스트·예상 결과를 함께 확인한 뒤 진행합니다. 실제 실행·실패·수정 과정을 확인하고 합의한 통과 조건을 충족하면 다음 단위로 넘어갑니다.
- 한 작업 단위에는 목적, 설계 이유, 변경 내용, 실행한 테스트, 남은 문제를 적습니다. 커밋·푸시는 담당자의 요청과 확인을 거쳐 진행합니다.
- 서로의 파트를 리뷰할 때는 파일·동작·재현 입력을 지정해 질문이나 문제를 남깁니다. 작성자는 판단 근거와 수정 결과를 답하고, 리뷰어는 재검증 결과를 남깁니다.
- 테스트가 실패했다면 실패한 사실을 지우지 않고, 원인 가설과 수정 전후 결과를 함께 남깁니다.

현재 상태는 루트 [WORKLOG](../WORKLOG.md), 요구·테스트 연결은 [TESTING](TESTING.md)에 둡니다. 작업 전에는 [AGENTS](../AGENTS.md)의 읽는 순서를 따릅니다. 다음 단위 구현은 사용자가 현재 단위의 결과를 확인한 뒤 진행합니다.

## 기능별 기록 양식

작업할 때마다 아래 항목을 복사해 PR 설명이나 작업 기록에 채웁니다. 실행하지 않은 테스트는 `미실행`으로 표시합니다.

```md
### 기능:
- 테스트 목적:
- 기대 동작과 사용 예:
- 설계 선택과 이유:
- 확인할 경계값·실패 조건:
- 실행 환경과 명령:
- 결과(기대/실제):
- 판정(PASS / FAIL / NOT RUN):
- 발견한 문제, 원인 가설, 수정 및 재검증:
- 부하 테스트 조건(입력 규모·동시 연결 수·반복 횟수)과 결과:
- 리뷰 질문·의견과 답변:
- 남은 한계:
```

성능 비교는 동일한 입력과 반복 횟수로 수행하고, 캐시가 비어 있는 경우와 채워진 경우를 구분해 기록합니다. 측정값이 나오기 전에는 성능 향상을 주장하지 않습니다.

## 개인 포크와 팀 저장소

개인 포크 origin은 jye-1123/mini-redis, 팀 upstream은 WEEK11-12/mini-redis다. main에는 실제 프로젝트의 요구사항·설계·API·테스트·코드를 관리한다. study-jye에는 공부한 개념과 예시만 보관한다. 학습 노트가 제품 계약을 대신하지 않는다.

개인 main이나 study-jye에 푸시해도 팀 저장소는 바뀌지 않는다. 팀 반영은 별도 요청과 대상 확인 후 진행한다. main과 학습 브랜치를 통째로 병합해서 학습 README나 필기를 실제 프로젝트에 섞지 않는다.

## 자료와 검증의 범위

문서는 사용자가 제공한 학습 인수인계 자료와 현재 대화, 각 장에 연결한 공식 자료를 바탕으로 정리합니다. 채팅 도구에서 반환하지 않은 이전 답변을 모두 읽었다고 주장하지 않습니다. 문서 링크·형식 확인과 실제 저장 엔진 테스트는 별개로 기록합니다.

실제 프로젝트 계약은 개인 main의 문서와 최신 사용자 합의가 기준입니다. 옵시디언은 개인 학습용 읽기 자료로 연결하며, 설계가 바뀌면 관련 개념 노트와 설계 노트를 함께 확인합니다. 과거 규격이 현재 선택처럼 남지 않도록 변경 상태와 미정 사항을 명시합니다.

설계 이유는 [선택 기록](DECISIONS.md)에 대안과 함께 남깁니다. 초기 수치를 최적값으로 표현하거나 실행하지 않은 비교를 선택 근거로 만들지 않습니다.

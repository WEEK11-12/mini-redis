# 설계 선택과 대안

선택한 방법의 일반적 장점과, 이번 프로젝트에서 그 선택을 지지하는 근거를 구분합니다. 아래 선택은 사전 설계이며 성능 우위를 측정한 결과가 아닙니다. 실제로 확인한 사실, 합의한 초기 정책, 앞으로 검증할 가정을 각각 표시합니다.

## 1. Python + Flask + Waitress

**문제와 조건:** 과제의 중심은 해시 충돌·TTL·동시 접근·캐시 활용을 구현하고 검증하는 것이다. 메모리 할당·해제 경험이 주요 목표는 아니다. Windows 환경을 유지한다.

| 대안 | 이득이 되는 상황 | 감수하는 비용 |
| --- | --- | --- |
| C | 포인터·메모리 배치·할당 비용까지 직접 제어하고 싶을 때 | 수동 해제·범위·빌드와 오류 진단 부담 |
| Python + Flask | 저장소 동작·실패·테스트에 시간을 배분하고 싶을 때 | 런타임·객체 비용, 실제 성능 검증 필요 |
| TypeScript + Node.js | 기존 JS 경험과 이벤트 루프를 활용할 때 | 비동기 처리·런타임 이해, 다른 생태계 선택 |

**선택:** Python + Flask. C가 느려서가 아니라 이번 우선순위에서 수동 메모리 관리의 비용을 감수할 필요가 약하다. dict로 핵심을 대체하지 않고 해시 테이블은 직접 구현한다. Python이 C와 같은 성능이거나 무조건 개발이 빠르다고 주장하지 않는다.

**서버 선택:** Flask 개발 서버도 Windows와 여러 요청 스레드를 지원한다. Waitress는 정해진 수의 워커를 재사용하고 실행·측정 환경을 명확히 하기 위해 선택했다. 워커는 기능별 담당이 아니다. 모두 바쁘면 요청은 기다린다. 고정 풀은 느린 작업에 묶일 수 있으며 대기열·총 메모리까지 자동 제한하는 것은 아니다. 초기 4워커는 실측 최적값이 아니다.

[Flask 요청 흐름](https://flask.palletsprojects.com/en/stable/lifecycle/) · [개발 서버](https://flask.palletsprojects.com/en/stable/server/) · [Waitress](https://flask.palletsprojects.com/en/stable/deploying/waitress/)

## 2. 충돌 처리: 체이닝

**현재 선택:** 버킷 배열 + 연결 리스트.

같은 버킷에 A → B → C가 있을 때 B를 삭제하면 A의 다음 노드를 C로 바꾸는 과정을 관찰하기 쉽습니다. 이번에 충돌·삭제의 정확성을 함께 검증한다는 목표와 연결됩니다.

개방 주소법은 테이블 안의 다른 칸을 찾습니다. 가까운 칸을 연속 탐색하는 방식은 메모리 접근과 할당 비용에서 유리할 수 있지만 삭제 표시나 뒤쪽 키의 탐색 경로를 관리해야 합니다. 작은 항목이 아주 많아지면 체이닝의 노드별 할당·포인터 비용이 더 부담될 수도 있습니다.

**다시 볼 조건:** 같은 데이터와 적재율에서 메모리 사용·조회·삭제 비용을 비교할 필요가 생겼을 때입니다. 현재는 어느 쪽의 실측 성능 우위도 확인하지 않았습니다.

## 3. 해시 함수: FNV-1a 64비트

**현재 선택:** 문자열 바이트를 XOR한 뒤 정해진 소수를 곱하는 작은 비암호학적 함수.

단순 바이트 합을 해시로 사용하면 `ab`와 `ba`는 순서가 달라도 같은 합이 됩니다. FNV-1a는 순서대로 반복 계산하므로 이런 단순 합과 다르며 과정을 검산하기 쉽습니다. 그래도 모든 다른 문자열의 결과가 달라지는 것은 아닙니다.

공격 대응을 고려한 키 기반 해시나 다른 고성능 비암호학적 해시도 대안입니다. 이들은 분포·처리량·위협 조건에 따른 선택입니다. FNV-1a를 골랐다는 사실만으로 우리 키에서 분포가 좋거나 다른 후보보다 빠르다고 결론 내리지 않습니다.

**현재 판단:** 구현·검산의 작은 범위는 이유가 될 수 있습니다. 적절한 키 분포와 최악 충돌의 동작은 테스트로 확인해야 합니다. FNV를 충돌 공격 방어 기능으로 취급하지 않습니다.

## 4. 적재율 0.75와 2배 확장

**현재 초기 정책:** 16개 버킷에서 신규 키로 적재율이 0.75를 초과하면 2배 확장.

| 조절 방향 | 얻는 것 | 비용 |
| --- | --- | --- |
| 더 낮은 적재율에서 확장 | 분산이 적절할 때 평균 탐색 후보를 일찍 줄임 | 버킷 메모리와 확장 횟수 증가 가능 |
| 더 높은 적재율까지 유지 | 버킷 공간을 덜 늘림 | 체인이 길어져 탐색 비용 증가 가능 |
| 2배로 확장 | 조금씩 반복 확장하는 재배치 비용을 줄이는 여유 | 확장 시 공간과 실행 시간 증가 |

**쉬운 사례:** 12/16은 0.75이므로 유지하고 13번째 신규 키에서 32개로 늘립니다. 확장 후 비율은 13/32입니다. 덮어쓰기는 신규 키가 아니므로 같은 경계에서 확장하지 않습니다.

**현재 판단:** 16·0.75·2배는 합의한 시작값입니다. 16을 고른 이유를 성능 최적화의 결과처럼 꾸미지 않습니다. 키 분포와 메모리·지연을 측정하기 전에는 최적값을 알 수 없습니다.

## 5. 전체 리해싱과 공용 락

**문제:** Flask 요청 스레드와 별도 TTL 청소가 같은 테이블을 읽고 바꾼다. 기존의 한 이벤트 루프 스레드 소유를 가정할 수 없다.

| 대안 | 이득 | 비용 |
| --- | --- | --- |
| 저장소 전체 락 | 호출 경로가 짧고 상태 변경을 한 번에 보호 | 리해싱·청소 중 다른 요청 대기 |
| 저장소 전담 스레드 + 대기열 | 저장소 소유를 한 스레드로 모음 | 결과 전달·대기열·종료 관리 추가 |
| 세분화된 락 | 독립 영역 작업의 병렬성 가능 | 확장·삭제·커서 사이의 잠금 순서 복잡 |

**선택:** 한 프로세스에서 공용 락 하나. 현재 짧은 메모리 작업과 전체 리해싱을 먼저 정확히 구현하는 데 대기열 구조를 추가하지 않는다. 키 개수·TTL·커서까지 보호한다. GIL이나 세마포어 추가로 대체하지 않는다.

전체 리해싱은 점진적 이동보다 단순하지만 대량 확장 지연이 생긴다. 향후 측정으로 개선 필요를 판단한다. 락은 여러 별도 요청으로 된 읽기-수정-쓰기까지 원자적으로 묶지 않는다.

## 6. TTL: 접근 검사와 주기적 회수

**현재 선택:** 수동·능동 만료를 함께 사용. 초기 능동 검사는 100ms마다 최대 100개 키.

접근 시 검사만 하면 만료된 값을 반환하지 않을 수 있지만 다시 읽히지 않는 항목이 메모리에 남습니다. 주기적 검사만 믿으면 청소 전의 조회에 오래된 값을 돌려줄 위험이 있습니다. 두 경로의 역할이 다르므로 함께 둡니다.

| 대안 | 유리한 상황 | 비용 |
| --- | --- | --- |
| 제한된 순차 검사 | 별도 만료 인덱스 없이 먼저 구현할 때 | 키가 많으면 회수가 늦고 안전한 진행 위치 관리 필요 |
| 만료 시각 순 자료구조 | 다음 만료 항목을 우선 찾고 싶을 때 | 갱신·삭제 시 별도 구조와 저장소의 일관성 관리 |
| 매번 전체 검사 | 아주 작은 저장소에서 단순하게 확인할 때 | 키가 늘면 요청 처리를 오래 점유 |

**쉬운 사례:** 키 10만 개를 중복 없이 100개씩, 100ms마다 검사한다면 한 바퀴에 약 100초가 걸립니다. 단순 계산 예시이며 실제 회수 시간의 보장이 아닙니다. 빈 버킷 비용과 타이머 지연도 남습니다.

**현재 판단:** 검사량을 제한하는 방향은 요청 지연과 연결됩니다. 100ms·100개가 적절한지는 실측해야 합니다. 버킷 번호와 다음 검사 노드를 기억하고, 삭제 전에 커서를 옮기며 리해싱 후 처음부터 재시작합니다. 빈 버킷 비용도 제한하려고 회차당 최대 100버킷 방문을 추가했습니다. 반복 확장 시 회수 지연은 남습니다.

## 7. HTTP 인터페이스

**현재 선택:** Flask + Waitress의 HTTP API. POST /set·/get·/delete, JSON 키·값·TTL과 응답은 [API](API.md)에 확정 규격을 기록합니다.

| 대안 | 유리한 상황 | 비용 |
| --- | --- | --- |
| HTTP | 외부 앱과 익숙한 요청 도구로 기능을 확인할 때 | HTTP 처리·라이브러리·요청 변환 비용 |
| 자체 줄바꿈 프로토콜 | 바이트 수신과 프레이밍 자체가 학습 목표일 때 | 클라이언트와 파싱 규칙을 별도로 만들고 유지 |
| RESP 호환 | 기존 Redis 클라이언트 사용이 목표일 때 | 해당 규격의 타입·길이·오류 동작을 구현·검증 |

**현재 판단:** 외부 사용성과 저장 엔진 검증에 집중해 HTTP로 변경했습니다. 실제 Redis와 같은 외부 프로토콜을 만들었다고 설명하지 않습니다. HTTP/1.1은 보통 TCP 위에서 사용되므로 'TCP 대신 HTTP'는 전송 계층을 없앴다는 의미가 아닙니다.

## 8. 입력·TTL·HTTP 세부 규칙의 이유

빈 키를 거부하는 대안도 있지만 문자열 계약에서 특별히 제외할 필요가 없어 허용했다. 빈 값은 None과 구별한다. 원문 공백을 유지하고 UTF-8 바이트로 길이를 제한한다. 키 1 KiB·값 1 MiB·본문 8 MiB는 경계를 검증하기 위한 시작값이다. JSON 이스케이프는 전송 크기를 늘리므로 값 길이와 본문 길이를 구분한다.

TTL 생략은 무기한, 잘못된 TTL은 거부한다. 0을 즉시 삭제로 해석하는 대안 대신 오입력을 드러낸다. 단조 시간은 시스템 시각 변경으로 TTL이 늘어나는 것을 피한다. 일반 저장은 TTL을 제거하고 TTL 포함 저장은 새 시각으로 교체한다.

JSON 본문에 키를 담으면 빈 키·슬래시·줄바꿈을 경로로 표현할 부담이 줄어든다. 대신 조회도 POST라 일반적인 GET 기반 HTTP 캐시를 활용하는 형태는 아니다. 없는 키는 예상 가능한 결과라 200과 found:false를 사용한다. 404도 가능한 대안이다.

미정의 필드는 무시하지 않고 400으로 거부한다. ttl_ms를 ttl로 오타 낸 요청이 무기한 저장되는 것을 방지하지만 확장 필드를 보내는 클라이언트에는 엄격하다. 입력 오류 시 기존 데이터를 변경하지 않는다.

## 9. 영속성의 범위

**현재 선택:** 초기 필수 범위에서 제외.

캐시처럼 원본에서 다시 채울 수 있는 데이터와 재시작 후에도 반드시 남아야 할 원본 데이터는 요구가 다릅니다. 스냅샷은 시점 간 변경 손실을, 변경 로그는 기록·재생과 디스크 반영 정책의 비용을 고려해야 합니다. 영속성을 선택 과제로 둔 만큼 현재 복구·무손실을 보장하지 않습니다.

## 앞으로 선택을 기록하는 형식

결정할 때마다 **해결할 문제 → 비교한 대안 → 이득이 되는 사례 → 손해가 되는 사례 → 이번 목표에서 우선한 조건 → 미검증 가정 → 다시 볼 조건**을 기록합니다. 대안의 장점만 모아 이미 정한 결정을 정당화하지 않습니다.

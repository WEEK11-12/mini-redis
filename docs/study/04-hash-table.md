# 4. 해시 테이블 설계와 구현 (과제의 핵심)

> - 왜 O(1)인가: 순차 탐색 O(N)과 해시 조회 비교
> - 해시 함수: 키를 배열 위치로 바꾸는 방법과 좋은 해시 함수의 조건
> - 충돌 처리: 체이닝과 오픈 어드레싱, 각각의 트레이드오프
> - 리사이징: 부하율(load factor), 테이블 확장과 재해싱
> - 주요 함수의 동작: put(set), get, delete, 키 갱신
> - 설명할 수 있어야 하는 것: 설계 원리, 구현 과정, 함수별 동작 방식
> - 참고: Redis dict의 점진적 리해싱

---

## Hash Table
- **핵심** : 키가 많아져도 원하는 값을 찾기 위해 처음부터 전부 훑지 않겠다.
- 예시
  ``` plain text
  ("a", 10), ("b", 20), ("c", 30), ("d", 40)
  ```
  - **순차 탐색 $O(N)$** : "d"의 값을 찾기 위해 "a"부터 하나씩 키를 비교
  - **해시 조회 $O(1)$** : key → 찾아볼 저장 위치를 계산
    - 언제나 한 번에 찾는다는 뜻은 아님
    - 목록의 맨 앞부터 훑지 않고 그 위치로 갈 수 있음 (평균 $O(1)$)

#### 해시 함수
- **해시 함수** : 키를 받아 저장 위치를 정하는 계산 규칙
  - 예를 들어 배열에 키 "apple"의 값을 저장한다면, 해시 함수로 "apple"이 들어갈 칸을 정함
  - 조회할 때에도 같은 키에 같은 규칙을 적용하므로 저장할 때의 칸을 다시 찾아갈 수 있음
- 해시 함수의 성질
  - **같은 키에는 언제나 같은 위치를 계산해야 한다.**
  - **서로 다른 키는 가능한 한 여러 칸에 고르게 퍼트려야 한다.**
    - 키들이 한 칸에 몰리면, 그 칸에서 다시 여러 키를 비교해야 하기 때문에, 빠른 조회의 이점이 줄어든다

#### 충돌 처리
- **충돌** : 서로 다른 키가 해시 함수를 거쳐 **같은 배열 칸**에 도착하는 경우
  - 해시값으로 위치를 빨리 좁힐 수는 있지만, 서로 다른 키가 절대 겹치지 않게 보장하는 것은 아님
  - 해시 테이블에는 충돌이 났을 때 **두 키를 모두 보관하고 구별**하는 방법이 필요
- `체이닝(chaining)` : 같은 칸에 도착한 키-값 쌍을 그 칸에 여러 개 **연결해 보관**하는 방식
  ``` plain text
  3번 칸 → ("apple", 10) → ("grape", 20)
  ```
  - "grape" 조회 : 해시 함수로 3번 칸을 찾음 → 그 칸에 연결된 항목들의 실제 키를 비교 → "grape"를 만나면 값 20을 가져옴
- `개방 주소법(open addressing)` : 충돌이 나면 배열의 다른 빈 칸을 찾아 지정
  - 해시 함수로 얻은 배열 칸을 이미 다른 키가 차지 → 탐색 규칙에 따라 다음 칸들을 살펴봄 → 빈 칸을 찾아 키-값 저장
  - 조회할 때에도 저장할 때와 같은 순서로 칸을 살펴봄 
- 비교
  - **체이닝** : 같은 칸의 항목들을 연결 → 충돌이 나도 새 항목을 붙일 수 있음. 대신 연결해 둘 추가 공간이 필요. 
  - **개방 주소법** : 별도의 연결 구조가 필요 없음. 배열이 찰수록 빈 칸을 찾기 위해 여러 빈 칸을 살펴봐야 함. 
- 선택 기준
  - **체이닝** : 항목이 늘어나거나 삭제가 찾을 때 구현, 처리가 비교적 직관적. 연결 구조를 위한 추가 메모리가 듦
  - **개방 주소법** : 배열의 연속된 메모리를 활용하기 좋음. 빈 칸을 충분히 유지해야 성능이 좋아지고, 삭제할 때 단순히 칸을 비우면 조회 경로가 끊길 수 있어 처리가 더 까다로움.
  - 예를 들어, 키 수를 예측하기 어렵고 삭제도 빈번한 저장소를 처음 구현한다면, 체이닝이 설명하고 구현하기 쉬운 선택일 수 있음. 반대로 메모리 사용과 조회 성능을 세밀하게 최적화하려는 경우에는 개방 주소법도 검토할 만 함.

#### 리사이징
- **부하율(load factor)** : 해시 테이블의 크기에 비해 항목이 얼마나 들어 있는지를 나타내는 값
  ``` plain text
  부하율 = 저장된 항목 수 ÷ 배열의 칸 수
  ```
  - 부하율이 높아지면 충돌이 더 자주 일어날 수 있음
    - 체이닝 : 한 칸에 연결된 항목이 길어짐
    - 개방주소법 : 빈 칸을 찾기 위해 더 많이 살펴봄
  - 체이닝은 부하율이 1을 넘을 수도 있지만, 개방주소법을 배열 안의 빈 칸을 써야 하므로 그럴 수 없음.
- **재해싱(rehashing)** : 해시 테이블의 배열 크기가 바뀔 때, 기존 키-값들을 새 배열의 알맞은 칸에 다시 배치하는 작업
  - 키 위치를 정하는 과정 : 키를 해시 함수에 넣어 **해시값** 구함 → 그 값을 **배열의 칸 수로 나눈 나머지**를 칸 번호로 사용
    ``` plain text
    [어떤 키의 해시값이 13인 상황]
    배열이 4칸: 13 % 4 = 1 → 1번 칸에 저장
    배열이 8칸: 13 % 8 = 5 → 5번 칸에 저장해야 함
    ```
  - 배열을 늘릴 때에는 기존 항목을 하나씩 꺼내 새 크기로 위치를 계산하고 옮겨야 함 (재해싱)
  - 키나 값, 해시값이 바뀌는 게 아니라, **저장할 칸이 바뀌는 것**임/

## Hash Table 주요 함수
#### put(set)
- 키 → 해시값 구하기 → 배열의 칸 정하기
- 그 칸에 이미 항목이 있는지 확인
- 그 칸에 자신과 일치하는 키가 있는지 확인
  - 새 키를 저장 : 일치하는 키가 없다면 새로운 데이터를 그 칸에 추가
  - 이미 키가 있는 경우 : 새로운 항목을 만들지 않고, 기존 값을 갱신함
#### get
- 저장할 때와 같은 방식으로 키의 칸을 찾음
  - `해시 계산` → 찾을 범위를 좁힘
- 그 칸에서 실제 키가 일치하는 항목의 값을 반환 (일치하는 키가 없으면 키가 없는 것으로 처리)
  - `키 비교` → 정확한 항목 고르기
#### delete
- get할 때와 마찬가지로 칸을 찾고 실제 키를 비교
- 일치하는 항목을 반환하는 대신 **제거**
- 저장된 칸과 무관하게, 일치하는 키를 기준으로 항목을 삭제함
- 일치하는 키가 없다면 제거할 항목도 없음

---
## 점진적 리해싱
- **점진적 리해싱** : 기존 항목을 새 배열로 한꺼번에 옮기지 않고 조금씩 옮기는 것
- 배열을 확장 → 기존 항목을 모두 새 위치로 옮김
- 문제점 : 항목이 아주 많다면, 그 작업을 한 번에 처리하는 동안 다른 명령이 오래 기다릴 수 있음
- Redis의 구현 : **기존 테이블과 새 테이블을 함께 사용**

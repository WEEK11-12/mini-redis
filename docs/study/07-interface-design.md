# 7. 외부 인터페이스(API) 설계

> - 개발자에게 제공되는 형태: 서버 접속 + 명령 전송
> - 인터페이스 선택: HTTP REST API vs TCP 서버
> - API 설계: 저장, 조회, 삭제, 남은 시간 조회
> - 사용하는 쪽에서 본 편의성: 클라이언트 예시 코드

---

## Redis의 사용
- **서버 접속** : 명령을 주고받을 통로를 마련하는 일
- **명령 전송** : 그 통로로 저장, 조회 같은 작업을 요청하는 일

#### 명령 전송의 형태
- 프로토콜의 필요성
  ``` plain text
  앱 코드 → Mini Redis 클라이언트 라이브러리 → 요청 인코딩
         → 네트워크
         → Mini Redis 서버 → 요청 해석·실행
  ```
  - 인코딩 / 디코딩 과정에서 기준이 되는 규칙 필요
- 프로토콜 비교
  ``` plain text
  HTTP 방식:   앱 → HTTP 요청 → TCP 연결(보통) → Mini Redis
  직접 정의:    앱 → 직접 정한 명령 형식 → TCP 연결 → Mini Redis
  ```
- **HTTP 방식** : 웹에서 쓰는 HTTP 요청으로 저장소를 이용하게 하는 방식
  - `PUT /keys/user:1:name` 요청에 값 `민지`를 담아 보내고, 서버가 저장 결과를 응답할 수 있음
  - 웹 개발 도구로 호출하기 쉽다는 장점 → 일반 웹/앱 도구에서 쉽게 쓰는 것이 중요할 때 선택
- **자체 명령 방식** : 앱이 서버와 TCP 연결을 맺고, 그 위로 응용 계층의 형식을 직접 정해 명령 형식을 주고받는 방식
  - `SET user:1:name` 민지를 보내도록 설계
  - 명령을 어디서 구분하고 값에 공백이 있으면 어떻게 표현할지 직접 정해야 함
  - 이점 : 저장소에 필요한 통신만 골라서 요청 및 응답을 단순하고 작게 설계할 수 있음

---

## API 설계
- **API** : 한 프로그램이 다른 프로그램의 기능을 어떻게 요청하고, 어떤 결과를 받을지 정한 약속
  - Mini Redis의 내부 저장소를 외부 앱이 사용할 수 있도록 ‘사용 약속’을 만드는 것이 핵심
  - 각 작업의 결과를 일관되게 정하는 것이 중요함
  
  | 작업 | 요청에 필요한 것 | 결과 |
  |---|---|---|
  | 저장 | 키, 값 | 키에 값을 저장. 같은 키가 있으면 덮어씀 |
  | 조회 | 키 | 해당 값 반환 |
  | 삭제 | 키 | 해당 키와 값을 제거 |
  | 남은 시간 조회 | 키 | 만료까지 남은 시간 반환 |

- 저장: 같은 키를 다시 저장하면 덮어쓰는가? 덮어쓸 때 기존 만료 시간은 유지되는가?
- 조회: 없는 키와 만료된 키를 사용하는 쪽에서 어떻게 받는가? 만료된 값이 반환되어서는 안 됨
- 삭제: 없는 키를 삭제해도 성공으로 보는가, 아니면 “삭제한 항목 없음”을 알려주는가?
- 남은 시간 조회: 만료 시간이 없는 키와 키 자체가 없는 경우를 어떻게 구별하는가?

#### 요청·응답 형식
- 핵심 : 앱이 결과를 보고 “값을 받았는지, 값이 없는지, 요청이 잘못됐는지” 판단할 수 있어야 한다
- 없는 키, 만료된 키, 잘못된 요청의 응답 등의 경우 고려
- HTTP를 택했다면 404, 400 같은 상태 코드를 활용할 수 있음
- 자체 명령 방식을 택했다면 그에 해당하는 응답 형식을 직접 정해야 함

## 사용자 시각으로 보기
``` python
response = requests.get("http://mini-redis/keys/greeting")

if response.status_code == 200:
    print(response.text)       # 저장된 값 사용
elif response.status_code == 404:
    print("저장된 값 없음")
```
- HTTP 방식으로 조회 API을 만든 예시
- 앱 개발자가 키를 보내고 결과를 쉽게 구별해 사용할 수 있는지가 중요
- 사용하는 쪽의 코드로 표현해보면, API가 이해하기 쉬운지 드러남.

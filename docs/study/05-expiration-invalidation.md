# 5. 만료와 무효화
> - 만료 시간 저장 방식: 만료 시각(타임스탬프) vs 남은 시간
> - 만료된 값을 요청받았을 때의 처리: Lazy 삭제(조회 시 확인)
> - 만료된 키의 메모리 정리: Active 삭제(주기적 정리)와 트레이드오프
> - 데이터 무효화(deprecated): 명시적 삭제 API와 TTL
> - 캐시와 원본 DB의 불일치 문제
> - 엣지 케이스: 만료 직전 조회, TTL 갱신, 만료 후 같은 키 재저장

---

## 만료 시간 저장 방식
- 만료 시각 저장: 키를 저장할 때 “이 키는 언제까지 유효하다”는 시각을 함께 기록. 조회할 때 현재 시각이 그 시각을 지났는지 확인.
- 남은 시간 저장: “앞으로 얼마나 남았다”는 값을 기록. 시간이 흐른 만큼 이 값을 계속 바꿔야 한다면, 조회가 없어도 시간을 반영하는 작업이 필요.

---

## 만료된 키 처리
- **Lazy 삭제** : 키를 조회하는 순간 만료 시각을 확인 → 이미 만료됐다면 값을 반환하지 않고 그 키를 삭제
  - 만료된 키에 대해 없는 키처럼 응답하며 저장된 항목도 제거
  - 단점 : 아무도 조회하지 않는 만료 키는 이 방식만으로 메모리에서 정리되지 않음
- **Active 삭제** : 저장소가 주기적으로 키의 만료 여부를 확인해 제거함
  - 다시 조회되지 않는 만료 키도 메모리에서 치울 수 있다는 장점이 있음
  - 키를 확인하는 작업 자체가 시간과 CPU를 쓰므로, 자주·많이 확인할수록 정리는 빨라지지만 다른 요청을 처리할 여유는 줄어듬
- 위 두 방식은 서로 대체하기보다 함께 쓸 수 있음

---

## 데이터 무효화
- 캐시에 값이 남아 있어도 더 이상 유효한 값으로 사용하지 않게 하는 것
- 데이터 무효화 방법
  - `DEL` : 명시적 삭제. 앱이 직접 캐시 키를 바로 삭제. **변경을 알게된 시점에서 즉시 무효화**
  - `TTL` : **정해둔 시간이 지나면** 값을 사용하지 않게 함

#### 캐시 ↔ 원본 DB
- 캐시는 DB와 별도로 저장된 값 → DB를 수정했다고 캐시가 자동으로 바뀌지는 않음
- DB의 값을 변경할 때 관련 캐시 키도 삭제하거나 새 값으로 갱신해야 함.
  - TTL은 오래된 값이 언젠가는 만료되는 것을 보장해주지만, 만료되기 전의 불일치까지 막아주지는 않음
- 데이터 무효화 : 단순히 메모리를 정리하는 일이 아니라, **앱이 오래된 데이터를 읽지 않도록 하는 일**이기도 함

---
## 엣지 케이스
#### 만료 직전 조회
- 조회 시점에 아직 만료되지 않았다면 값을 반환
- 반환 직후 유효 기간이 끝날 수는 있지만, 이미 완료된 조회 결과를 거슬러 취소하지는 않음
- 처리 :  값을 읽은 시점에는 처리가 어려우므로, 그 값으로 실제 작업을 승인하는 시점에 유효한지 확인

#### TTL 갱신
- TTL을 갱신하면 만료 시각도 새 기준으로 바뀜
- 만료 판단에는 항상 그 키의 최신 TTL이 적용되어야 한다
- 주의 : 주기적으로 만료 키를 효율적으로 찾으려고 별도의 구조를 둘 때, 만료 정보를 두 곳에서 관리할 수 있음

#### 만료 후 같은 키로 다시 저장
- 키 이름이 같아도 새로 저장한 값에는 이전 값의 만료가 적용되면 안 됨
- 주의
  - Lazy 삭제: 만료됐지만 아직 남아 있는 항목 자체를 새 저장이 올바르게 덮어쓰는가?
  - 별도 힙: 항목을 올바르게 덮어쓴 뒤에도 남은 옛 만료 예약이 새 값을 건드리지 않는가?

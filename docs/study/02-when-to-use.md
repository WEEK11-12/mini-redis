# 2. 언제, 어떻게 Redis를 쓰나

> - 대표 사용처: 캐시, 세션, 조회수/카운터, 랭킹, 인증번호(TTL), 요청 제한
> - 서비스 구조에서의 위치: 앱 서버 ↔ Redis ↔ DB
> - 캐시 연동 방식: Cache-Aside(앱이 직접 처리)와 Read-Through
> - Redis가 맞지 않는 경우: 복잡한 조회/조인, 메모리보다 큰 데이터

---

## Redis의 사용
#### 캐시
- 다시 필요할 가능성이 큰 결과를 잠시 보관해 재사용하는 것.
  - 원본 데이터를 대신 만들거나 관리하는 것이 아님.
- **사용 이유** : 같은 조회를 반복할 때 원본 DB가 처리해야 할 일을 줄이기 위함
- 캐싱 방법 : **앱 서버가 Redis 조회와 DB 조회를 직접 결정함** (_Cache-Aside_)
  - 앱 서버 → Redis에 키에 해당하는 값이 있는지 먼저 확인
  - 값 없음 → DB에서 조회한 뒤, Redis에 저장
  - 값 있음 → 찾은 값을 바로 반환
  - **문제점** : DB의 상품 정보가 나중에 바뀌면, Redis의 값도 맞춰야 한다는 문제가 있음
#### 세션
- 로그인한 사용자의 상태를 서버가 알아보기 위해 보관하는 정보.
  - 세션 정보를 Redis에 저장 → 앱 서버는 Redis에서 이 정보를 찾아 어느 사용자의 요청인지 확인 가능
- **사용 이유** : 여러 앱 서버가 같은 세션 정보를 빠르게 조회할 수 있음
#### 조회수/카운터
- 어떤 일이 일어날 때마다 숫자를 하나씩 올리는 용도로 사용.
  - 앱 서버가 값을 읽어 직접 더한 뒤 다시 저장하는 방식이 아니라, 값 증가를 Redis 한 명령으로 처리
- **사용 이유** : 동시에 여러 요청이 와도 각각의 증가가 빠지는 문제를 피할 수 있음
  - `INCR` 명령어가 한 번의 증가를 안전하게 처리함
- 이러한 값은 Redis에만 둘 수도, DB에도 반영할 수도 있음 (선택의 문제)
#### 랭킹
- 항목마다 점수를 붙여 보관하고, 점수 순서로 가져오는 _Sorted Set_을 제공
- `Sorted Set` : 요소를 '멤버(member) + 점수(score)'로 다룸.
  - Sorted Set 자체가 value임. 임의의 키로 저장 → 반환된 Set은 score로 정렬된 상태
#### 인증번호
- 인증번호는 잠깐만 유효해야 함 → **만료 시간 (TTL, Time To Live)** 개념이 중요
- `TTL` : 설정된 시간이 지나면 키가 만료되고, 더이상 유효한 값으로 취급되지 않음
- **사용 이유** : 짧은 시간 뒤 쓸 수 없어야 하는 값에 적합
- 주의 사항 : 한 번 사용한 번호를 즉시 무효화하는 것은 TTL 외의 별도의 방법으로 처리해야 함
#### 요청 제한
- 일정 시간 동안 한 사용자가 요청할 수 있는 횟수를 제한하는 것
  - 앱 서버가 사용자 별 시도 횟수를 Redis에 기록
  - 요청이 올 때마다 횟수 증가
  - 지정 시간 내에 요청 횟수가 한도를 넘으면 요청 거절
- **카운터**와 **TTL**을 함께 사용 

---

## 서비스 구조와 Redis의 위치
- 앱 서버가 Redis와 DB를 각각 사용함
  ``` plain text
  사용자 → 앱 서버 → Redis
                ↘ DB
  ```
- `앱 서버 ↔ Redis ↔ DB`의 관계로 나타낼 수도 있음
  - 하지만 모든 DB 요청이 반드시 Redis를 통과한다는 뜻이 아님
  - 반례 : Redis는 빠른 재사용에, DB는 원본 데이터 보관에 쓰는 구성

---

## 캐시 연동 방식
``` plain text
Cache-Aside: 앱 서버가 Redis 확인 → 없으면 앱 서버가 DB 조회
Read-Through: 앱 서버가 캐시 계층에 조회 → 없으면 캐시 계층이 DB 조회
```
- Cache-Aside : 값이 없을 때 **앱 서버가 직접 DB를 조회**하고 Redis에 저장
- Read-Through : 앱 서버가 캐시 계층에 조회를 요청하고, 값이 없을 때 **DB에서 가져오는 일을 캐시 계층이 맡음**
  - Redis에서 자동적으로 Read-Through를 실행하지 않음.
  - DB 조회까지 담당하도록 하고 싶으면 별도의 캐시 계층을 구성해야 함.

---

## Redis가 적합하지 않은 경우
#### 복잡한 조회/조인
- Redis는 일반적인 관계형 DB와 같은 기능을 제공하지는 않음
  - Redis는 이미 알고 있는 키로 값을 빠르게 찾는 데 강함
  - 반면, **여러 데이터 사이의 관계를 따라가며 조건에 맞는 대상을 찾아내는 기능은 제공하지 않음**
- 복잡한 쿼리 문제
  - DB는 분리된 데이터를 연결하고 조건을 적용하는 쿼리를 작성할 수 있음
  - Redis는 키 조회 방식을 기본으로하기 때문에, 이러한 조회가 부적절함
#### 메모리보다 큰 데이터
- 모든 데이터를 Redis에 넣으면, 그만큼의 메모리가 필요해짐
  - 전체 상품 → DB에 보관하는 것이 적합
  - 자주 조회되는 일부 → Redis에 캐시하는 것이 적합
- Redis에 모든 데이터가 항상 있다고 기대해서는 안 됨
  - 캐시가 가득 찼을 때 오래되거나 덜 필요한 값을 내보내도록 구성할 수 있음

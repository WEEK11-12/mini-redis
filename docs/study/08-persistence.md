# 8. 서버 다운 대비: 영속성 (Optional)
> - 메모리 저장소의 약점: 서버가 꺼지면 데이터가 사라짐
> - RDB: 주기적 스냅샷, 구현이 쉽지만 마지막 시점 이후 유실 가능
> - AOF: 쓰기 명령 로그 누적, 재시작 시 재실행으로 복구
> - 트레이드오프: 안전성, 성능, 구현 난이도
> - 복구 시 만료된 데이터 처리

---

## 메모리 저장소의 약점
- 메모리에 저장된 데이터는 서버가 꺼졌다 다시 켜질 때 사라질 수 있다
- **영속성** : 재시작 후에도 데이터를 되살릴 수 있게 저장하는 것
- TTL과 비교
  - TTL 만료는 정해진 시간이 지나서 값을 더 이상 쓰지 않는 것
  - 서버가 꺼지면 아직 유효한 값인데 잃어버림

---

## 복구 방법
#### RDB 스냅샷
- **RDB 스냅샷** : 특정 시점의 저장소 상태를 파일로 남기는 방식
- 서버가 다시 시작하면 그 파일을 읽어 당시 상태로 복구함
- 매 명령을 기록하는 방식이 아니라, 저장한 시점의 상태를 통째로 남기는 방식
- **한계** : 저장 시점 사이에 생긴 변경은 복구하지 못할 수 있음
#### AOF
- **AOF(Append-Only File)** : 데이터를 바꾼 명령을 차례로 기록하는 방식
- SET 같은 쓰기 명령을 실행하면 그 쓰기 명령을 로그 파일에 남김
- 서버가 재시작하면 기록된 명령을 다시 실행해 메모리의 데이터를 복구함
- 파일에 기록한 내용을 디스크에 언제 확정하느냐에 따라 유실 가능성이 달라짐
#### 영속성의 선택 
- 얼마나 적게 잃을지 vs 기록에 드는 비용
- **RDB 스냅샷** : 스냅샷을 드물게 남기면?
  - 장점 : 평소 저장 부담은 줄어듦
  - 단점 : 마지막 스냅샷 이후의 변경을 잃을 수 있음
- **AOF** : 쓰기 명령을 자주 확정하면?
  - 장점 : 유실 범위를 줄일 수 있음
  - 단점 : 디스크 작업이 늘어나며, AOF를 쓴다는 사실만으로 무유실이 보장되지 않음
---

## 복구 시 만료 데이터 처리
- 저장된 키가 지금도 유효한지 다시 확인 필요
- 복구 시, 현재 시각과 저장된 만료 시각 비교 필요
- 중요 : _남은 시간_이 아니라 _만료 시각_을 기준으로 복구

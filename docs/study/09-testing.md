# 9. 테스트와 성능 비교
> - 단위 테스트: 저장, 조회, 삭제, 만료, 충돌, 리사이징
> - 기능 테스트: 간단한 API를 만들고 응답 값을 Mini Redis에 저장해 활용
> - 엣지 케이스 정리: 없는 키, 빈 값, 동일 키 덮어쓰기, 동시 요청, 만료 경계
> - 성능 비교: Redis(캐시) 사용 전/후 응답 시간 측정 방법

---
## 단위 테스트
- **단위 테스트** : 작은 기능 하나를 직접 호출해, 기대한 결과가 나오는지 확인하는 것
  - 한 기능에 특정 조건을 주고, 결과가 기대와 일치하는지 확인
  - 필수 테스트 항목 : 저장, 조회, 삭제
  - 추가로 고려할 것 : 만료, 충돌, 리사이징
- (예시) `저장` : "저장 함수가 오류 없이 끝났다"가 아니라, **저장한 값을 다시 읽었을 때 약속한 결과가 나오는지** 확인 필요

---

## 기능 테스트
- **기능 테스트** : 외부 프로그램이 테스트 대상 프로그램을 사용했을 때 제대로 동작하는지 확인
- 예시 : 간단한 외부 API 구현 →  API 응답 값을 mini-redis에 저장 → 다음 요청에서 값을 다시 활용할 수 있는지 확인
- 필요성 : 저장소 내부 함수가 각각 맞게 동작해도, 외부에서 보내는 요청이나 돌려받는 응답이 잘못 연결돼 있으면 실제 사용은 실패할 수 있기 때문

---

## 엣지 케이스 정리
#### 없는 키와 빈 값 구별
- 특정 키의 값으로 빈 문자열 저장 → "키가 있고, 값이 비어 있다"는 결과 반환 필요
- 저장하지 않은 키 `unknown`을 조회한 결과는 **다르게 취급해야 함**
- 앱이 **빈 값을 저장한 것인지, 키가 아예 없는 것인지** 파악할 수 있어야 하기 때문

#### 동일 키 덮어쓰기
- 같은 키에 다시 저장하는 경우
- 주의 : 새 항목을 하나 더 만들지 않고, 기존 키의 값이 바뀌도록 보장해야 함
- 인수 조건 : 이미 존재하는 키에 새로운 값을 다시 저장한 후, 다시 키를 통해 값 조회를 하면 변경된 값이 반환되어야 한다.

#### 동시 요청
- 여러 요청이 비슷한 시점에 들어와도 저장된 데이터가 잘못된 상태가 되지 않는지 확인 필요
- 동시에 요청을 보낸다고 내부 명령까지 반드시 동시에 실행되는 것은 아님
  - 순차 처리 구조 → 저장소 작업이 차례로 실행됨
- 테스트의 목적은 특정 구조를 강제하는 것이 아니라, 선택한 구조에서 요청이 겹칠 때도 기대한 결과가 유지되는지 확인하는 것

#### 만료 경계
- 만료 시각 바로 전과 후에 조회했을 때, 결과가 정한 규칙에 맞는지 확인
- 주의 : 메모리에서 아직 삭제되지 않았다는 사실과, 값을 사용해도 된다는 판단은 다르다.
  - Active 삭제와 Lazy 삭제 모두 만료된 데이터가 메모리에 존재할 수 있음
  - 조회할 때 만료 여부를 확인해야 함

---

## 성능 비교
- 같은 API 요청을 처리할 때, Redis 캐시를 사용 vs 캐시 사용하지 않음
- 주의 :
  - 서로 다른 데이터를 반환하거나 요청 조건이 다르면, 시간 차이를 캐시의 효과라고 해석하기 어려움
  - 캐시 미스와 캐시 히트는 처리 과정이 다름 → 둘을 섞어서 하나의 "캐시 사용 시간"으로 말하지 않고 구분해서 측정해야 함

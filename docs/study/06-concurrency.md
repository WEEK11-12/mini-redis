# 6. 동시성 구조

> - 경쟁 상태(race condition): 조회수 증가 예시
> - Redis의 방식: 싱글 스레드 이벤트 루프와 I/O 멀티플렉싱
> - 멀티 스레드 방식: 뮤텍스, 읽기/쓰기 락과 락의 비용
> - 원자성 보장: 명령 단위의 순차 처리
> - 만료 정리 같은 백그라운드 작업과의 충돌
> - Mini Redis의 구조 선택: 순차 처리 vs 락 기반

## 경쟁 상태
- **경쟁 상태** : 여러 요청이 같은 값을 다룰 때, 실행 순서에 따라 결과가 달라지는 상황
  ``` plain text
  요청 A: 10을 읽음
  요청 B: 10을 읽음
  요청 A: 11을 저장
  요청 B: 11을 저장
  ```
  - 두 번 증가했으니 기대한 값은 12
  - 실제 값은 11이 되는 문제
  - 원인 : 두 요청이 모두 증가 전의 값을 읽었기 떄문
- **읽기 → 증가 → 저장**의 흐름이 끝난 뒤, 다른 요청이 시작해야 원하는 결과를 얻을 수 있음
- **단순히 저장, 조회 기능이 각각 잘 동작하는지만으로는 동시 요청의 결과를 보장할 수 없음**

## Redis의 동시성 문제 처리
> 명령 실행은 한 번에 하나씩 진행됨
> <br> **여러 연결을 동시에 지켜보되, 준비된 요청의 명령은 하나씩 실행함**

- **싱글 스레드** : 핵심 명령을 실행하는 흐름이 하나라는 뜻.
  - 클라이언트 A의 명령을 실행하는 도중에 클라이언트 B의 명령 실행이 끼어들지 않음
  - 클라이언트가 한 명만 접속할 수 있다는 뜻은 아님
  - Redis의 핵심 명령 실행 모델이 싱글스레드일 뿐, Redis의 모든 작업에 스레드가 단 하나 뿐이라는 뜻은 아님
- **I/O 멀티플렉싱** : 여러 네트워크 연결 중 지금 읽거나 쓸 준비가 된 연결을 알아내는 방식
  - A, B, C가 접속해 있어도 서버가 A의 데이터가 올 때까지 A만 붙잡고 기다릴 필요가 없음.
  - 운영체제에게 여러 연결을 지켜보게 하고, 데이터가 도착한 연결을 알려받음
- **이벤트 루프** : 위의 일을 반복하는 서버의 흐름
  ``` plain text
  준비된 연결 확인 → 요청 읽기 → 명령 실행 → 응답 보내기 → 다시 준비된 연결 확인
  ```

#### (비교) 멀티 스레드 방식
- 전제 : 여러 스레드가 같은 헤시 테이블을 동시에 수정할 수 있음
- **뮤텍스(mutex)** : 한 번에 한 스레드만 공유 데이터에 접근하도록 잠그는 장치
  -  무엇을 한 덩어리로 보호하느냐가 중요해짐
- **읽기/쓰기 락** : 읽기만 하는 스레드끼리는 함께 들어오게 하고, 쓰기가 있을 때는 다른 읽기/쓰기를 막음
  - 읽기가 많은 구조에서는 유리할 가능성이 있음
  - 락을 잡고 풀고 기다리는 데도 비용이 들고, 어떤 데이터를 함께 잠글지 정하는 일도 필요함
- 멀티 스레드 방식은 "여러 스레드니까 무조건 빠른 것은 아님"

#### 원자성 보장
- “명령 하나의 원자성”과 “앱이 의도한 작업 전체의 원자성”은 다름
- **명령 하나의 원자성** : Redis의 명령 순차 실행 → 한 명령이 실행되는 도중 다른 클라이언트의 명령이 끼어들지 않음
  - `INCR views`처럼 한 명령으로 증가시키면 조회 → 증가 → 저장 작업 사이에 다른 클라이언트의 명령이 실행되지 않음
- **앱이 의도한 작업 전체의 원자성** : 원자적으로 실행되어야 하지만 각각의 명령으로 요청할 경우 한 작업처럼 보호되지 않음
  - 앱에서 GET views로 읽고, 계산한 뒤, SET views ...로 저장하면 세 명령 사이에 다른 클라이언트의 명령이 들어올 수 있음

## 백그라운드 작업
- 만료 정리 등의 명령 처리가 명령 스레드와 충돌하는 문제 발생 가능
- Active 삭제 상황
  - 만료 정리와 명령 실행이 **같은 흐름에서 순서대로 진행**된다면, 두 작업이 해시 테이블을 동시에 수정하지는 않음
  - **별도의 스레드가 만료 정리를 하면서 명령 스레드도 해시 테이블을 수정**한다면, 같은 키에 함께 접근을 할 수 있으므로 조정 필요

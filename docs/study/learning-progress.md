# Mini Redis 학습 진행 기록

## 완료: 1장 — Redis는 왜 등장했나

[01-background.md](./01-background.md)와 overview 1장에 나온 항목을 모두 다뤘으며, 사용자가 단위별로 이해를 확인했다.

1. 반복되는 DB 조회와 디스크 I/O 부담. 단, 디스크 기반 DB가 매번 디스크를 읽는 것은 아니며 DB 자체도 메모리 캐시를 사용한다고 구분했다.
2. 자주 쓰는 결과를 메모리에 `키 → 값`으로 저장하는 캐시와 Memcached. 키는 어떤 요청 결과인지 식별하며, 동일 입력 결과를 다시 찾기에 알맞다. 언어별 결과처럼 서로 다른 결과는 키도 구분해야 한다.
3. Memcached와 Redis의 비교: 구조 없는 값 전체를 꺼내 다시 저장하는 방식과 서버가 자료구조를 이해하고 일부를 조작하는 방식의 차이. 메모리 보관과 디스크 영속성은 별개의 성질이며 Redis의 영속성도 무유실 보장은 아니다.
4. Redis 탄생 배경: 2009년 Salvatore Sanfilippo가 실시간 로그 분석 서비스 LLOOGG의 확장 문제를 풀기 위해 만들고 이후 공개했다. ‘Memcached의 한계를 해결하려고 탄생했다’는 직접적인 역사적 동기로 단정하지 않도록 바로잡았다. 현재의 모든 자료형이 처음부터 있던 것은 아니며 Hash는 이후 추가됐다. 참고: [Redis FAQ](https://redis.io/docs/latest/develop/get-started/faq/).
5. Redis는 단순 GET/SET 외에 `INCR` 같은 서버 측 증가 명령과 자료구조별 명령을 제공한다. 명령 단위로 처리되는 증가와 앱의 GET→계산→SET을 구분했다. 범용 계산기라는 의미는 아니다.
6. 이후 캐시 외 세션·랭킹·큐 등으로 사용처가 확장되고 원본 DB와 공존할 수 있다는 점까지 설명했다.

## 완료: 2장 — 언제, 어떻게 Redis를 쓰나

[02-when-to-use.md](./02-when-to-use.md)와 overview 2장의 모든 항목을 다뤘으며, 사용자가 마지막 단위까지 이해를 확인했다.

1. 대표 사용처: 캐시(반복 조회 결과의 재사용), 세션(여러 앱 서버의 로그인 상태 조회), 조회수/카운터(`INCR`), 랭킹(Sorted Set), 인증번호(TTL), 요청 제한(카운터 + TTL).
2. 카운터의 원자적 증가와 결과의 장기 보관은 별개다. Redis에만 둘지 DB에도 반영할지는 유실 허용 범위 등 서비스 요구에 따라 결정한다.
3. Sorted Set은 하나의 Redis 키에 저장되는 값이며, 각 항목은 멤버와 점수의 쌍이다. 임의의 사용자 객체 필드를 골라 정렬하는 방식은 아니다.
4. 앱 서버가 Redis와 원본 DB를 각각 사용할 수 있다. `앱 서버 ↔ Redis ↔ DB`는 모든 DB 요청이 Redis를 반드시 거친다는 뜻이 아니다.
5. Cache-Aside에서는 앱 서버가 캐시 미스 후 DB를 조회한다. Read-Through에서는 캐시 계층이 그 일을 맡는다. Redis 서버 자체가 원본 DB를 자동 조회하지 않으며, 캐시 계층은 앱 서버 내부 모듈·라이브러리 또는 외부 서비스일 수 있다.
6. 기본 Redis의 키 조회 방식은 관계형 DB의 복잡한 조건 조회·조인을 그대로 대신하기에 적합하지 않다. 보관 대상이 메모리보다 훨씬 크다면 원본은 DB에 두고 일부만 캐시하는 방식을 설명했다. 디스크 영속성은 메모리 용량 문제를 없애지 않는다.

## 완료: 3장 — 사용자가 실제로 쓰는 기능

[03-how-to-use.md](./03-how-to-use.md)와 overview 3장의 개념 항목을 순서대로 다뤘고, 사용자가 단위별로 이해를 확인했다.

1. 기본 명령: `SET`, `GET`, `DEL`, `EXISTS`. `user:1:name`의 콜론은 키 이름의 관례일 뿐 Redis가 DB 엔티티나 필드를 자동으로 해석하지 않는다. `EXISTS`는 키 하나를 검사할 때 있으면 1, 없으면 0을 반환한다. 같은 키에 다시 `SET`하면 값을 덮어쓴다.
2. 만료: `SET ... EX`는 저장과 함께, `EXPIRE`는 기존 키에 TTL을 설정한다. `EXPIRE`는 설정 성공 1, 없는 키 0을 반환하고 기존 TTL도 새 시간으로 재설정할 수 있다. `TTL`은 남은 초를 반환하며, 만료 설정 없는 키는 -1, 없는 키는 -2다. 일반 `SET`으로 덮어쓰면 기존 TTL은 제거된다.
3. 자료구조: String은 별도 int 자료형이 아니며 정수로 해석 가능한 문자열에 수치 명령을 쓸 수 있다. List는 순서와 중복을 허용하고, Hash는 키 내부의 필드를 실제로 나눠 저장한다. Set은 중복을 허용하지 않고 순서를 보장하지 않으며, Sorted Set은 멤버에 숫자 점수를 붙여 정렬한다. 기본 자료구조는 서로 직접 중첩하지 않으며, 다른 키의 이름을 문자열로 저장해 앱에서 연결할 수 있다.
4. 원자적 명령: `INCR`은 String 키의 정수를 명령 하나로 증가시킨다. Hash 필드는 `HINCRBY`, Sorted Set 점수는 `ZINCRBY`를 쓴다. `RPUSH`, `SADD` 등도 개별 명령 단위로 처리되지만 앱의 여러 명령이 자동으로 원자적인 묶음이 되지는 않는다.
5. 접속: Redis 서버가 데이터를 저장하고 명령을 실행한다. `redis-cli`는 사람이 터미널에서 서버에 명령을 보내는 도구이고, 언어별 라이브러리는 코드의 함수 호출을 서버 명령·응답으로 중개한다.
6. 직접 체험 항목의 명령 흐름(저장→조회→`EX`로 다시 저장하며 TTL 설정→`TTL` 조회)은 설명하고 사용자가 목적을 확인했다. 현재 환경에서 `redis-cli`가 없어 실제 실행은 하지 않았으며, 사용자는 이론 학습만으로 충분하다고 선택했다. Mini Redis 구현 범위 결정도 사용자 요청에 따라 지금은 보류한다.

## 완료: 4장 — 해시 테이블 설계와 구현의 개념 학습

[04-hash-table.md](./04-hash-table.md)와 overview 4장의 주제를 개념 단위로 다뤘으며, 사용자가 마지막 점진적 리해싱까지 이해를 확인했다. 해시 테이블을 실제로 구현하거나 테스트한 것은 아니다.

1. 순차 탐색 O(N)과 해시 테이블의 평균 O(1) 조회를 비교했다. 평균 O(1)은 항상 한 번에 찾는다는 뜻이 아니다.
2. 해시 함수는 키를 해시값으로 바꾸고, 그 값을 배열 크기에 맞춰 칸 번호로 변환한다. 같은 키는 같은 규칙에서 같은 결과를 내야 하고, 키가 여러 칸에 고르게 퍼져야 한다. 해시값과 칸 번호는 다르다. `hash`의 어원(잘게 썰다)과 SHA 같은 암호학적 해시도 구별해 설명했다.
3. 충돌은 서로 다른 키가 같은 칸에 도착하는 것이다. 체이닝은 같은 칸의 항목을 연결하고, 오픈 어드레싱은 배열의 다른 빈 칸을 찾는다. 두 방식의 공간 사용, 배열이 찼을 때의 탐색, 삭제 난이도와 선택 기준을 비교했다. 칸이 같아도 실제 키를 다시 비교해야 한다.
4. 부하율은 항목 수를 배열 칸 수로 나눈 값이다. 높은 부하율은 충돌·탐색 비용을 늘릴 수 있어 배열을 확장한다. 배열 크기가 바뀌면 같은 해시값이라도 칸 번호가 달라질 수 있으므로 기존 항목을 새 크기에 맞게 재배치한다(리해싱). 사용자가 지적한 인과관계를 바로잡았다. 배열 크기만 바뀌면 해시값은 그대로일 수 있고, 해시 함수나 시드가 바뀌면 해시값 자체가 달라질 수 있다.
5. `put`은 키가 없으면 추가하고, 이미 있으면 기존 값을 갱신한다. `get`은 일치하는 실제 키의 값을 찾고, `delete`는 일치하는 키의 항목만 제거한다. 모두 해시 계산으로 후보 칸을 찾은 뒤 실제 키를 구별한다. 체이닝을 예로 들어 동작을 설명했다.
6. Redis `dict`의 점진적 리해싱은 기존 테이블과 새 테이블을 함께 두고 항목을 조금씩 옮겨 한꺼번에 옮길 때의 긴 대기를 줄이는 참고 사례다. Mini Redis의 필수 구현 방식으로 단정하지 않았다.

## 완료: 5장 — 만료와 무효화

[05-expiration-invalidation.md](./05-expiration-invalidation.md)와 overview 5장의 모든 항목을 개념 단위로 다뤘고, 사용자가 마지막 항목까지 이해를 확인했다. 구현·테스트를 진행한 것은 아니다.

1. 키에 남은 시간을 계속 갱신하기보다 만료 시각을 저장하고 조회 시 현재 시각과 비교하는 방식을 설명했다.
2. Lazy 삭제는 요청받은 키의 만료를 확인해 없는 키처럼 처리하고 제거한다. 조회되지 않은 만료 키는 메모리에 남을 수 있다.
3. Active 삭제는 주기적으로 만료 키를 찾아 메모리를 정리한다. 전체 해시 테이블을 훑는 방법과, TTL이 있는 키를 별도 힙·RB 트리 등으로 관리하는 선택지를 비교했다. 별도 구조는 필수가 아니며 정리 비용과 관리 비용의 절충이 있다.
4. 무효화는 값이 더 이상 유효하지 않도록 하는 일이다. 명시적 삭제는 변경을 알았을 때 즉시 처리할 수 있고, TTL은 만료 전까지 이전 값이 남을 수 있다. 원본 DB 수정만으로 캐시가 자동 갱신되지 않으므로 불일치가 생길 수 있다.
5. 만료 직전 조회는 그 요청의 확인 시점에 유효하면 값을 반환할 수 있지만, 인증 등 실제 승인 시점에 만료 여부가 중요한 작업은 사용 시 다시 유효성을 확인해야 한다. 문서는 구체적인 경계 정책을 지정하지 않았다.
6. TTL 갱신은 해시 테이블 항목의 만료 시각만 수정하는 구조라면 자연스럽게 처리된다. 별도 힙 등에도 옛 만료 예약이 있으면 갱신된 키를 잘못 삭제하지 않도록 일치 여부를 확인하거나 기록을 제거해야 한다. 이는 구현 선택에 따른 문제이지 TTL 갱신 자체의 필연적 문제가 아니다.
7. 만료 후 같은 키로 재저장할 때는 Lazy 삭제로 옛 항목이 남아 있더라도 새 값과 새 만료 조건으로 덮어써야 한다. 별도 만료 인덱스를 쓰면 이전 예약이 같은 이름의 새 값을 삭제하지 않도록 구별해야 한다.

## 완료: 6장 — 동시성 구조

[06-concurrency.md](./06-concurrency.md)와 overview 6장의 모든 항목을 개념 단위로 다뤘고, 사용자가 이해를 확인했다. 구현·테스트나 Mini Redis의 구체적인 동시성 구조 선택은 진행하지 않았다. 사용자는 구조 선택을 설계 과정에서 하기로 했다.

1. 경쟁 상태: 두 요청이 같은 조회수 값을 읽고 각각 증가 결과를 저장하면 증가 한 번이 사라질 수 있다.
2. Redis의 핵심 명령 실행은 순차적이다. 싱글 스레드는 클라이언트가 하나만 접속한다는 뜻이 아니다. 이벤트 루프는 준비된 연결을 확인하고 요청을 처리하는 반복 흐름이며, I/O 멀티플렉싱은 여러 연결 중 읽거나 쓸 준비가 된 연결을 운영체제의 감시 기능으로 알아내는 방식이다. 연결이 열려 있는 상태와 읽을 데이터가 준비된 상태는 다르다. Redis의 모든 작업에 스레드가 하나뿐이라는 뜻은 아니다.
3. 멀티스레드 대안에서는 공유 데이터를 여러 스레드가 동시에 건드릴 수 있으므로 뮤텍스로 읽기→증가→저장 전체를 보호해야 한다. 읽기/쓰기 락은 읽기끼리 함께 허용하고 쓰기 시에는 다른 접근을 막는다. 락의 대기·관리 비용 때문에 멀티스레드가 무조건 빠른 것은 아니다.
4. 명령 하나의 원자성과 앱의 여러 명령을 묶은 작업의 원자성은 다르다. `INCR` 한 명령은 순차 처리되지만 `GET`→계산→`SET` 사이에는 다른 명령이 들어올 수 있다.
5. 만료 정리와 명령 처리가 같은 흐름에서 순차 실행되면 저장소를 동시에 수정하지 않는다. 별도 스레드로 정리한다면 같은 키에 대한 조회·재저장과 충돌할 수 있어 동기화가 필요하다. 옛 만료 예약과 새 값을 구별하는 문제도 별개로 남는다.
6. Mini Redis의 순차 처리와 락 기반 처리의 차이 및 선택 기준을 설명했다. 과제는 동시성 문제가 생기지 않을 구조를 고민하라고 요구하지만 특정 방식을 지정하지 않는다. 구체적 선택은 이후 설계 과정으로 보류했다.

## 완료: 7장 — 외부 인터페이스(API) 설계의 개념 학습

[07-interface-design.md](./07-interface-design.md)와 overview 7장의 모든 항목을 다뤘다. 사용자는 API의 의미, 통신 방식, 네 가지 작업, 요청·응답 형식까지 이해를 확인했다. 마지막 클라이언트 예시 코드도 설명했지만 별도의 이해 확인 응답은 받지 않았다. 실제 API 규격 선택·설계, 구현·테스트는 하지 않았다.

1. API는 외부 앱이 Mini Redis의 기능을 어떻게 요청하고 어떤 결과를 받는지 정한 약속이다. 내부 해시 테이블 구현과 분리된다. 앱이 서버에 접속해 명령을 보내는 형태를 설명했다.
2. HTTP REST API와 자체 TCP 명령 방식은 같은 계층의 프로토콜을 고르는 비교가 아니다. HTTP는 응용 계층 요청 형식을 제공하며 보통 TCP 위에서 동작한다. 자체 방식은 TCP 바이트 흐름 위에 명령·인자·요청 경계와 응답 형식을 직접 정한다. 전용 클라이언트와 서버가 같은 형식을 이해해야 한다. 전용 방식이 항상 빠른 것은 아니며, 어떤 방식을 택할지는 정하지 않았다.
3. 저장·조회·삭제·남은 시간 조회는 같은 키의 상태를 서로 다르게 다룬다. 저장은 값을 만들거나 바꾸고, 조회는 현재 사용 가능한 값을 읽고, 삭제는 제거하며, 남은 시간 조회는 만료까지의 시간을 묻는다. 학습 관점에서는 덮어쓰기와 TTL, 없는 키와 빈 값, 이미 삭제되거나 만료된 키, 만료 설정이 없는 키의 의미를 구분했다. 세부 계약을 확정하지는 않았다.
4. 요청에는 작업에 필요한 키·값 등이 담겨야 하고, 응답은 값이 있음·값이 없음·잘못된 요청을 앱이 구별할 수 있어야 한다. 만료된 값은 사용 가능한 값으로 반환하지 않는다. HTTP 상태 코드나 자체 프로토콜의 응답 표기는 방식 선택 후 정한다.
5. 사용하는 앱의 짧은 HTTP 조회 예시로 API를 호출하고 결과를 분기하는 모습을 살폈다. 예시 URL·상태 코드는 확정된 Mini Redis 규격이 아니다. 앱 개발자의 입장에서 호출과 결과 해석이 쉬운지 확인하는 관점이다.

## 완료: 8장 — 서버 다운 대비: 영속성 (Optional)의 개념 학습

[08-persistence.md](./08-persistence.md)와 overview 8장의 모든 항목을 순서대로 다뤘고, 사용자가 각 단위의 이해를 확인했다. 영속성은 과제의 선택 사항이며 구현 여부나 구체적 저장 정책은 결정하지 않았다. 실제 구현·테스트도 진행하지 않았다.

1. 메모리의 키-값은 서버 종료 뒤 재시작만으로 복구되지 않는다. TTL에 따른 의도된 만료와 서버 종료로 유효한 값을 잃는 상황을 구분했다.
2. RDB(Redis Database)는 특정 시점의 상태를 스냅샷 파일에 저장하고 재시작 시 읽는다. 마지막 스냅샷 이후 파일에 남지 않은 변경은 장애 시 유실될 수 있음을 사용자가 설명했다.
3. AOF(Append Only File)는 쓰기 명령을 로그에 기록하고 재시작 시 재실행해 상태를 복구한다. 명령을 기록한다는 것과 디스크에 즉시 확정되어 무유실이라는 것은 다르다.
4. RDB·AOF의 안전성, 기록 비용·성능, 구현 난이도 사이의 절충을 설명했다. AOF도 디스크 확정 정책에 따라 유실 가능성이 달라지고, 어느 방식을 채택할지는 정하지 않았다.
5. 복구할 때 저장된 만료 시각을 현재 시각과 비교해 이미 만료된 키를 유효한 값으로 되살리지 않아야 한다. 종료 당시 남은 시간만 다시 부여하면 키의 수명이 늘어날 수 있다.

## 완료: 9장 — 테스트와 성능 비교의 개념 학습

[09-testing.md](./09-testing.md)와 overview 9장의 모든 항목을 개념 단위로 다뤘고, 사용자가 이해를 확인했다. 테스트를 실제로 작성·실행하거나 성능을 측정한 것은 아니다.

1. 단위 테스트는 저장·조회·삭제와 만료·충돌·리사이징 등에서 실행 성공 여부뿐 아니라 기대 결과와 일치하는지 확인한다. 단일 기능의 검증과 기능을 이어서 사용하는 검증은 구분한다.
2. 기능 테스트는 외부 앱이 API 응답 값을 Mini Redis에 저장하고 다시 가져와 활용할 수 있는지 확인한다. 내부 함수가 맞아도 외부 요청·응답 연결은 별도로 확인해야 한다.
3. 엣지 케이스는 없는 키와 빈 값의 구별, 동일 키 덮어쓰기, 동시 요청의 결과, 만료 시각 전후의 조회를 살폈다. 구체적인 API 결과 표현과 만료 경계 정책은 아직 정하지 않았다.
4. 성능 비교는 캐시 미사용과 캐시 사용의 같은 API 요청 응답 시간을 측정한다. 캐시 미스와 히트를 구분해야 하며, 비교 조건과 반환 데이터가 같아야 차이를 해석할 수 있다.

**study/00-overview.md의 1~9장 개념 학습 완료.** 과제의 구현 범위·API 규격·동시성 구조·영속성 채택 여부는 아직 결정하지 않았고, 구현·테스트·실측은 진행하지 않았다. 7장의 마지막 클라이언트 예시 코드는 설명했지만 별도의 이해 확인 응답은 받지 않았다. 이후 요청이 있으면 개념 복습 또는 구현·설계 단계의 출발점을 별도로 정한다.

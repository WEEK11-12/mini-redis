# 프로젝트 컨벤션

- 상태: 초기안 — 검토 대기
- 적용 범위: 문서, 의사결정, 코드, 검증, 에이전트 협업
- 근거: [과제 원문](assignment.md), [프로젝트 진행 원칙](decisions/0001-project-workflow.md)

이 문서는 사람이 읽는 프로젝트 운영 기준이다. AI도 이 기준을 참고하지만, AI가 읽는다는 이유만으로 Git에서 제외하지 않는다. 아래 세부 운영 방식은 초기안이며, 이미 정해진 원칙과 구분한다.

## 1. 목적과 현재 출발점

- Redis 이론 학습은 완료했다. 학습 완료를 구현·테스트 완료로 표시하지 않는다.
- 과제의 결과물을 만들고, 핵심 로직을 이해하고 설명할 수 있게 한다.
- AI는 선택지·비교·구현·검증을 지원하되, 중요한 선택을 임의로 확정하지 않는다.
- 확인된 목표와 범위는 [1단계 기록](iterations/01-scope-and-contract/overview.md)에 정리했다. 언어와 외부 통신은 [Python·HTTP API](decisions/0002-python-http-interface.md), 기본 캐시·응답 계약은 [D-0003](decisions/0003-http-response-contract.md)에서 정했고, 세부 구현 방식은 해당 단위에서 결정한다.
- 문서화는 실행과 판단을 돕는 만큼만 한다. 문서 양 자체를 완료 기준으로 삼지 않는다.

## 2. 문서 분류와 Git 관리

**작성 주체가 아니라 주 독자와 목적을 기준으로 나눈다.** 사람이 읽는 문서를 에이전트도 참고할 수 있다.

| 분류 | 경로 | 내용 | Git 관리 |
| --- | --- | --- | --- |
| 프로젝트 입구 | `README.md` | 프로젝트 소개, 주요 문서, 확정된 실행 방법 | 포함 |
| 과제 원문 | `docs/assignment.md` | 외부에서 주어진 과제의 기준 | 포함 |
| 공통 컨벤션 | `docs/conventions.md` | 사람이 확인·변경할 운영 기준 | 포함 |
| 학습 자료 | `docs/study/` | 사람이 참고할 개념 정리 | 포함 |
| 결정 기록 | `docs/decisions/` | 비교한 선택지, 선택 이유, 영향, 재검토 조건 | 포함 |
| 유동적 단계 계획 | `docs/plans/` | 전체 단계, 의존 관계, 현재 우선순위 | 포함 |
| 단계별 산출물 | `docs/iterations/` | 요구사항, 설계, 검증, 결과 | 포함 |
| 에이전트 진입 안내 | `AGENTS.md` | 공통 기준과 로컬 맥락의 읽기 순서 | 제외 |
| 에이전트 작업 맥락 | `.agent/` | 세션 이어가기, 학습 진행 기록, 역할 간 인계, 임시 검토 메모 | 제외 |

- `docs/plans/`, `docs/iterations/`는 실제 작성할 때 만든다. 빈 문서를 미리 채우지 않는다.
- 학습 진행 기록은 에이전트가 학습 맥락을 이어가기 위한 문서이므로 `.agent/learning-progress.md`에 두고 Git에서 제외한다. 사람이 읽는 개념 자료와 구분하며, 사람용 문서 목록에는 넣지 않는다.
- 에이전트 전용 문서는 반드시 `.agent/` 안에 둔다. 예외는 진입점인 `AGENTS.md`뿐이다. 하위 디렉터리에 필요한 `AGENTS.md`도 Git 제외 대상이다.
- `.gitignore`는 이미 추적 중인 파일을 자동으로 추적 해제하지 않는다. 문서 성격을 변경할 때는 내용을 분리하고 Git 추적 상태도 확인한다.
- 비밀·인증 정보는 어느 문서에도 기록하지 않는다. Git 제외는 보안 저장 수단이 아니다.
- 다른 환경에는 Git 제외 문서가 전달되지 않는다. 공유 작업 기준은 반드시 `docs/`에 남긴다. 로컬 에이전트 문서가 없으면 이 문서를 기준으로 진입 안내와 현재 맥락을 다시 만든다.

## 3. 문서 작성 규칙

### 이름과 구조

- 파일·디렉터리는 영어 소문자 `kebab-case`, 확장자는 `.md`를 사용한다. `README.md`, `AGENTS.md`와 기존 파일명은 예외다.
- 본문은 한국어로 작성하고 코드 식별자·명령·API 이름은 원문을 유지한다.
- 링크는 저장소 내 상대 경로를 사용한다. 로컬 절대 경로를 공유 문서에 넣지 않는다.
- 날짜가 필요한 기록은 `YYYY-MM-DD`를 사용한다. 같은 날짜의 사건 순서가 중요하면 시간대도 명시한다.
- 문서 상단에 상태와 관련 근거를 적는다. 공유 문서는 기여자별 작성 내역보다 목표·결정·검증 결과에 집중한다.
- 기존 과제 원문은 재해석해서 덮어쓰지 않는다. 해석·범위·질문은 별도 문서에 적는다.

### 상태와 근거

| 대상 | 상태 |
| --- | --- |
| 일반 산출물 | `초안` → `검토 중` → `확정`, 이후 `대체됨` 가능 |
| 결정 기록 | `제안` → `채택` / `기각` / `보류`, 채택 뒤 `대체됨` 가능 |
| 단계 진행 | `계획` → `진행 중` → `결과 검토 대기` → `완료`, 필요 시 `중단` |

- 문서 확정과 구현 완료는 별개다. 설계가 확정되어도 기능은 미구현일 수 있다.
- 과제에서 확인한 사실, 채택된 결정, 검토 중인 제안, 미결정 사항을 구분한다. 누가 문장을 작성했는지에 따라 나누지 않는다.
- 사람이 읽는 본문은 확정된 범위·선택·검증 상태를 직접 서술한다. 대화 상대를 `사용자가 ~했다`처럼 제3자로 지칭하거나 AI와의 대화 이력을 서술하지 않는다. 결정의 승인 출처와 역할 경계가 필요한 메타데이터는 유지한다.
- 사실에는 파일·절·실행 결과 등 확인 가능한 근거를 연결한다.
- 테스트 결과에는 실행 명령, 실행 조건, 실제 결과를 적는다. 미실행·실패·차단도 그대로 남긴다.
- AI의 검토 통과는 실제 실행 통과나 결과 검토를 대신하지 않는다.
- 완료 체크는 증거가 있을 때만 한다. 계획·예상 결과를 실행 결과처럼 쓰지 않는다.

## 4. 의사결정 기록

상세 규칙과 양식은 [decisions 안내](decisions/README.md)를 따른다. 사람이 생각하고 결정하며, 에이전트는 요구사항·설계·검증·구현의 반복 실행을 돕는다.

- 목표·범위, 기술 스택, 외부 인터페이스, 주요 동작 정책, 동시성 구조 중에서도 여러 단위에 영향을 주거나 바꾸는 비용이 커서 선택의 근거를 다시 살필 만한 것만 기록한다. 세부 사항은 기존 결정의 공유 계약이나 해당 이터레이션에 둔다.
- 프로젝트 진행 방식에 관한 결정도 기록할 수 있다. 각 기록의 필수 `카테고리`와 결정 목록의 분류 열로 `프로젝트 진행`, `요구사항`, `설계`, `구현`, `검증` 중 주된 결정 영역을 드러낸다.
- 결정 배경은 현재의 목표·판단 기준과 해당 결정에 직접 필요한 근거 중심으로 쓴다.
- AI는 판단 기준과 현실적인 선택지를 비교하고 추천 이유를 밝힌다. 추천은 채택이 아니다.
- 선택이 확정되면 결과·이유·영향을 기록한다. 이유가 확인되지 않았으면 추정하지 말고 미확인으로 표시한다.
- 실행 가능한 코드 실험이 필요하면 목적·범위를 먼저 합의한다. 실험 결과도 설계 확정과 구분한다.
- 사소한 구현 선택, 한 단위의 진행·검증 기록, 오탈자 수정마다 결정 문서를 만들지 않는다.
- 채택한 결정을 변경할 때는 새 결정 기록으로 이전 기록을 연결한다. 과거 판단의 근거를 조용히 지우지 않는다.

## 5. 작은 단계로 반복하는 진행 방식

### 전체 그림은 가볍게, 현재 단계는 구체적으로

1. 제작 목표와 과제 해석을 정리한다.
2. 전체 구현을 작은 단계로 나눈 유동적 계획을 만든다. 단계별 목적·확인할 결과·선행 조건·의존 관계·미결정 사항만 적는다.
3. 현재 단계에 대해서만 아래 반복을 진행한다.
4. 결과를 검토한 뒤 다음 단계와 계획을 다시 조정한다.

미래 단계까지 상세 요구사항·설계·코드를 한 번에 확정하지 않는다. 단계 간 의존성을 없앨 수 있다고 가정하지 않고, 공유할 인터페이스를 먼저 드러내 변경 영향을 줄인다.

### 단계별 반복과 확인 지점

각 단위의 작업을 시작할 때 [공통 진행 체크리스트](plans/implementation-units.md#진행-체크리스트)를 바탕으로 그 단위의 `overview.md`에 확인할 항목을 **먼저** 적고, 체크리스트 순서에 따라 진행한다. 계획·제안, 확정된 범위, 실제 구현·테스트 결과를 구분해 체크한다.

| 순서 | 확인할 일 | 지원 내용 | 다음으로 넘어가는 기준 |
| --- | --- | --- | --- |
| 요구사항 정의 | 요구사항·예외·궁금한 점을 먼저 나열 | 비교용 초안과 누락·충돌 질문 정리 | 이번 단계 범위와 관찰 가능한 완료 조건 확정 |
| 설계 | 선택 기준을 정하고 대안을 비교해 선택 | 인터페이스와 대안의 장단점·비용·위험 정리 | 중요한 선택이 기록되고 검증할 계약이 명확함 |
| 설계 검증 | 검토 쟁점과 수정 필요 여부 확인 | 요구사항 대응, 경계 조건, 의존 관계 검토 | 진행을 막는 쟁점이 해결되거나 영향과 함께 명시적으로 보류 |
| 구현 | 확정한 범위 안에서 진행 상황 확인 | 작은 변경 단위로 구현·테스트, 예상 밖 선택은 재검토 | 이번 단계의 실행 가능한 결과물과 검증 증거 확보 |
| 구현 검증 | 결과물을 실행하거나 시연을 확인하고 핵심 동작 설명 | 실제 테스트·실행 결과와 한계 정리 | 완료 조건 충족 및 결과 검토 |

- 요구사항 초안을 검토하기 전에 AI가 전체 요구사항을 임의로 확정하지 않는다. 필요하면 먼저 질문과 사고할 틀을 제공한다.
- 구현 중 새로운 정책·기능·인터페이스 결정이 필요하면 멈추고 결정 지점으로 돌아간다.
- 실패·누락이 발견되면 요구사항·설계로 돌아갈 수 있다. 범위·결정·검증 계획도 함께 갱신한다.
- 단순한 수정은 관련 항목만 검토한다. 매번 모든 문서를 새로 만들지 않는다.
- 완료는 문서 완성이 아니라 실제 결과와 검토를 기준으로 판단한다. 미해결 쟁점을 다음 단계로 넘긴다면 영향과 재검토 조건을 남긴다.

### 단계별 문서의 최소 단위

필요할 때 `docs/iterations/01-<topic>/`처럼 생성한다. 단계 번호는 작성 당시 순서이지 고정된 일정이 아니다.

- `requirements.md`: 이번 범위·비범위와 요구사항별 고정 ID(`REQ-<단계>-<일련번호>`), 명세, 관찰 가능한 인수 조건, 출처·상태를 적는다. ID는 재번호화하지 않고 구현·테스트 근거와 연결한다. [단계별 요구사항 색인](iterations/README.md)에서 각 단위의 명세를 모아 찾는다. 1단계의 기존 공유 계약에는 ID를 소급해 붙이지 않는다.
- `design.md`: 외부·내부 인터페이스 계약, 구성 요소 책임·의존 관계, 결정 기록 링크, 실패·경계 처리.
- `verification.md`: 설계 검토 및 실제 테스트의 구분, 검증 대상·명령·조건·결과·남은 위험.
- `result.md`: 실제 변경과 시연 방법, 결과 검토 상태, 핵심 로직 설명, 남은 일과 다음 단계 영향.

작은 단계의 설계·검증·결과는 한 `overview.md`에 합칠 수 있다. 요구사항이 있는 구현 단위의 명세는 별도 `requirements.md`에 두어 ID·인수 조건을 같은 형식으로 찾고, `overview.md`에는 진행 상태와 근거 링크만 둔다. 범위 확정과 인수 조건의 실제 충족은 구분한다.

## 6. 코드 컨벤션

### 지금 적용하는 공통 규칙

- 합의한 현재 단계만 구현한다. 추측으로 미래 기능·확장 구조·의존성을 추가하지 않는다.
- 모듈은 역할과 변경 이유를 기준으로 분리한다. 통신 처리와 저장소 내부 구현이 서로의 세부 구조에 의존하지 않게 한다. 구체적 분리 방식은 설계 때 선택한다.
- 인터페이스에는 입력·반환값·오류·상태 변경·호출 측의 기대를 명시한다. 시간·동시성이 영향을 준다면 그 계약도 드러낸다.
- 이름은 역할과 의도를 나타내는 영어를 사용한다. 임의 약어와 단위 없는 시간·크기 값은 피한다.
- 들여쓰기·대소문자·파일 확장자 등 언어별 표기법은 선택한 언어의 일관된 도구 설정을 따른다. 지금 특정 스타일을 강제하지 않는다.
- 주석은 코드의 직역보다 선택 이유·제약·불변 조건을 설명한다. 바뀐 코드와 어긋나는 주석은 함께 수정한다.
- 잘못된 입력과 예상 가능한 실패를 정상 결과와 구별한다. 오류를 조용히 무시하거나 임의의 성공 값으로 바꾸지 않는다. 구체적인 오류 표현은 설계에서 정한다.
- 한 변경에 기능·관련 테스트·필요한 문서 갱신을 묶는다. 무관한 리팩터링은 분리한다.
- 기존 변경을 덮어쓰지 않는다. 수정 전 변경 상태와 관련 코드를 확인한다.

### 테스트와 실행 증거

- 합의한 완료 조건과 테스트를 연결한다. 정상 흐름뿐 아니라 선택한 기능에 해당하는 경계·실패를 검증한다.
- 만료 테스트는 가능하면 제어 가능한 시간원을 사용한다. 실제 시간 대기에만 의존하지 않는다. 구체적 주입 방식은 설계에서 정한다.
- 동시성 테스트는 요청 횟수·동기화 조건·기대 상태를 기록한다. 단순히 여러 요청이 오류 없이 끝났다는 것으로 정합성을 입증하지 않는다.
- 과제의 단위·기능 테스트 및 성능 비교를 최종 확인에서 빠뜨리지 않는다. 과제에 없는 기능을 테스트 때문에 추가하지 않는다.
- 성능 비교는 같은 요청·데이터·환경에서 캐시 미사용, 미스, 히트 조건을 구분한다. 측정하지 않은 향상을 주장하지 않는다.
- 핵심 로직의 입력→처리→출력과 선택 이유를 설명할 수 있어야 한다. 설명문 작성만으로 이해를 검증했다고 기록하지 않는다.

### 기술 스택 선택 뒤 확정할 항목

Python·HTTP API는 결정되었다. 다음 세부 항목은 **미결정**이다. 기술 선택만으로 도구를 설치하거나 설정 파일을 만들지 않는다.

- Python 런타임 버전·패키지 관리 방식·HTTP 프레임워크.
- 소스·테스트 디렉터리 구조와 식별자 명명법.
- 포매터·린터·정적 검사·테스트 도구와 실행 명령.
- 의존성·잠금 파일 관리 및 자동 검증 여부.

선택한 도구의 실제 실행으로 확인한 명령만 `README.md`에 안내한다.

## 7. 에이전트 간 맥락 공유

- 새 세션은 `AGENTS.md` → 이 문서와 과제 원문 → `.agent/context.md` → 현재 단계 문서·관련 결정 → 실제 코드와 Git 변경 상태 순으로 확인한다.
- `.agent/context.md`에는 현재 목표·단계, 확인된 사실과 근거, 사용자 확정 사항, 미결정 사항, 다음 확인 지점을 짧게 유지한다.
- 인계가 필요할 때만 `.agent/handoffs/`에 작업 목적·범위, 관련 파일·요구사항, 완료한 일과 검증 증거, 가정·열린 질문, 기대 결과·완료 조건을 기록한다.
- 인계받은 에이전트는 실제 파일·코드·실행 결과를 재확인한다. 다른 에이전트의 보고를 검증된 사실로 자동 승격하지 않는다.
- 내부 추론·중복 대화 로그 전체를 공유 문서로 옮기지 않는다. 사람이 판단할 근거·변경 결과·미해결 문제만 `docs/`에 정리한다.
- `.agent/`에는 유일한 확정 결정이나 유일한 실행 방법을 두지 않는다. 확정된 프로젝트 정보는 사람이 읽는 문서에 먼저 반영하고, 에이전트 문서는 링크와 짧은 요약으로 연결한다.
- 다른 에이전트에게 실제 작업을 전달하거나 병렬 실행하는 것은 사용자 요청 또는 사전 허용 범위 안에서만 한다. 컨벤션 작성 자체가 위임 권한은 아니다.

## 8. 변경·보고 규칙

- 문서 정리 요청은 문서 범위에서 수행한다. 구현·의존성 변경·커밋·푸시·배포 권한으로 확대하지 않는다.
- 작업 후 실제 변경, 실제 검증 결과, 남은 일·결정이 필요한 항목을 구분해 보고한다.
- 컨벤션 초기안은 검토 후 확정한다. 이후 작은 표현 수정은 이 문서를 수정하고, 진행 방식에 영향을 주는 변경은 결정 기록을 남긴다.

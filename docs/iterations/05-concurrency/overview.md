# 5단계: 동시성 위험 점검과 필요한 방어

- 문서 상태: 요구사항 범위·인수 조건 확정 — 설계 초안 전체 검토 완료, 구현 전 TC 목록 작성
- 단계 상태: 완료 — 최초 결함 3건 해소, 계측 적용 동시성 25/25·수정 후 HTTP 회귀 47/47·보완 검증 10/10 통과; 이번 HTTP 동시성 범위 승인
- 근거: [과제 원문](../../assignment.md), [1단계 범위·공유 계약](../01-scope-and-contract/overview.md), [D-0005 기존 HTTP 계약](../../decisions/0005-http-api-boundary.md), [D-0007 단일 스레드 명령 실행](../../decisions/0007-single-thread-command-execution.md), [2단계 저장소](../02-hash-table/overview.md), [3단계 HTTP 연결](../03-http-api/overview.md), [4단계 만료·무효화](../04-expiration-invalidation/overview.md), [구현 단위 가이드](../implementation-units.md)

## 이 단계의 문서 길잡이

`overview.md`는 이 단계의 상태와 문서로 가는 입구다. **요구사항 → 설계 → 구현 전 테스트 계획 → 실제 구현 → 실행·검토 결과** 순서로 읽는다. 뒤 문서는 앞 문서의 기준을 따르며, 테스트 계획은 실행 결과가 아니다. 작성 전인 파일에 유효하지 않은 링크나 빈 양식을 만들지 않는다.

| 문서 | 역할·연결 관계 |
| --- | --- |
| [요구사항 명세 (`requirements.md`)](requirements.md) | HTTP 경로의 동시 사용 범위와 관찰 가능한 인수 조건. 명령·정리는 한 스레드에서 실행한다. |
| [설계 문서 (`design.md`)](design.md) — 초안 전체 검토 완료 | 병렬 HTTP 해석·단일 명령 실행, 공통 한도와 과부하·종료·정리 정책. 전체 설계 검토 결과는 아래 3절 참조; 구현·테스트 통과와 구분한다. |
| [테스트 케이스 (`test-cases.md`)](test-cases.md) — 구현 전 목록 | 요구사항 ID와 설계 경계를 연결한 통합·검토 계획. 동기화 조건과 기대 최종 상태를 명시한다. 실행 결과는 아니다. |
| [구현 기록 (`implementation.md`)](implementation.md) | HTTP 병렬 접수·단일 명령 실행과 자체 확인 범위. |
| [검증 기록 (`verification.md`)](verification.md) — 최종 범위 승인 | 구현 전 RED와 결함 수정·재검토 이력, 최종 TC/회귀/실패·부하 결과와 적용 한계. |

전체 단계의 현재 위치는 [진행 현황](../README.md), 단계별 파일 형식의 공통 기준은 [산출물 가이드](../iteration-deliverables.md)를 참고한다.

## 진행 체크리스트

[공통 진행 순서](../implementation-units.md#진행-체크리스트)에 맞춰 **요구사항 명세 → 설계 → 설계 검토 → 구현 전 TC → 구현 → 테스트·결과 확인** 순서로 관리한다. 아래 항목은 예정 작업이며, 실제 작성·검토·실행 후에만 체크한다.

- [x] 과제의 동시성 중점 항목과 2~4단계의 실행 구조·상태 변경 경로를 대조해 이번 범위와 관찰 가능한 완료 조건을 [요구사항 명세 (`requirements.md`)](requirements.md)에 확정한다. (실행 인수 확인은 별도)
- [x] HTTP 요청 처리와 단일 명령 실행의 경계·경쟁 가능성을 판단하고, 필요한 전달·방어 방식과 만료 정리의 실행 주체를 [설계 문서 (`design.md`)](design.md)에 정한다. 구조 변경이 필요하면 기존 계약에 미치는 영향도 확인한다. (설계 문서 작성·전체 검토 완료, 구현 검증은 별도)
- [x] 설계가 기존 저장소·HTTP·TTL 계약과 충돌하지 않는지 검토하고, 구현 착수를 막는 쟁점을 해결한다. (전체 설계 검토에서 차단 결함 발견 없음; 구현·테스트 승인 아님)
- [x] 구현 전에 동시 요청의 제어 조건·기대 최종 상태와 기존 연산·만료 경계의 회귀 사례를 요구사항 ID에 연결해 [테스트 케이스 (`test-cases.md`)](test-cases.md)에 기록한다. (TC 문서의 두 지적 보완 후 제한 재검토 승인; 코드·실행은 별도)
- [x] 필요한 방어를 구현하고 실제 변경을 [구현 기록 (`implementation.md`)](implementation.md)에 남긴다. (최초 검토 결함 3건 수정·제한 재검토 및 최종 범위 검증 완료)
- [x] 선택한 구조의 테스트와 기존 저장소·HTTP 연결부 회귀를 실행하고 명령·조건·결과를 [검증 기록 (`verification.md`)](verification.md)에 남긴다. (계측 적용 TC 25개, 수정 후 HTTP 회귀 47개, 보완 10개 통과; 순서·정확한 응답/값·자리·물리 수·종료를 대조)
- [x] 남은 위험과 6단계의 선행 조건을 확인해 [진행 현황](../README.md)을 갱신한다. (성능 비교·전체 시나리오는 후속 단계, 자동 착수하지 않음)

## 목표와 범위

목표는 여러 클라이언트의 HTTP 요청에서 접수·해석을 별도 스레드에서 병렬화할 수 있게 두면서, **모든 저장소 명령과 만료 정리를 한 실행 스레드에서 순서대로 수행**하는 것이다([D-0007](../../decisions/0007-single-thread-command-execution.md)). 이전 순차 서버를 병렬 접수·단일 실행 구조로 변경했고 이번 HTTP 동시성 범위의 실행·독립 검토를 완료했다.

저장·덮어쓰기·삭제, 조회 중 만료 제거, TTL 설정·제거, 주기 정리와 해시 테이블 확장의 상태 변경 경로를 확인하고 동시 HTTP 요청의 기대 최종 상태를 정의한다. 다른 스레드의 저장소 직접 호출은 보장하지 않는다. HTTP 접수·해석의 병렬화와 단일 명령 실행 방식은 [설계 초안](design.md)에 정했다. 수용 전 한도 초과·배출 중 접수 거부에는 기존 오류 분류보다 앞선 좁은 가용성 예외를 둔다. 6단계의 전체 종단 간·성능 비교와 Optional 영속성은 이번 단계에 포함하지 않는다.

## 1. 요구사항 명세 — 범위·인수 조건 확정

[요구사항 명세 (`requirements.md`)](requirements.md)의 `REQ-05-001`~`REQ-05-005`에 HTTP를 통한 사용 범위와 관찰 가능한 완료 조건을 정했다. 저장소 직접 병렬 호출은 비범위다. 요청 접수·해석의 병렬 처리는 허용하지만 명령과 만료 정리의 실행 스레드는 하나로 유지한다([D-0007](../../decisions/0007-single-thread-command-execution.md)). 범위 확정과 실제 검증 통과는 별개다. 단계별 명세의 입구는 [요구사항 색인](../README.md)이다.

## 2. 설계 — 초안 전체 검토 완료

[설계 문서 (`design.md`)](design.md)에 병렬 HTTP 해석·전담 명령 실행 스레드, 요청 전체 고정 한도 16과 가능한 `503 SERVER_BUSY`, 기존 수용 요청 배출 종료, 도래 시 명령 사이 정리를 제안·선택한 계약으로 기록했다. 저장소 직접 병렬 호출은 여전히 보장하지 않는다. 이는 설계 초안과 검토 기록이지 코드 적용이나 테스트 통과가 아니다.

## 3. 설계 검토 — 전체 검토 완료·차단 결함 발견 없음

독립 검토에서 발견한 과부하 시 `HEAD` 본문 금지 계약 문제와 네 비차단 의견을 [설계](design.md#6-미결-사항구현-위임검증-지점)에 반영하고 초점 재확인을 받았다. [요구사항](requirements.md#req-05-005--기존-계약-유지와-동시성-검증-증거) 및 D-0005·D-0007의 가용성 예외도 문서 간 초점 검토에서 정합한 것으로 확인했다.

이후 설계 검증 에이전트가 현재 설계 전체를 `REQ-05-001`~`005`, 관련 결정, 2~4단계 계약 및 실제 `mini_redis/http_api.py`·`mini_redis/store.py`와 종료 호출 경로에 대조했다. 책임 분리, 명령 순서·TTL 정합성, 공통 한도와 요청 수명, 제출·배출 종료, 정리 실패 격리, HTTP 계약·느린 연결 경계를 검토했으며, **구현 착수를 막는 차단 결함은 발견하지 못했다.** 구현 전 TC 작성 단계로 진행할 수 있다.

이는 당시 설계 적합성 판정이며 구현·테스트 승인과 구분한다. 이후 구현의 제출·종료 경합, 자리 반환, 전체 마감 및 정리 실패 후 진행은 아래 최종 검증에서 확인했다. 당시 설계 검토에서 테스트 실행과 Mermaid 실제 렌더링 확인은 하지 않았다.

## 4. 구현 — 결함 3건 해소·단계 범위 승인

[구현 전 TC 목록](test-cases.md)에 따라 병렬 HTTP 해석·단일 명령 실행 경계를 `mini_redis/http_api.py`에 적용했다. 실제 변경과 시간 경계는 [구현 기록 (`implementation.md`)](implementation.md)에 있다. 최초 검토의 완료 통지 실패·CLI 종료·제출 전 RST 관련 결함 3건을 수정하고 제한 재검토에서 해소했다. 같은 수정본의 나머지 TC·회귀·미확인 경계를 최종 검증했다.

## 5. 테스트·결과 확인 — 최종 고유 사례 82/82 통과

구현 전 계획과 실제 결과는 구분한다. 수정본에서 동시성 TC 25개를 **임시 계측을 연결한 복사본**으로 실행했고 HTTP·만료 HTTP 회귀 47개와 보완 검증 10개를 확인했다. 원본 테스트의 임시 접점을 저장소에 반영한 것은 아니므로 보정 없는 원본 runner 자체가 25개 Green이라는 뜻은 아니다. 계측 보정 전 실패와 재실행·최신 집계는 [검증 기록](verification.md#최종-검증--5단계-범위-승인)에 보존했다.

| 검증 대상 | 실제 확인 결과 |
| --- | --- |
| 접근 경로·순서 | 명령·정리가 한 전담 스레드에서 비중첩 실행. 제출 순서 및 실제 실행 순서와 각 응답·최종 값이 일치. |
| TTL·확장·정리 | 갱신 TTL의 옛/새 기한 경계, 확장 중 덮어쓰기·삭제·만료 조회와 물리 수 일치, 정리/진단 실패 후 진행 확인. |
| 수용량·단절·응답 | 끊긴 제출 요청과 응답 대기까지 16자리에 포함, 17번째 거부·HEAD 본문 부재·자리 회복 확인. |
| 마감·실패·종료 | 요청 trickle, 거부 입력/실제 TCP 송신 정체의 유한 마감, 결합 실패 격리, 배출 중 기존 해석 요청·정리·종료 순서 확인. |
| 기존 계약 회귀 | 수정 후 HTTP 32개·만료 HTTP 15개 통과. 변경 없는 저장소 24개·만료 저장소 15개의 이전 증거 재사용. |
| 제한된 반복 시험 | 8클라이언트·60.453초, HTTP 7,938건·정리 58회. 저장소 중첩 없음, 물리 수/자리 0과 정상 종료. 성능 비교는 아님. |

## 다음 확인 지점

5단계의 `REQ-05-001`~`005`는 이번 HTTP 범위에서 통과했다. 다음 확인 지점은 [6단계 전체 통합·성능 검증](../implementation-units.md#6-최종-사용성능-검증과-설명)의 요청·데이터·비교 조건을 정하는 것이다. 이번 결과는 운영 시간 전체의 안전성, 반환하지 않는 저장소 명령의 종료, 직접 병렬 저장소 호출·강제 종료 복구를 보장하지 않는다. 네트워크 단절과 제출이 겹치는 적용 불확실성도 유지한다. 계측의 저장소 반영과 성능 비교는 별도 작업이며, 이 문서 갱신으로 자동 착수하지 않는다.

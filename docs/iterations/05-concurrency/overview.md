## 이 단계의 문서 길잡이

`overview.md`는 이 단계의 상태와 문서로 가는 입구다. **요구사항 → 설계 → 구현 전 테스트 계획 → 실제 구현 → 실행·검토 결과** 순서로 읽는다. 뒤 문서는 앞 문서의 기준을 따르며, 테스트 계획은 실행 결과가 아니다. 작성 전인 파일에 유효하지 않은 링크나 빈 양식을 만들지 않는다.

| 문서 | 역할·연결 관계 |
| --- | --- |
| [요구사항 명세 (`requirements.md`)](requirements.md) | HTTP 경로의 동시 사용 범위와 관찰 가능한 인수 조건. 명령·정리는 한 스레드에서 실행한다. |
| 설계 문서 (`design.md`) — 작성 전 | 실행 구조·상태 변경 경로의 분석과 필요할 때의 방어 방식·선택 근거. 설계 검토 내용도 여기에 둔다. |
| 테스트 케이스 (`test-cases.md`) — 작성 전 | 요구사항 ID와 설계 경계를 연결한 구현 전 단위·통합 검증 계획. 동기화 조건과 기대 최종 상태를 명시한다. |
| 구현 기록 (`implementation.md`) — 변경 발생 시 | 실제 코드 변경과 설계 대비 구현 선택. 변경이 불필요하다고 판단되면 그 근거와 구분한다. |
| 검증 기록 (`verification.md`) — 실행·검토 시 | 실제 명령·조건·결과 및 코드 검토 판정과 남은 위험. 계획만으로 통과를 표시하지 않는다. |

전체 단계의 현재 위치는 [진행 현황](../../plans/progress.md), 단계별 파일 형식의 공통 기준은 [산출물 가이드](../../plans/iteration-deliverables.md)를 참고한다.

## 진행 체크리스트

[공통 진행 순서](../../plans/implementation-units.md#진행-체크리스트)에 맞춰 **요구사항 명세 → 설계 → 설계 검토 → 구현 전 TC → 구현 → 테스트·결과 확인** 순서로 관리한다. 아래 항목은 예정 작업이며, 실제 작성·검토·실행 후에만 체크한다.

- [x] 과제의 동시성 중점 항목과 2~4단계의 실행 구조·상태 변경 경로를 대조해 이번 범위와 관찰 가능한 완료 조건을 [요구사항 명세 (`requirements.md`)](requirements.md)에 확정한다. (실행 인수 확인은 별도)
- [ ] HTTP 요청 처리와 단일 명령 실행의 경계·경쟁 가능성을 판단하고, 필요한 전달·방어 방식과 만료 정리의 실행 주체를 설계 문서 (`design.md`)에 정한다. 구조 변경이 필요하면 기존 계약에 미치는 영향도 확인한다.
- [ ] 설계가 기존 저장소·HTTP·TTL 계약과 충돌하지 않는지 검토하고, 구현 착수를 막는 쟁점을 해결한다. (설계 검토는 구현 검증과 별개)
- [ ] 구현 전에 동시 요청의 제어 조건·기대 최종 상태와 기존 연산·만료 경계의 회귀 사례를 요구사항 ID에 연결해 테스트 케이스 (`test-cases.md`)에 기록한다.
- [ ] 필요한 방어를 구현하고 실제 변경을 구현 기록 (`implementation.md`)에 남긴다. 변경이 필요 없는 범위라면 판단 근거와 적용 한계를 명시한다.
- [ ] 선택한 구조의 테스트와 기존 저장소·HTTP 연결부 회귀를 실행하고 명령·조건·결과를 검증 기록 (`verification.md`)에 남긴다. 오류가 없었다는 사실만으로 정합성을 주장하지 않는다.
- [ ] 남은 위험과 6단계의 선행 조건을 확인해 [진행 현황](../../plans/progress.md)을 갱신한다.

## 목표와 범위

목표는 여러 클라이언트의 HTTP 요청에서 접수·해석을 별도 스레드에서 병렬화할 수 있게 두면서, **모든 저장소 명령과 만료 정리를 한 실행 스레드에서 순서대로 수행**하는 것이다([D-0007](../../decisions/0007-single-thread-command-execution.md)). 현재 HTTP 서버는 한 프로세스의 순차 `HTTPServer`이고 만료 정리도 같은 서버 스레드에서 요청 사이에 수행한다. 이는 현재 구현 현황이지 새로운 실행 구조가 이미 적용됐다는 뜻은 아니다.

저장·덮어쓰기·삭제, 조회 중 만료 제거, TTL 설정·제거, 주기 정리와 해시 테이블 확장의 상태 변경 경로를 확인하고 동시 HTTP 요청의 기대 최종 상태를 정의한다. 다른 스레드의 저장소 직접 호출은 보장하지 않는다. HTTP 접수·해석의 실제 병렬화 여부와 명령 전달·대기 방식은 설계에서 정한다. 6단계의 전체 종단 간·성능 비교와 Optional 영속성은 이번 단계에 포함하지 않는다.

## 1. 요구사항 명세 — 범위·인수 조건 확정

[요구사항 명세 (`requirements.md`)](requirements.md)의 `REQ-05-001`~`REQ-05-005`에 HTTP를 통한 사용 범위와 관찰 가능한 완료 조건을 정했다. 저장소 직접 병렬 호출은 비범위다. 요청 접수·해석의 병렬 처리는 허용하지만 명령과 만료 정리의 실행 스레드는 하나로 유지한다([D-0007](../../decisions/0007-single-thread-command-execution.md)). 범위 확정과 실제 검증 통과는 별개다. 단계별 명세의 입구는 [요구사항 색인](../README.md)이다.

## 2. 설계 — 작성 전

설계 문서 (`design.md`)에서 현재 요청 처리·정리·저장소 접근 경로를 조사하고, 요청 해석을 병렬화할지, 명령을 한 스레드로 전달·실행할 방법과 정리 시점·실패 처리를 선택한다. 현재 구조를 유지할 수도 있으나 기존 HTTP·TTL 계약의 회귀와 단일 스레드 보장을 입증해야 한다. 구체적 구현 방식은 아직 채택하지 않았다.

## 3. 설계 검토 — 대기

요구사항 범위, 기대 최종 상태, 저장소의 값·기한·항목 수 보존, HTTP 응답 계약과의 연결을 독립적으로 대조한다. 발견한 문제와 반영 여부는 설계 문서 (`design.md`)에 남기며, 문서 검토를 테스트 통과로 표현하지 않는다.

## 4. 구현 — 착수 전

설계에서 정한 실행 경계를 코드에 적용할 필요가 있는 경우 변경하고 구현 기록 (`implementation.md`)에 실제 경로·선택을 적는다. 현재 구조를 유지한다면 그 근거와 적용 한계를 기록한다. 아직 구현을 착수하지 않았다.

## 5. 테스트·결과 확인 — 미실행

구현 전 계획은 테스트 케이스 (`test-cases.md`)에, 실제 실행과 판정은 검증 기록 (`verification.md`)에 분리한다.

| 검증 대상 | 실행 시 확인할 관찰 결과 |
| --- | --- |
| 접근 경로·실행 구조 | 대상 경로가 직렬인지 겹칠 수 있는지 재현·코드 경로로 확인하고, 판단의 적용 범위를 명시한다. |
| 같은 키의 변경 | 선택한 동기화 조건에서 순서별 기대 최종 값·기한이 관찰 결과와 일치한다. |
| 만료·정리와 상태 변경 | 만료 제거·TTL 갱신·삭제·주기 정리가 겹치는 대상 범위에서 오래된 값의 재등장이나 항목 수 불일치가 없는지 확인한다. |
| 기존 계약 회귀 | 저장소와 HTTP의 기존 연산·만료 응답이 유지되는지 실행 결과로 확인한다. |

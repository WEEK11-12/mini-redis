# 5단계 구현 기록 — HTTP 접수와 단일 명령 실행

- 상태: 최초 독립 검토 결함 3건 해소 및 이번 HTTP 동시성 범위 승인 — 최종 실행 결과·계측 한계는 [검증 기록](verification.md) 참조
- 근거: [요구사항](requirements.md), [설계](design.md), [구현 전 TC](test-cases.md)

`mini_redis/http_api.py`에서 HTTP 접수는 `ThreadingMixIn`의 요청 스레드로, 저장소 공개 연산과 정기 만료 정리는 전담 명령 실행 스레드 하나로 분리했다. 유효한 요청은 연산·검증된 인자를 FIFO 큐에 넣고 요청별 완료 이벤트의 결과/예외를 기다린다. 정리 목표가 도래하면 다음 대기 명령보다 먼저 시도하고, 시도 종료부터 다음 1초를 계산한다. 실패한 정리의 진단 오류도 명령 처리를 막지 않는다.

접수 전 원자적 공통 한도 16을 두며, 초과/배출 중 연결은 제한 시간 안에 요청 행과 헤더 일부만 읽어 메서드를 확인하고 가능한 경우 `503 SERVER_BUSY`를 보낸다. `HEAD` 응답에는 본문을 쓰지 않는다. 수용 요청은 응답/연결 처리와 명령 완료까지 자리를 점유한다. 종료는 새 접수를 막고 수용 요청을 배출한 뒤 전담 스레드를 합류한다. 요청 연결에는 2초 소켓 읽기 제한과 6초 전체 처리 마감, 거부 경계에는 0.5초 마감을 적용했다. 정상 종료는 반환하지 않는 저장소 호출을 강제로 중단하지 못한다. 서버를 생성만 하고 실행하지 않은 경우 `server_close()`로 전담 스레드를 회수한다.

HTTP 경로와 응답 형식은 유지했다. 저장소 직접 병렬 호출의 안전성은 보장하지 않는다. 구현 전 TC의 `_test_*` 이름은 임시 시험 접점이므로 제품 API로 추가하지 않았다. 최종 검증에서는 원본 테스트의 scratch 복사본에 실제 큐·접수·응답 경계를 연결했다. 계측은 로컬 산출물에 보존했으며 원본 테스트의 저장소 반영과는 구분한다. 제출 직전의 연결 단절 관찰은 원자적이지 않으며, 단절과 제출이 겹치면 클라이언트가 적용 여부를 확정할 수 없다.

최초 독립 검토에서 세 결함을 재현했다: 완료 통지 실패로 현재 요청이 영구 대기, CLI Ctrl-C 후 전담 스레드 잔존, 제출 전 관찰 가능한 TCP 리셋 후에도 PUT 적용. 수정은 완료 이벤트 실패의 요청별 오류 격리 및 실행 주체 사망 시 대기 해제, CLI 정상 종료에서 `shutdown()` 호출, 큐 제출 직전 요청 마감·확인 가능한 리셋 관찰에 한정했다. TCP의 단순 FIN은 읽기 반닫힘일 수 있으므로 리셋으로 추정하지 않는다. 수정본의 세 결함은 독립 제한 재검토에서 해소 판정을 받았다. 이후 같은 제품 해시에서 동시성 TC·HTTP 회귀·보완 검증을 완료해 이번 단계의 HTTP 범위를 승인했다. 이 상태 문장은 제품 소스 변경 없이 최종 검증 결과를 반영한 문서다.

자체 점검: `test_http_api.py` 32개, `test_expiration_http.py` 15개, `test_expiration_store.py` 15개, `test_store.py` 24개 통과. 5단계 초점 I-001·002 및 I-003·005·007·012·017·022 통과(일부는 최종 편집 전). 한도 16과 과부하 GET/HEAD는 별도 소켓 실행에서 확인했다. 최초 전체 5단계 실행의 접점 부재·I-016 계측 실패는 이력으로 보존한다. 최종 검증은 계측 적용 TC 25/25·HTTP 회귀 47/47·보완 10/10 통과이며 자세한 실행·재실행 증거는 [검증 기록](verification.md)에 별도로 남긴다.

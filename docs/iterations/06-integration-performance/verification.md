## 1. 기존 기능 재확인

### 1.1. 기존 검증 증거 재사용

전체 테스트를 일괄 재실행하지 않고, 기존 증거가 현재 소스에 적용되는지 먼저 확인했다. 5단계 최종 검증의 실행 전후 manifest와 현재 제품·테스트 7개의 SHA-256이 모두 일치했다. 예제 클라이언트·원본 API도 최종 제품 커밋 이후 변경이 없고, 저장소·저장소 단위 테스트는 4단계 완료 커밋 이후 변경이 없다.

| 재사용한 범위 | 기존 결과 | 근거와 적용 한계 |
| --- | --- | --- |
| 기본 저장소·만료 저장소 | 24/24·15/15 통과 | [2단계 검증](../02-hash-table/verification.md), [4단계 제한 재검토](../04-expiration-invalidation/verification.md#제한-재검토-판정과-범위) 및 [5단계 최종 검증](../05-concurrency/verification.md#최종-검증--5단계-범위-승인). 이번 신규 실행 수가 아니다. |
| HTTP·만료 HTTP | 32/32·15/15 통과 | 5단계 최종 `regression-results.json`의 고유 ID 47개와 모두 pass임을 코드로 확인했다. |
| 동시성 I-001~025 | 계측 적용본 25/25 통과 | 5단계의 임시 시험 접점을 연결한 scratch 결과다. 원본 무보정 runner의 Green을 뜻하지 않는다. |
| 5단계 보완 경계·배출·반복 | 7/7·2/2·1/1 통과 | 5단계 최종 판정과 기록을 재사용했다. 제한된 반복 시험을 이번 성능 비교나 운영 시간 전체의 보증으로 사용하지 않는다. |

5단계 최종 고유 82개와 저장소 재사용 39개를 이번 신규 실행 수에 더하지 않았다. 기존 계측 실패·재실행 이력과 승인 한계도 유지한다. 기존 테스트·문법 검사는 동일 소스의 통과 증거가 있어 반복 실행하지 않았다. 정적 타입 검사 도구·린터 미설정이라는 기존 한계는 남는다.

새 연결 흐름과 관련된 예제 실패 경로는 이전 HTTP 회귀의 다음 5개 통과 ID를 선별해 재사용했다. 이번 재실행 결과가 아니다.

- `test_e_003_cache_failure_does_not_fallback`: 캐시 실패 시 원본으로 우회하지 않음.
- `test_e_003_cache_redirect_does_not_call_origin`: 캐시 리다이렉트를 따라 원본을 호출하지 않음.
- `test_e_004_origin_failure_does_not_write`: 원본 실패 시 캐시 쓰기 없음.
- `test_e_005_numeric_stored_is_not_true`: 숫자 `1`을 저장 성공 불리언으로 인정하지 않음.
- `test_e_005_put_failure_is_not_success`: 저장 실패를 값 획득 성공으로 반환하지 않음.

위 ID는 모두 `tests/test_http_api.py`의 `ExampleContractTests`에 속한다. 6단계 E ID와 혼동하지 않는다.

### 1.2. 이번 신규 실행 — 지속 클라이언트 연결 확인

#### 선정 근거와 조건

성능 비교 계획은 one-shot 프로세스 기동 시간을 제외하고 **실행 중인 클라이언트가 `reuse(cache_url, origin_url)`를 호출**한다. 기존 예제 테스트는 one-shot CLI를 사용하므로, 이 연결 방식의 공백만 실제 HTTP probe로 보완했다. 제품 변경이 없고 기존 해시가 동일하므로 해시 충돌·확장·정밀 TTL·프레이밍·과부하·종료 경계를 전수 재검토하지 않았다.

- 환경: Python 3.14.5, macOS 26.6.2 arm64, 저장소 루트에서 실행.
- Mini Redis와 원본 API는 각각 실제 서버 factory를 호출한 별도 장기 실행 자식 프로세스다. 가짜 제품 서버·제품 patch·제품용 시험 API를 추가하지 않았다.
- 주소: Mini Redis `http://127.0.0.1:63910`, 원본 `http://127.0.0.1:63911`. OS가 할당한 임시 포트이며 고정 포트 수동 시연이 아니다.
- 클라이언트는 하나의 계속 실행 중인 Python 프로세스에서 실제 `examples.client.fetch()`·`reuse()`를 사용했다.
- 준비·관찰 요청을 값 획득 요청과 구분했다. 캐시 응답의 상태·JSON·불리언 타입·`Cache-Control: no-store`도 확인했다. 시간 측정은 하지 않았다.

#### 실제 명령과 증거

실제 실행은 검토 프로필 scratch의 `probe.py`를 아래 형태로 호출했다. 부모 subprocess의 45초 제한 아래 stdout/stderr와 종료 코드를 보존했다. 아래 `REVIEW_ARTIFACTS`는 당시 원본 산출물 디렉터리이며, 실행 후 동일 파일을 로컬 보존본 `.agent/verification/mini-redis-i06-existing-recheck`에 복사하고 파일별 해시 일치를 확인했다. 보존본 복사는 추가 테스트 실행이 아니다.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -B "$REVIEW_ARTIFACTS/probe.py"
```

로컬 보존본은 저장소 루트 기준으로 다음 명령으로 참조·재실행할 수 있다. `probe.py`는 당시 로컬 저장소 위치를 고정하므로 다른 위치의 checkout에서는 경로 조정이 필요하다. Git 제외 로컬 산출물은 다른 clone에 자동 전달되지 않는다.

```sh
REVIEW_ARTIFACTS=.agent/verification/mini-redis-i06-existing-recheck
PYTHONDONTWRITEBYTECODE=1 python3 -B "$REVIEW_ARTIFACTS/probe.py"
```

원자료는 로컬 [results.json](../../../.agent/verification/mini-redis-i06-existing-recheck/results.json), [실행 로그](../../../.agent/verification/mini-redis-i06-existing-recheck/probe.log), [재현 스크립트](../../../.agent/verification/mini-redis-i06-existing-recheck/probe.py)에 보존했다. 같은 디렉터리에 실행 전후 manifest·서버 로그·상세 검토 보고서도 있다. 이 문서의 결과 표와 판정은 로컬 산출물 없이도 읽을 수 있도록 요약했다.

#### 실제 결과

신규 probe `persistent_client_prerequisite_smoke`는 **1/1 통과, exit 0**이다. 최초 한 차례 실행이며 실패·기대값 완화·재실행은 없었다. 아래 6개 위상은 하나의 연속 probe의 관찰점이며 별도 공식 TC로 집계하지 않는다.

| 관찰 위상 | 반환값 | 원본 호출 횟수 | 추가 확인 |
| --- | --- | --- | --- |
| 캐시 미사용 직접 조회 | `sample-response` | 0→1 | 캐시 키 404·exists false 유지 |
| 미스 1 | `sample-response` | 1→2 | 삭제·부재 확인 후 문자열 저장·exists true |
| 히트 1 | `sample-response` | 2→2 | PUT 준비 뒤 캐시 재사용 |
| 삭제 후 미스 2 | `sample-response` | 2→3 | 같은 서버·클라이언트 수명에서 상태 재준비 |
| 다시 준비한 히트 2 | `sample-response` | 3→3 | 같은 주소·같은 `reuse()` 경로 |
| 빈 문자열 히트 | 빈 문자열 | 3→3 | GET 200·exists true, 보조 키 `control-key`의 `control-value` 보존 |

원본·캐시 서버 모두 SIGINT 후 exit 0으로 종료하고 자식을 회수했다. 강제 kill은 없었다. 실행 전후 저장소 파일 63개의 해시가 동일했다(`.git`·`.agent`·`__pycache__` 제외). 제품·테스트·문서에 대한 당시 읽기 전용 경계를 확인한 결과이며, 이 검증 기록과 개요의 후속 문서 갱신까지 파일이 불변이라는 뜻은 아니다.

### 1.3. 범위 판정

**기존 기능 재확인 범위는 통과**다. 기존 증거의 적용 가능성과 새 지속 클라이언트 호출 경로를 확인했고, 이 범위에서 필수 수정 사항을 발견하지 못했다. 제품 안전성 전체를 보증하거나 6단계 완료로 판정하지 않는다.

## 2. 전체 사용 흐름 검증

- 상태: **통과** — [E-001~007의 전체 인수 절차](test-cases.md#종단-간-사용-흐름--사례-정의)를 실제 별도 서버·외부 요청으로 실행했다. 고유 7/7 통과, 실패·오류·skip 0, 각 worker exit 0이다.
- 실행일·환경: 2026-11-18 KST, Python 3.14.5, macOS 26.6.2 arm64. 저장소 루트에서 실행했다.
- 범위: 최초 조회·캐시 재사용, 삭제·만료 뒤 재조회, 빈 값·덮어쓰기, 거부 후 상태 보존, 실패 처리, 복수 클라이언트·삭제 경합. 1절의 연결 probe와 별도의 신규 실행이다.

### 2.1. 실행 조건과 계측 경계

각 E 사례는 캐시·원본 서버 두 프로세스를 새로 시작하고 원본 횟수 0·캐시 GET 404·exists false를 확인했다. E-006의 원본 실패·캐시 실패 두 위상도 각각 새 서버 쌍으로 분리했다. 실제 서버 factory·실제 HTTP 해석/명령 실행/응답 코드를 사용했으며, 예제 호출은 매번 별도 `python3 -B -m examples.client --cache-url … --origin-url …` 프로세스로 실행했다. 주소·PID·실제 argv·응답·stdout/stderr는 사례별 원자료에 보존했다.

- **제어 시간:** 실제 `HashTableStore(clock=…)`에 주입한 단조 나노초 시간원을 서버 자식의 시험용 stdin/stdout 채널로 전진시켰다. 공개 HTTP 시간 API나 제품 변경은 없다. 초기 `t0=100초`; E-003은 TTL 1초, 유효 중 `t0+0.5초`와 기한 뒤 `t0+1.1초`를 확인했다. E-004/005는 TTL 10초와 `t0+1초`의 변경/거부, `t0+9초`·`t0+10초`의 GET/exists를 확인했다. E-004는 `t0+11초`도 추가 확인했다. 시간 전진 완료 응답 뒤 HTTP 관찰을 수행해 시각 변경과 요청을 동기화했다.
- **명령 관찰:** 실제 저장소 메서드를 호출하는 얇은 wrapper로 연산·인자·반환값·실행 순번·시각·스레드를 기록했다. 캐시 응답 계측도 원본 핸들러의 송신 함수를 그대로 호출한 뒤 상태·헤더·payload를 기록했다. 값을 대신 계산하거나 기대 결과를 반환하는 가짜 제품 구현은 없다.
- **경합 제어:** E-007의 두 클라이언트가 준비 배리어에 도달한 뒤 실제 CLI를 실행했다. 삭제 경합은 첫 저장소 명령을 시험 gate에 잡고, 다른 명령이 실제 큐에 들어왔음과 수용 요청 2개를 확인한 뒤 해제했다. 큐·수용량은 실제 내부 잠금 아래 읽었다. 시작 시각만으로 실행 순서를 추정하지 않았다.
- **수명 제한:** 사례 전체를 각각 별도 worker에서 실행하고 부모가 45초 제한을 적용했다. 서버 정리·클라이언트 대기도 유한 시간으로 제한했다. 실제 실행에서 watchdog 만료나 강제 kill은 없었다.

### 2.2. 명령과 증거

실제 검토 scratch에서 아래 형태로 각 사례를 한 번씩 실행하고 `case-001.log`~`case-007.log`에 worker 결과를 보존했다. 아래 명령은 그 실행 절차를 나타내며, 보존본 복사는 재실행이 아니다.

```sh
for case in 1 2 3 4 5 6 7; do
  python3 -B "$REVIEW_ARTIFACTS/run.py" --case "$case"
done
python3 -B "$REVIEW_ARTIFACTS/aggregate.py"
```

로컬 보존본은 `.agent/verification/mini-redis-i06-e2e/`다. [집계 (`summary.json`)](../../../.agent/verification/mini-redis-i06-e2e/summary.json), [실행기 (`run.py`)](../../../.agent/verification/mini-redis-i06-e2e/run.py), [서버 계측 (`server.py`)](../../../.agent/verification/mini-redis-i06-e2e/server.py), [집계 코드 (`aggregate.py`)](../../../.agent/verification/mini-redis-i06-e2e/aggregate.py)를 보존했다. `e001`~`e007`에는 `result.json`, 서버 로그/명령 기록, 실행 전후 소스 manifest가 있다. 원본과 복사본의 72개 파일 해시가 모두 일치했다. Git 제외 로컬 증거는 다른 clone에 자동 전달되지 않는다.

`run.py`는 저장소 루트를 현재 작업 디렉터리로 사용하며 같은 산출물 디렉터리를 덮어쓰지 않는다. 재현할 때는 세 스크립트를 비어 있는 별도 디렉터리에 복사하고 그 디렉터리를 `REVIEW_ARTIFACTS`로 지정해야 한다. 이전 검증의 로컬 manifest·회귀 기록도 참조하므로 해당 증거가 없는 환경에서는 전제 자료를 준비해야 하며 결과를 임의 통과 처리하지 않는다.

### 2.4. 판정과 한계

**전체 사용 흐름 E-001~007은 이번 범위에서 통과**다. 원본 무보정 `unittest discover` 전체의 Green이나 성능 비교 완료를 뜻하지 않는다. TTL은 제어 시간을 사용한 실제 HTTP 동작이며 실시간 스케줄링·주기 정리의 정확한 시각을 입증하지 않는다. E-007은 제어한 명령 순서와 이번 외부 사용 경합의 증거이고 모든 가능한 스케줄의 전수 검증이 아니다. 기존 단계의 세부 경계 증거는 재사용하고 이번 E 결과와 합산하지 않았다.

### 3.1. 측정 방법

[확정된 성능 비교 조건](overview.md#확정된-성능-비교-조건)을 [`examples/benchmark.py`](../../../examples/benchmark.py)로 구현했다.

- 원본 API(`python3 -B -m examples.origin_api`)와 Mini Redis(`python3 -B -m mini_redis.http_api`)를 OS가 고른 빈 로컬 포트의 별도 장기 실행 프로세스로 띄운다. 측정은 하나의 실행 중인 클라이언트 프로세스에서 순차로 한다.
- 타이머는 `time.perf_counter_ns()`로 **값 획득만** 감싼다. 미사용은 `fetch(GET /items/demo)` 뒤 JSON 문자열 추출, 미스·히트는 예제의 실제 `reuse(cache_url, origin_url)`다. 요청마다 새 HTTP 연결(예제 클라이언트의 기존 방식)이다.
- 타이머 밖: 미스 준비 `DELETE /keys/example-demo`, 히트 준비 `PUT {"value":"sample-response"}`(`{"stored":true}` 확인), 전후 `GET /origin-calls`. 값이 `sample-response`가 아니거나 원본 증가분이 미사용·미스 1, 히트 0이 아니면 그 회차를 실패로 기록한다. 회차마다 마지막 단계(`stage`: prepare/origin_before/acquire/origin_after/verify/done)를 남긴다. 값 획득 중 오류(HTTP 프로토콜 오류 포함)도 실패 회차로 남기고, 타이머가 시작됐으면 오류 확정까지의 `elapsed_ns`를 기록한다. 타이머 전 실패는 `elapsed_ns=null`이다. 예상 밖 예외·중단이 나도 그때까지의 예열·측정 회차와 `aborted` 원인, `complete=false`를 결과 파일에 쓴다.
- 조건마다 준비를 포함해 5회 예열한 뒤(집계 제외) 100라운드를 측정했다. 라운드 순서는 `미사용→미스→히트`를 라운드마다 한 칸씩 순환해 각 조건이 33~34회 먼저 실행됐다.
- 집계: 성공 회차의 중앙값(`statistics.median`)을 주 비교값, nearest-rank 90백분위값을 보조값으로 한다. 실패는 제거·대체하지 않으며, 조건별 성공 100·실패 0일 때만 `complete=true`, exit 0이다.

### 3.4. 해석과 한계

- **이 환경에서는 캐시 히트가 미사용보다 느렸다**(중앙값 약 1.7배, 직전 실행 1.6배). 원본이 같은 호스트에서 고정 응답을 즉시 돌려주므로 원본 작업 비용이 거의 없고, 히트도 같은 HTTP 왕복 한 번에 Mini Redis의 요청 해석·단일 명령 스레드 경유가 더해지는 구조이기 때문으로 **추정**한다. 구간별 내부 시간은 측정하지 않았다.
- 미스는 캐시 조회·원본 조회·캐시 저장의 HTTP 3회라 가장 느렸다(미사용 대비 약 4.9배, 직전 실행 4.4배).
- 따라서 이 결과는 "원본 비용이 매우 작을 때 로컬 HTTP 캐시는 지연을 줄이지 못한다"는 관찰이다. 원본에 실제 계산·I/O 지연이 있으면 결과가 달라질 수 있지만 그런 조건은 측정하지 않았다. 확정 조건대로 인위적 지연을 넣지 않았다.
- 순차 단일 클라이언트의 지연 비교이며 동시 처리량, 다른 원본 작업, 원격 네트워크로 일반화하지 않는다. 한 호스트의 결과이며 실행 간 편차는 위 두 번의 실행 외에 체계적으로 측정하지 않았다.
- 클라이언트 수명 내 원본 횟수·값 검증은 하지만 스크립트 자체에 대한 별도 단위 테스트는 없다. 실패 기록 경로는 위 `f1-probe`, P90 계산은 nearest-rank(1~100 → 90) 단발 확인으로 점검했다.

- 설명 판정 근거: 4.1절에서 직접 확인한 답변과 4.2절의 코드·문서 대조 자료를 구별한다. 이후 설명 가능하다는 본인 확인을 받아 이번 단계의 설명 항목을 닫는다. 직접 답변하지 않은 내용을 구술 검증 통과로 표시하지 않는다.

### 4.1. 대화 기반 설명 확인 — 일부 진행

- 해시값을 버킷 수로 나눈 나머지로 위치를 정하고, 같은 버킷에서는 전체 키를 비교해 충돌을 구분한다는 설명을 확인했다. 실제 구현은 연결 리스트가 아니라 버킷별 Python 리스트에 항목을 두는 체이닝이다(`store.py`의 `_hash`, `_locate`, `_insert`).
- 기존 키 `set`은 값을 교체하고 TTL을 해제한다는 설명을 확인했다. 항목 수가 늘지 않는 점과 만료 기한을 `None`으로 바꾸는 코드를 대조했다. 만료된 키의 GET은 옛 값을 반환하지 않고 미존재로 처리한다는 설명을 확인했으며, 조회 경로가 물리적 제거와 항목 수 감소도 수행한다는 세부 사항은 코드와 함께 보완했다.
- 명령 실행 스레드를 하나로 유지해 경쟁 조건을 다루며, GET도 만료 시 저장 상태를 바꾸므로 분리된 조회 스레드에서 실행하면 경합할 수 있다는 설명을 확인했다. 실제 HTTP 요청 해석은 병렬이어도 저장소 명령과 만료 정리는 한 전담 스레드에서 순차 실행한다(`http_api.py`의 `execute`, `_run_commands`).
- 새 키를 넣은 뒤 적재율이 1을 넘을 때 버킷을 늘리고 기존 키를 재해싱해 새 버킷에 옮긴다는 설명을 확인했다. 실제 `set`은 새 키의 예상 항목 수가 현재 버킷 수를 초과하면 `_rehash()`로 버킷 수를 두 배로 만들고, 기존 키·값·TTL 기한을 함께 재배치한 뒤 새 항목을 반영한다. 기존 키 덮어쓰기는 확장을 유발하지 않는다.
- 이는 대화에서 직접 확인한 설명의 부분 기록이다. 주요 함수 전체 흐름, 만료 시간원·무효화 선택 및 재현 방법은 코드·문서 근거를 아래 4.2절에 따로 정리하며, 직접 설명을 확인한 것으로 바꾸지 않는다.

### 4.2. R-001/002 근거 대조 — 문서·코드 점검

**R-001 (설명 자료, 실행 TC 아님):** [저장소 코드](../../../mini_redis/store.py)는 문자열 키·값을 검증하고, 키의 해시값을 버킷 수로 나눈 위치에서 전체 키를 비교한다. `set`은 새 키를 추가하거나 기존 값과 TTL을 교체하며, 새 키 추가 후 적재율이 1을 넘을 때 버킷을 두 배로 재배치한다. `get`은 `(존재 여부, 값)`, `exists`와 `delete`는 불리언을 반환한다. 빈 문자열은 존재하는 값이다. 만료 기한 이상이면 접근 시 항목을 제거하고, `sweep_expired`는 접근하지 않은 만료 항목도 정리한다. 단조 시간원은 시스템 날짜 조정에 TTL이 흔들리지 않게 하며, `DELETE /keys/{key}`는 키 전체 무효화이고 `DELETE /keys/{key}/ttl`은 값은 남긴 채 기한만 해제한다([4단계 설계](../04-expiration-invalidation/design.md#2-외부-인터페이스와-확정된-계약)). [HTTP 처리 코드](../../../mini_redis/http_api.py)는 요청을 병렬 해석해 저장소 공개 연산을 큐에 넣고, 한 전담 스레드가 연산과 주기 정리를 순차 실행한다. [예제 클라이언트](../../../examples/client.py)는 `404 KEY_NOT_FOUND`일 때만 원본을 호출하고 저장 성공을 확인한 뒤 값을 반환한다. 이는 코드·설계 대조 결과이지 모든 항목을 대화에서 직접 설명해 확인한 결과가 아니다. 기존 단위별 실행 증거의 적용 범위와 5단계 임시 계측 한계는 1절에 분리했다.

**R-002 (기록 완결성 점검, 실행 TC 아님):** 2절의 E-001~007은 사례별 원자료·실행 명령·초기화·제어 시간/명령 순서·실패/한계를 연결한다. 로컬 `summary.json`에서 고유 7건 중 7건 통과, 실패·skip 0, 서버 16개 회수·강제 종료 0을 확인했다. 3절의 P-001/002는 측정 명령·환경·원자료와 조건별 결과·실패 경계를 연결한다. 로컬 `results.json`에서 예열 15건과 측정 300건, 각 조건 100건 성공·실패 0, 중앙값과 nearest-rank P90의 재계산 일치, 서버 2개 exit 0을 확인했다. 이 문서의 상대 링크와 참조한 로컬 산출물 경로도 존재한다. Git 제외 산출물은 다른 checkout에서 자동 재현되지 않으며, 이 점검은 E/P 재실행이나 별도 독립 판정이 아니다. 기존 동시성 원본 runner의 무보정 Green으로 확대하지 않는다.

설명 자료와 기록 대조를 마쳤고, 이후 핵심 로직·선택 이유를 **설명할 수 있다는 본인 확인**을 받았다. 대화에서 실제로 확인한 답변은 4.1절에 한정하며, 남은 선택 이유를 하나씩 구술 검증하거나 사용자가 별도 수동 재현을 완료했다고 주장하지 않는다. 본인 확인과 독립 검증의 차이를 유지한 채 6단계의 결과 정리·설명 항목을 완료로 판정한다.

## 5. 종합 판정과 남은 확인

기존 기능 재확인·전체 사용 흐름·성능 비교의 실행 검증과 R-001/002 기록 대조를 마쳤다. 설명 가능하다는 본인 확인을 받아 **6단계 범위를 완료**로 판정한다. 이는 모든 설명 항목의 독립 구술 검증이나 다른 환경·원본 작업의 성능 보증이 아니다.

| 후속 범위 | 현재 상태 |
| --- | --- |
| E-001~007 전체 사용 흐름 | 이번 신규 실행 7/7 통과. 2절에 실제 결과와 계측 한계 기록. |
| P-001/002 성능 비교 | 측정·집계 완료(3절). 히트 0.381ms가 미사용 0.228ms보다 느림. 수정 요청 반영 후 제한 재검토 승인. |
| 측정 스크립트 검증 | `examples/benchmark.py` 작성. 첫 검토에서 정상 경로·집계 불일치 없음, 실패 보존(F1) 수정 후 제한 재검토 승인. |
| 결과 설명·이해 확인 | 코드·증거 자료 정리 및 설명 가능하다는 본인 확인 완료. 직접 대화로 확인한 범위는 4.1절에 한정. |

검토 깊이는 기존 기능 재확인은 **보통**, 이번 TTL·삭제 경합은 **높음**이다. 실제 클라이언트→HTTP→명령 큐→저장소→응답·최종 상태와 실패 경로를 추적하고, 시간·명령 순서를 제어해 실행했다. 기존 단계 전수·정적 검사는 같은 소스 통과 증거가 있어 반복하지 않았다. 고정 포트 수동 시연, Optional 영속성·배포, 성능 비교·실제 설명 확인은 이번 E 실행 범위 밖이다.

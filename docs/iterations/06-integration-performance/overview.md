## 목표와 범위

앞선 단계에서 만든 저장소·HTTP API·만료·무효화·동시성 동작을 **외부 사용 흐름에서 최종 확인**하고, 과제의 **캐시 미사용·미스·히트 성능 비교**를 실제 측정으로 수행한다. 해시 테이블의 설계와 주요 함수, 만료·동시성 선택을 실제 코드에 근거해 설명할 수 있는지도 확인한다.

새 기능이나 별도의 6단계 요구사항 명세를 만드는 단계가 아니다. 검증 기준은 [과제 원문](../../assignment.md)과 [기존 단계의 요구사항·계약](../README.md)이다. 검증에서 결함이 나오면 관련 단위로 돌아가 수정·재검증한다. Optional 영속성이나 배포 형태 결정은 자동으로 포함하지 않는다.

## 확정된 성능 비교 조건

- **대상:** 원본 API는 Docker의 MongoDB(`mongo:7`, WiredTiger 캐시 0.25GB, 컨테이너 메모리 1GiB)에서 `_id`로 문서 하나를 조회해 응답한다. 시드는 문서 100만 개 × 값 1,024바이트(저장 약 1.09GB)로 DB 캐시보다 크게 만들고, 측정 전에 WiredTiger 캐시를 비운다. 인위적 지연은 넣지 않는다. 클라이언트 관점의 순차 요청 지연시간을 비교하며 동시 부하 처리량은 제외한다. 같은 키를 반복해 읽으면 DB 캐시 효과로 원본 조회 비용이 가려지므로 매 측정마다 다른 키를 읽는다([조건 설계](verification.md#31-측정-조건--mongodb-원본키-분산)). 처음 사용한 고정 응답 원본의 측정은 [참고 기록](verification.md#35-고정-응답-원본-조건-결과--이전-측정-참고-보존)으로만 남겼다. DB 조회가 OS·Docker VM 파일 캐시에서 처리될 수 있어 디스크 읽기로 단정하지 않고, 모든 경로가 로컬 HTTP를 거치는 전체 흐름 비교다.
- **측정 구간:** 실행 중인 클라이언트가 값 획득을 시작하기 직전부터 호출 결과가 확정될 때까지. 서버·클라이언트 프로세스 시작, 상태 준비, 별도의 원본 호출 횟수 확인은 제외한다.
- **상태 준비:** 두 서버는 계속 실행한다. 고정 시드로 컬렉션 전체에서 서로 다른 항목을 뽑아 매 호출에 하나씩 배정하고(세 조건 같은 분포, 키 공유 없음), 예제의 `reuse()`에 해당 캐시 키·원본 경로를 넘긴다. 미사용은 캐시를 건너뛰고 원본을 조회한다. 미스는 측정 전에 해당 캐시 키를 삭제하고, 측정 중 캐시 조회→원본 조회→저장을 거친다. 히트는 측정 전에 해당 키에 예상 값을 저장하고, 측정 중 캐시를 조회한다. 상태 준비는 매번 측정 구간 밖에서 한다.
- **반복·순서:** 실행 경로별 준비 동작을 포함해 미사용·미스·히트를 각 5회 예열한 뒤(측정에서 제외), 세 조건을 번갈아 100회씩 측정한다. 조건 실행 순서는 라운드마다 순환해 한 조건이 항상 먼저 오지 않게 한다. 미스·히트는 매 회차 상태를 다시 준비한다.
- **집계·유효성:** 회차별 경과 시간과 성공/실패를 원자료로 보존하고, 성공한 100회씩의 중앙값을 주 비교값, 90백분위값을 보조값으로 보고한다. 각 호출의 값과 원본 데이터 요청 횟수 변화(미사용·미스 각 1, 히트 0)를 측정 구간 밖에서 확인한다. 실패는 제거하거나 성공으로 대체하지 않고 원인·재실행을 별도로 기록하며, 조건별 100회 성공이 확보되지 않으면 완결된 비교로 판정하지 않는다. Python·OS·실행 호스트·서버/클라이언트 버전과 측정 명령을 함께 기록한다. 로컬 DB 조회 API의 결과를 다른 원본 작업·환경·동시 부하의 성능으로 일반화하지 않는다.

## 진행 체크리스트

완료된 조건·사례 정리와 남은 실행을 구분한다. 체크 표시는 문서화 또는 실행을 실제로 마친 범위에만 적용하며, 계획 확정은 테스트 통과가 아니다.

- [x] **성능 비교 조건 정하기:** 기존 원본 API를 사용해 미사용·미스·히트의 측정 구간, 상태 준비, 순차 요청, 반복·집계·유효성 기준을 위에 정리한다. (조건 확정만 완료; 측정·실행 결과 아님)
- [x] **전체 사용 시나리오·TC 정하기:** 원본 API 포함 요청·초기 상태·기대 결과 및 성능 비교 절차를 [테스트 케이스 (`test-cases.md`)](test-cases.md)에 기존 요구사항과 연결했다. 문서 검토의 두 지적을 보완한 뒤 제한 재검토 승인을 받았다. (실행 전 계획만 완료; 실행·측정 승인 아님)
- [x] **기존 기능 재확인:** 제품·테스트 7개의 해시가 5단계 최종 검증 당시와 일치함을 확인해 2~5단계 증거를 재사용했다. 새 지속 클라이언트의 `fetch()`·`reuse()` 연결 probe 1/1 통과(exit 0), 서버 정상 종료·회수와 실행 전후 파일 불변을 확인했다. 전체 테스트는 반복하지 않았으며 5단계 계측 적용 결과와 원본 무보정 runner를 구분한다. [검증 기록](verification.md) 참조. 이후 제품·연결 경로가 바뀌면 영향 범위를 추가 검증한다.
- [x] **전체 사용 흐름 검증:** 실제 별도 서버·예제 프로세스로 E-001~007 고유 7/7 통과, 각 worker exit 0. 원본 재사용·삭제/만료 뒤 재조회·빈 값·거부 후 보존·실패·삭제 경합을 확인했다. 제어 시간과 실제 명령 순서 계측, 결과·한계는 [검증 기록](verification.md#2-전체-사용-흐름-검증)에 남겼다. 제품·원본 테스트 변경 없이 서버 정상 종료·회수를 확인했으며 성능 측정은 포함하지 않는다.
- [x] **성능 비교 실행:** MongoDB·키 분산 조건의 측정·기록 및 측정 당시 소스 해시 기준 독립 검증 완료. 이후 예제 정리도 제한 재검토 승인(성능 재측정은 하지 않음). 조건별 값·집계 방식·환경과 비교의 한계는 [검증 기록의 해당 절](verification.md#3-성능-비교-실행)에 남겼다. [5단계 반복 시험](../05-concurrency/verification.md#최종-검증--5단계-범위-승인)을 성능 비교 결과로 대신하지 않는다.
- [x] **결과 정리·설명:** E/P 실행의 명령·환경·결과·한계를 [검증 기록 (`verification.md`)](verification.md)에 반영하고 R-001/002 코드·원자료 대응을 점검했다. [결과 정리·설명 절](verification.md#4-결과-정리설명)에서 직접 대화로 확인한 설명과 나머지 코드·문서 근거를 구분했으며, 설명 가능하다는 본인 확인을 받아 이번 항목을 마감했다.

## 다음 확인 지점

이번 단계의 실행·근거 점검·설명 가능 여부의 본인 확인을 마쳤다. [검증 기록 (`verification.md`)](verification.md)에 실제 결과와 한계를 남겼으며, 이 로컬 환경의 MongoDB·키 분산 조건에서는 히트가 미사용보다 빨랐다(중앙값 0.558ms 대 2.352ms, 독립 검증 승인). 고정 포트 수동 시연, Optional 영속성·배포, 다른 원본 작업·환경의 성능은 이번 완료 범위에 포함하지 않는다.

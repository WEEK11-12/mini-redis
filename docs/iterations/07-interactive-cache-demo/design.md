# 7단계 설계 — 키·값 인터랙티브 캐시 시연 페이지

- **상태:** 구현에 사용한 간소화 설계. 엄격한 TCP 소유 증명·내구적 PUT 선기록·세대 장부·자동 복구는 범위에서 제외했다. 구현·시험 및 선별 독립 검토 결과와 한계는 [검증 기록](verification.md)에 정리했다.
- **근거:** [요구사항](requirements.md), [단계 개요](overview.md), [Mini Redis HTTP 코드](../../../mini_redis/http_api.py). 앞선 OS 스파이크는 전용 자식의 정상 PUT/GET과 일부 종료 경로만 확인했으며, 이 간소화 설계 전체를 검증한 것은 아니다.

## 1. 목표와 경계

브라우저에서 키·값을 저장·수정하고, 캐시 우선 읽기와 DB 직접 읽기의 출처·시간을 보여 준다. MongoDB의 `mini_redis_demo.entries`가 원본, 새로 시작한 **7단계 전용 Mini Redis 자식의 메모리**가 사본이다. 기존 사용자 서비스·DB·컨테이너·시드 `mini_redis_origin.items`는 건드리지 않는다. 제품 `mini_redis/` 코드도 바꾸지 않는다.

**운영 가정:** 한 번에 페이지 서버 하나, 로컬 단일 사용자 시연이다. 같은 checkout의 중복 실행은 페이지 서버만 보유하는 잠금으로 거부한다. 다른 checkout이나 같은 사용자의 별도 로컬 프로그램이 DB·캐시 포트를 임의로 건드리는 상황은 보장 범위 밖이다. 일반 서버의 공격·고가용성·무중단 캐시 복구를 해결하려는 설계가 아니다.

## 2. 실행과 캐시 실패 경계

### 2.1. 전용 자식 한 번만 실행

1. 페이지 서버는 시작할 때 새 자식 래퍼를 실행한다. 래퍼가 `create_server('127.0.0.1', 0, HashTableStore())`로 **새 빈 캐시**를 만들고, 실제 OS 배정 포트를 부모 전용 채널로 전달한다. 페이지 서버의 캐시 작업은 그 포트의 공개 Mini Redis HTTP API만 사용한다. 외부 `--cache-url`이나 기존 인스턴스 재연결은 받지 않는다. 준비 통지를 못 받거나 자식이 이미 종료했다면 캐시는 시작부터 사용하지 않는다.
2. 페이지 서버는 자기가 만든 자식 핸들·포트만 보유한다. 캐시 호출 전 살아 있는지 확인하지만, 매 연결의 `lsof` 조회·peer PID 인증·FD 전달은 **요구하지 않는다**. 포트가 다른 로컬 프로세스에 재점유되는 극단적인 경쟁까지 증명해 막지는 않는다. 이는 로컬 시연의 명시적 한계이며 보안 보증이 아니다.
3. 자식의 기동 실패, 종료, 접속 실패, 시간 초과, 예기치 않은 HTTP 상태·본문 등 **캐시 결과가 조금이라도 불분명하면 즉시 이 페이지 서버 수명 동안 캐시 전체를 비활성화**한다. 그 뒤 캐시 GET·PUT·DELETE를 일절 보내지 않고 DB에서만 읽는다. 잠시 기다리거나 DELETE를 재시도해 다시 켜지 않는다. 캐시 자동 재기동·자동 복구도 없다.
4. 정상 페이지 종료 때는 생성한 자식에만 종료를 요청하고 자식 핸들로 회수한다. 부모의 비정상 종료에는 제어 파이프 EOF를 받은 자식이 종료를 시도한다. 종료 지연·고아 자식이 있을 수 있지만 **새 페이지 서버는 이를 입양·종료·재접속하지 않는다**. 새 페이지 시작은 매번 새 빈 `HashTableStore()`와 새 OS 배정 포트를 사용하므로 이전 자식의 늦은 PUT을 읽지 않는다. 기존 프로세스를 PID나 포트만 보고 종료하지 않는다.

**왜 지연 PUT에도 이전 값이 다시 보이지 않나:** 값 읽기에서 캐시 PUT 응답이 불확실하면 그 즉시 캐시를 비활성화한다. 옛 자식에서 그 PUT이 뒤늦게 실행되더라도 이 서버는 다시 그 자식을 읽지 않는다. 페이지가 중단됐다면 다음 서버는 **새 빈 자식만** 사용한다. 시간 경과나 늦은 DELETE를 안전 증거로 쓰지 않는다. 이전 설계의 선기록·수명 잠금·세대 장부·고아 회수·`SCM_RIGHTS` 후보는 **이 간소화안에서 사용하지 않는다**. 다만 다른 로컬 프로그램의 포트 선점 및 자식 종료 후 재점유까지 막는 엄격한 소유 보증은 포기한다.

### 2.2. DB 데이터

- `mini_redis_demo.entries`에 `{_id: 키, value: 문자열, updated_at: UTC 시각}`을 저장한다. `_id`로 같은 키를 갱신한다. 목록도 이 컬렉션에서만 조회한다. 시드 DB는 읽거나 변경하지 않는다.
- 원본 DB와 캐시 외에 보존하는 것은 속도 기록 파일뿐이다. DB `cache_cleanup_pending`·`save_id`, 디스크 PUT 선기록과 복구 장부는 쓰지 않는다. 재시작 때 옛 캐시를 복원하지 않으므로 이 표시가 필요 없다.

## 3. 저장·읽기와 예외

모든 저장·읽기 작업은 페이지 서버의 잠금 하나로 **한 번에 하나씩** 실행한다. 앞 요청이 끝나기 전에 뒤 요청이 오래된 DB 값을 캐시에 다시 채우지 못하게 한다. DB 호출에는 유한 시간 제한을 둔다(예: `timeoutMS=3000`, 실제 pymongo 환경에서 확인 필요). 캐시 HTTP 호출도 유한 시간 제한(예: 3초)을 둔다. 타임아웃은 원격 작업의 취소 증거가 아니다.

### 3.1. 저장·수정

1. 입력 검증 후 DB에 값을 `upsert`한다. 새 키면 “저장했어요”, 기존 키면 같은 값을 다시 저장해도 “수정했어요”. DB 쓰기가 실패하거나 결과가 불분명하면 저장 실패를 알리고 **캐시 내용을 변경하지 않는다**. 실패 종류를 세분하지 않고 이 서버 수명 동안 캐시 접근도 중단한다(내용은 수정하지 않음).
2. DB 성공 뒤 캐시를 사용 중이면 `DELETE /keys/키`를 **한 번** 보낸다. `200 {"deleted": true|false}`로 확인되면 그 키의 첫 읽기는 캐시 미스→DB, 다음 읽기는 캐시 히트다. DELETE 실패·타임아웃·응답 불명은 재시도하지 않고 **전체 캐시를 비활성화**한다. DB 저장 성공은 그대로 알리되 “다음에 읽을 때는 조금 더 걸릴 수 있어요.”를 덧붙인다. 이후 값 읽기는 DB 대체 읽기다.
3. DB 성공 직후 페이지 서버가 종료돼 DELETE를 못 보냈더라도 새 페이지 서버는 옛 캐시를 사용하지 않고 새 빈 캐시를 시작한다. 캐시가 없는 상태에서는 저장에 따라 캐시를 새로 만들거나 기존 프로세스를 찾지 않는다.

### 3.2. 캐시 우선·DB 직접 읽기

- **값 읽어오기:** 캐시 사용 가능 시 `GET /keys/키`의 `200 {"value": 문자열}`은 캐시 히트다. `404 KEY_NOT_FOUND`면 DB에서 값을 읽고, 값이 있을 때만 캐시 `PUT`을 시도한다. `200 {"stored": true}`를 확인하면 “DB에서 읽어와 캐시에 담았어요”; PUT이 불분명하면 즉시 전체 캐시를 비활성화하고 방금 읽은 DB 값을 “캐시를 쓸 수 없어 DB에서 읽었어요”로 반환한다. 캐시 GET 오류도 같은 DB 대체 읽기다. DB에도 없으면 `404 KEY_NOT_FOUND`이고 캐시에는 쓰지 않는다.
- **DB에서 직접 읽기:** 캐시를 호출하거나 바꾸지 않고 DB만 읽어 “DB에서 직접 읽어왔어요”로 표시한다. DB 조회 실패는 `503 DB_UNAVAILABLE`이고 임의 값을 만들지 않는다.
- **캐시 응답 검증:** 404라도 코드가 `KEY_NOT_FOUND`가 아니거나 JSON·필드형식이 틀리면 미스가 아니라 캐시 장애다. 읽기 출처는 실제 완료된 경로와 일치해야 한다. 캐시 비활성화 뒤 DB도 불능이면 `503` 오류다.

**남은 한계:** DB 쓰기가 시간 초과로 실패한 것처럼 보였지만 나중에 반영되는 경우는 [REQ-07-008](requirements.md#req-07-008--캐시db-장애-때의-동작-확정)의 이미 수용한 예외다. 이 안은 불확실한 DB 쓰기 뒤 캐시를 비활성화해 그 서버 수명 중 오래된 캐시 히트를 더 보이지 않게 하지만, DB 반영 자체의 시점을 보증하지는 않는다. 다른 프로그램의 직접 DB 변경도 감지하지 않는다.

## 4. 속도 기록과 화면

- 페이지 서버에서 `time.perf_counter_ns()`로 작업 잠금을 얻은 뒤부터 마지막 DB/캐시 호출이 끝날 때까지 측정한다. 잠금 대기·브라우저 렌더링·기록 파일 쓰기는 제외한다. 캐시 요청은 매번 새 TCP 연결이고 DB는 연결 풀을 쓸 수 있으므로 시간은 **단발 체험 수치**일 뿐 공식 성능 측정이 아니다.
- `var/interactive-cache-demo/timings.jsonl`에 동작마다 한 줄씩 추가한다. 시각·키·`save/read/read_db`·`cache/db_then_cache/db_fallback/db_direct` 출처·성공/실패·밀리초를 남기고 값은 기록하지 않는다. 자동 삭제하지 않는다. 전체 유효 성공 행으로 출처별 횟수·평균·중앙값을 계산하고 실패/없는 키는 별도 집계한다. 잘린 행은 요약에서 제외하고 수를 표시한다. 화면에는 최근 50행만 보여 주되 파일은 보존한다. 파일 쓰기 실패는 동작 결과를 바꾸지 않고 `timing_saved: false`로 알린다.
- 화면은 (1) 키·값 입력/저장, (2) DB 기준 키 목록의 “값 읽어오기”·“DB에서 직접 읽기” 버튼과 결과, (3) 속도 기록·요약으로 구성한다. 값은 텍스트로만 표시한다. 저장 안내에는 내부 DB·캐시 용어를 쓰지 않고, 읽기 결과에만 출처를 알린다. 기록 위에 “이 화면의 시간은 이 컴퓨터에서 한 번씩 잰 체험 수치예요. 6·7단계 성능 비교와 같은 측정이 아니에요.”를 표시한다.

## 5. 페이지 HTTP·입력 경계

Mini Redis의 기존 `/keys/...` 계약은 바꾸지 않는다. 페이지 서버는 `127.0.0.1`에만 바인딩하고 브라우저에 임의 DB 주소·경로 입력을 제공하지 않는다.

| 페이지 경로 | 역할 |
| --- | --- |
| `GET /` | 화면 HTML과 이번 서버의 요청 토큰 |
| `GET /api/keys` | DB 키 목록(최대 200개, 초과 시 `truncated: true`) |
| `POST /api/entries` | `{key,value}` 저장, `created/updated`, 안내·시간·기록 여부 |
| `POST /api/reads` | `{key,mode: cache_first\|db_direct}` → 값·실제 출처·문구·시간·기록 여부 |
| `GET /api/timings` | 최근 기록·전체 성공 요약·실패/없는 키 수 |

모든 JSON 응답은 `Cache-Control: no-store`, 오류는 `{"error":{"code":"…","message":"…"}}` 형식을 쓰고 내부 주소·경로·예외는 노출하지 않는다. POST는 Host·Origin을 현재 페이지와 대조하고 페이지별 무작위 `X-Demo-Token`을 요구하며 CORS는 열지 않는다. 검증 거부는 DB·캐시·기록 호출 전이다. 키는 비어 있지 않은 ASCII 영숫자·`-_.~`만 허용하되 전체 `.`·`..`는 금지, 최대 200자다. 값은 빈 문자열도 허용하고 `json.dumps({"value": 값}, ensure_ascii=False, separators=(",", ":")).encode("utf-8")` **전체가 65,536바이트 이하**여야 한다. 틀리면 이해하기 쉬운 `400`, DB·캐시 변화 없음. 보호 실패는 `403`, 없는 키는 `404`, DB 장애는 `503`이다.

## 6. 요구사항 대응과 확인 범위

| 요구사항 | 간소화안의 대응 |
| --- | --- |
| REQ-07-001~003 | DB upsert·키 목록, 성공한 저장 뒤 캐시 DELETE; 실패한 DELETE는 캐시 전체 중단 |
| REQ-07-004~006 | 정상 미스→DB→확정 PUT→다음 캐시 히트. 수정 뒤 삭제 실패·불확실 PUT은 그 세션의 캐시 접근 중단. 새 세션은 빈 캐시 |
| REQ-07-007~009 | 서버 측 기록 보존·출처 문구·캐시 장애 시 DB 대체 읽기; DB 장애는 오류 |
| REQ-07-010~011 | Mini Redis 입력 한도, 별도 DB 컬렉션·기존 데이터 비접근 |
| REQ-07-012~013 | 폐기한 성능 비교 웹 뷰 코드 미사용, 제품 코드 불변, 페이지의 루프백·출처/토큰 보호 |

**검증 범위:** (a)~(f)의 구현 경로는 자동 시험·격리 시연·선별 독립 검토로 확인한 범위가 [검증 기록](verification.md)에 표시돼 있다. 복잡한 OS 소유권·세대 증명, 포트 재점유 경쟁 및 협력하지 않는 고아 프로세스의 완전한 회수는 범위 제외다. 실제 MongoDB 장애 시험은 수행하지 않았으며, 단위/이중물 오류 주입의 확인 범위와 구분한다.

# 7단계 요구사항 명세서 — 키·값 인터랙티브 캐시 시연 페이지

- 상태: 요구사항과 범위는 확정. 인수 조건별 증거와 확인 범위는 [검증 기록](verification.md)에 있으며, 문서의 명세 자체를 통과 증거로 보지 않는다.
- 적용 범위: 브라우저에서 키·값을 직접 입력해 저장·수정하고, 키별로 값을 읽어 오면서 **캐시에서 읽었는지 DB에서 읽었는지**와 걸린 시간을 확인하는 로컬 페이지. 사용자에게는 저장소 구조를 드러내지 않는 일반적인 저장·조회 화면으로 보이되, 내부에서는 DB와 캐시(Mini Redis)를 모두 사용한다.
- 근거: 개발자 요구(이전 성능 비교 화면은 버튼 실행형이라 의도와 달라 별도 단계로 분리; 그 단계는 이후 폐기·정리됨), [3단계 요구사항](../03-http-api/requirements.md)의 Mini Redis HTTP 계약, [6단계 성능 비교 조건](../06-integration-performance/overview.md#확정된-성능-비교-조건)
- 제외(이번 범위 밖): 삭제 버튼, 만료 시간(TTL) 입력, 여러 사용자의 동시 접속, 인증·배포, 6단계와 같은 공식 성능 측정, 대량 데이터 시드.

## 식별·상태

- ID는 `REQ-07-001`처럼 단계 번호와 일련번호를 쓴다. **명세**는 기대 동작이고 **인수 조건**은 실행으로 확인할 기준이다. 판정은 [검증 기록](verification.md)의 TC별 증거를 따른다.
- 각 요구의 `확정`은 개발자가 방향을 정한 항목이고 `제안`은 설계 검토에서 조정될 수 있는 항목이다. 알고리즘·파일 구조·프로세스 기동 방식 같은 내부 선택은 설계에서 정한다.

## 기능 요구사항

### REQ-07-001 — 저장 화면 (확정)

- **명세:** 화면에 "무엇을 저장하시겠어요?" 입력 영역(키, 값)과 저장 버튼을 둔다. 같은 키로 다시 저장하면 값이 바뀐다. 결과 메시지는 새 저장이면 "저장했어요", 기존 키 갱신이면 "수정했어요" 같은 일반적인 문구로 알린다. 빈 문자열 값은 허용한다.
- **인수 조건:** 새 키를 저장하면 키 목록에 나타난다. 같은 키를 다른 값으로 저장하면 목록에 새 항목이 늘지 않고 값만 바뀌며 메시지가 수정으로 구별된다. 빈 값으로 저장한 키도 존재하는 키로 목록에 나온다.
- **근거:** 개발자 요구, [REQ-03-001](../03-http-api/requirements.md#req-03-001--저장덮어쓰기의-외부-호출).

### REQ-07-002 — 저장·수정 때 DB 반영과 캐시 무효화 (확정)

- **명세:** 저장·수정은 **DB에 먼저 반영**하고, 성공한 뒤 해당 키의 **캐시 항목을 삭제**한다(캐시는 저장 때 채우지 않고 읽을 때 채운다). 그래서 저장·수정 직후 첫 읽기는 DB를 거치고 이후 읽기는 캐시에서 이루어진다. DB 반영이 실패하면 캐시를 바꾸지 않고 저장 실패를 알린다. DB는 성공했지만 캐시 항목 삭제가 실패하면 값은 저장되었음을 알리되 이후 읽기에서 오래된 값을 반환하지 않아야 하며, 그 방법은 설계에서 정한다.
- **인수 조건:** 정상 저장·수정 뒤 DB에는 새 값이 있고 캐시에는 해당 키가 없다(삭제 뒤 조회 `404 KEY_NOT_FOUND`). DB 쓰기 실패를 주입하면 캐시 값이 이전 그대로이고 실패 메시지가 나온다. 캐시 삭제 실패를 주입하면 DB에는 새 값이 있고 안내 메시지가 나오며, 이어지는 읽기에서 이전 값이 나오지 않는다.
- **근거:** 개발자 요구(내부적으로 캐시와 DB를 모두 사용, 저장 직후 첫 읽기에서 DB 경유를 시연으로 확인), [REQ-03-001](../03-http-api/requirements.md#req-03-001--저장덮어쓰기의-외부-호출), [REQ-03-004](../03-http-api/requirements.md#req-03-004--삭제).

### REQ-07-003 — 저장된 키 목록 (확정)

- **명세:** 저장한 키들을 목록으로 보여 주고 키마다 읽기 동작 버튼을 둔다. 목록의 기준은 DB에 저장된 키이며, 서버나 캐시를 다시 시작해도 목록이 유지된다.
- **인수 조건:** 키를 저장한 뒤 서버를 재시작해도 같은 키 목록이 보인다. 캐시를 비우거나 재시작해도 목록은 변하지 않는다.
- **근거:** 개발자 요구(키마다 버튼).

### REQ-07-004 — 값 읽어오기: 캐시 우선 (확정)

- **명세:** 키별 "값 읽어오기" 버튼은 **캐시를 먼저 조회**한다. 캐시에 있으면 그 값을 보여 주며 "캐시에서 읽어왔어요"를, 없으면 DB에서 읽어 와 캐시에 저장한 뒤 "DB에서 읽어와 캐시에 담았어요"를 표시한다. 두 경우 모두 읽은 값과 걸린 시간을 함께 보여 준다.
- **인수 조건:** 읽기 결과는 캐시 상태에 따라 위 두 메시지 중 정확히 하나다. 캐시에 해당 키가 없는 상태의 첫 읽기는 "DB에서 읽어와 캐시에 담았어요"이고 이어지는 두 번째 읽기는 "캐시에서 읽어왔어요"이다. 표시된 출처가 실제 읽은 경로와 일치한다(캐시 서버 호출·DB 호출 기록으로 대조). REQ-07-002에 따라 저장·수정 직후에는 캐시에 해당 키가 없으므로 그 첫 읽기는 항상 "DB에서 읽어와 캐시에 담았어요"이다.
- **근거:** 개발자 요구, [REQ-03-007](../03-http-api/requirements.md#req-03-007--api-응답-저장재사용-기능-사례)의 응답 재사용 흐름.

### REQ-07-005 — DB에서 직접 읽기 (확정)

- **명세:** 키별 보조 버튼 "DB에서 직접 읽기"는 캐시를 거치지 않고 DB에서 값을 읽으며 "DB에서 직접 읽어왔어요"를 표시한다. 이 동작은 캐시 내용을 바꾸지 않는다.
- **인수 조건:** 캐시에 값이 없는 키를 직접 읽은 뒤에도 캐시는 여전히 비어 있다(이어서 값 읽어오기가 DB 경유 메시지로 나온다). 걸린 시간이 기록된다.
- **근거:** 개발자 요구(캐시·DB 속도 비교).

### REQ-07-006 — 수정 뒤 읽기의 최신성 (확정)

- **명세:** 값을 수정한 직후 어떤 읽기 동작을 해도 수정 전 값을 보여 주지 않는다.
- **인수 조건:** 키 `a`를 값 1로 저장·읽기(캐시 담김) → 값 2로 수정 → 값 읽어오기와 DB에서 직접 읽기 모두 값 2다. 캐시 삭제 실패를 주입한 경우에도 이전 값이 나오지 않는다.
- **근거:** REQ-07-002의 목적.

### REQ-07-007 — 속도 기록 (확정, 세부 표시는 제안)

- **명세:** 읽기·저장 동작마다 서버 안에서 잰 소요 시간을 기록한다. 기록 항목은 시각, 키, 동작 종류, 읽은 곳(캐시/DB 직접/DB 경유 후 캐시 저장), 소요 시간(ms), 성공·실패다. 기록은 화면에 시간순으로 보여 주고 읽은 곳별 횟수·평균·중앙값 요약을 제공한다(제안). 기록은 서버를 다시 시작해도 남는다(제안: 파일 저장). 기록은 자동 삭제하지 않으며(REQ-07-011), 화면에는 최근 일정 수만 표시할 수 있다(표시 수 제한은 삭제가 아니다). 화면에는 이 수치가 단발 체험 수치이며 6·7단계 공식 성능 비교와 같지 않다는 문구를 둔다. 브라우저에서 잰 시간으로 판정하지 않는다.
- **인수 조건:** 동작 뒤 기록 행이 추가되고 출처·시간이 채워진다. 요약의 횟수는 기록 행 수와 일치하고 평균·중앙값은 기록 원자료에서 다시 계산한 값과 같다. 서버 재시작 뒤 기록이 남아 있다. 실패한 동작은 성공 기록과 섞여 요약에 들어가지 않는다.
- **근거:** 개발자 요구(속도 비교 기록), [6단계 성능 비교 조건](../06-integration-performance/overview.md#확정된-성능-비교-조건)의 서버 측 측정 원칙.

### REQ-07-008 — 캐시·DB 장애 때의 동작 (확정)

- **명세:** DB를 읽을 수 없으면 오류를 알리고 값을 지어내지 않는다. 캐시 서버를 쓸 수 없을 때 값 읽어오기는 DB에서 읽고 "캐시를 쓸 수 없어 DB에서 읽었어요"로 알린다(개발자가 추천안을 채택). 어느 경우에도 화면에 내부 경로·명령·접속 정보를 노출하지 않는다.
- **인수 조건:** 장애를 주입한 시험에서 위 메시지와 기록(실패 또는 폴백 구분)이 일치하고, 오래된 값이 표시되지 않는다.
- **알려진 한계(개발자 수용):** DB 쓰기가 시간 초과로 끝난 뒤 그 쓰기가 **늦게 반영**되면, 반영 전 DB 조회에서 이전 값이 보일 수 있다. 단일 사용자 로컬 시연 전제에서 이 한계를 수용한다. 간소화 설계는 DB 쓰기 실패 뒤 그 페이지 서버 수명 동안 캐시 접근을 중단해 이전 값을 다시 캐시에 담아 지속 노출하는 경로를 줄이지만, DB의 늦은 반영 자체는 막지 못한다. 위 인수 조건은 이 한계 상황에는 적용하지 않는다.
- **근거:** REQ-07-002·006.

### REQ-07-009 — 화면 어휘 (확정)

- **명세:** 저장·수정 화면과 메시지는 "저장했어요"처럼 저장소 구조를 드러내지 않는 문구를 쓴다. 읽기 동작의 반응에서는 값을 어디서 읽었는지(캐시/DB)를 구별해 알린다.
- **인수 조건:** 저장·수정 결과 문구에 DB·캐시 같은 내부 용어가 나오지 않는다. 읽기 반응 문구는 REQ-07-004·005의 문구를 따른다.
- **근거:** 개발자 요구.

### REQ-07-010 — 입력 제약 (확정)

- **명세:** 키는 Mini Redis HTTP 키 제약([REQ-03-005](../03-http-api/requirements.md#req-03-005--입력-거부와-내부-오류-구별): 비어 있지 않은 ASCII 영숫자·`-_.~`, 키 전체 `.`·`..` 금지)을 따르고 길이는 200자 이하, 값은 문자열이며 Mini Redis 요청 본문 전체가 65,536바이트 이하가 되는 크기(화면 문구 "약 64KB까지")로 한다. 제약에 어긋나면 이해하기 쉬운 문장으로 거부하고 DB·캐시를 변경하지 않는다.
- **인수 조건:** 금지 문자 키·빈 키·초과 크기 값은 저장되지 않고 DB·캐시가 그대로이며 사유가 화면에 나온다.
- **근거:** [D-0004](../../decisions/0004-http-key-no-slash.md), [D-0005](../../decisions/0005-http-api-boundary.md), REQ-03-005.

### REQ-07-011 — 데이터 분리와 보존 (확정)

- **명세:** 이 페이지의 데이터는 6단계 시드 컬렉션(`mini_redis_origin.items`)과 **별도 컬렉션**에 저장한다. 시드와 기존 데이터를 읽거나 바꾸거나 삭제하지 않는다. 서버·화면을 종료해도 데이터와 기록을 자동 삭제하지 않는다.
- **인수 조건:** 시연은 별도 컬렉션만 사용하고 기존 데이터에 접근하는 경로가 없다(코드·설정 확인). 서버 종료·재시작 뒤 시연의 저장 데이터와 기록이 남아 있다.
- **근거:** 개발자 요구. 시연 데이터를 분리하고 기존 데이터에는 접근하지 않으며, 시연의 저장 데이터와 기록도 자동 삭제하지 않는 보존 원칙을 따른다.

### REQ-07-012 — 낮은 결합 (확정)

- **명세:** 7단계 코드는 폐기한 성능 비교 웹 뷰(이전 `examples/live_benchmark*`, `tests/*live_benchmark*`)의 코드·실행 상태·공유 파일을 가져오거나 공유하지 않는다. 해당 파일은 현재 저장소에서 제거됐다. 페이지의 캐시 작업은 공개 Mini Redis HTTP API로만 하고 DB에는 MongoDB 접속을 사용한다. 전용 자식의 **실행 래퍼에 한해** 기존 제품 서버 팩터리 `create_server(..., HashTableStore())`를 호출할 수 있으나 `mini_redis/` 제품 코드는 바꾸지 않는다. 폐기한 파일의 제거가 7단계 동작과 테스트에 영향을 주지 않아야 한다.
- **인수 조건:** 7단계 소스가 폐기한 모듈을 import하거나 그 경로를 참조하지 않는다(검색으로 확인). 해당 파일이 없는 현재 작업 트리에서 7단계 테스트가 통과한다. `mini_redis/`의 Git 변경이 없다.
- **근거:** 개발자 요구(새 구현 뒤 폐기한 부분 정리). 정리는 완료됐다.

### REQ-07-013 — 로컬 전용 접근 (확정, 세부는 설계)

- **명세:** 페이지와 서버는 로컬(`127.0.0.1`)에서만 접근되며 브라우저가 임의 DB 주소·명령·경로를 입력하게 하지 않는다. 다른 출처 웹페이지가 이 서버로 저장·수정 요청을 보낼 수 없어야 한다. 구체적인 보호 방식(출처·토큰 등)은 설계에서 정한다.
- **인수 조건:** 외부 인터페이스 바인딩이 없고, 다른 출처에서 온 쓰기 요청이 거부되며 DB·캐시가 변하지 않는다.
- **근거:** 로컬 시연 서버 보호 원칙(루프백 전용 바인딩, 페이지와 같은 출처·Host 대조, 시작마다 새로 만든 요청 토큰, 임의 주소·명령 입력 불허)을 이전 후속 시연에서 이어받는다. 개발자 요구.

## 확정한 선택

- **저장 때 캐시는 갱신하지 않고 삭제한다(읽을 때 채움):** 개발자가 선택했다. 수정 직후 첫 읽기에서 "DB에서 읽어와 캐시에 담았어요"를 시연으로 볼 수 있고, 저장 직후 캐시에 오래된 값이 남는 위험이 없다. 별도의 캐시 비우기 동작은 두지 않는다. 대안(저장 때 캐시 갱신 + 화면의 캐시 비우기, 캐시 서버 재시작으로만 확인)은 채택하지 않았다.

## 설계로 넘기는 선택 (요구사항이 아님)

- Docker MongoDB와 Mini Redis를 누가·어떻게 기동하는가(사용자가 미리 띄움 / 페이지 서버가 기동). 기존 측정용 자원을 재사용하더라도 코드는 공유하지 않는다.
- 캐시 항목 삭제가 실패했을 때 오래된 값 반환을 막는 방법.
- 속도 기록 파일 형식·위치와 요약 계산 방식, 기록 보존 한도.
- 페이지 서버 구조(제공 방식, 요청 보호 방식).
- 키 목록이 많아질 때의 표시 방식(이번 범위는 소규모 시연).

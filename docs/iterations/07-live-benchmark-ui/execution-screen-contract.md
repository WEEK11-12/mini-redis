# 7단계 실행 조건·화면 계약

- **상태:** B안(환경 준비 자동화)과 아래 상세 실행·화면 계약 채택([D-0008](../../decisions/0008-live-benchmark-contract.md)). 전체 설계 검토는 조건부 적합이었고 당시 차단 의견의 수정은 해당 범위 재점검에서 설계 수준 비차단. 수정본 전체의 독립 재승인이나 구현·실행 검증 완료 기록은 아니다.
- **근거:** [7단계 범위](overview.md), [6단계 MongoDB 측정 조건과 한계](../06-integration-performance/verification.md#3-성능-비교-실행), [`benchmark.py`](../../../examples/benchmark.py), [`seed_mongo.py`](../../../examples/seed_mongo.py).

## 이미 정해진 경계와 현재 코드

- 로컬 시연에서 브라우저는 준비·실행 요청과 상태·결과 표시를 맡는다. `examples/benchmark.py`가 별도 원본 API·Mini Redis 서버를 띄우고 MongoDB를 조회한다. 브라우저 시간이나 6단계의 저장된 수치로 새 실행 결과를 대신하지 않는다. 제품 코드·측정 규칙은 변경하지 않는다.
- 측정기는 MongoDB URI와 매번 **새로운** `--output` 경로를 필수로 받는다. 세 조건(`no_cache`, `miss`, `hit`)에 각 5회 예열(집계 제외), 100회 순차 측정, 서로 다른 키, 값 획득 구간만 타이머, 성공 표본의 중앙값·nearest-rank P90을 적용한다. 회차별 실패와 중단 사유는 원자료에 남긴다. `summary.complete`는 각 조건 100회 성공·실패 0이고 중단이 없을 때만 참이다.
- `seed_mongo.py` 기본 실행은 `mini_redis_origin.items` 컬렉션을 **삭제 후 재생성**하여 `item-0`~`item-999999`와 `demo`를 넣는다. 값은 1,024바이트 hex 문자열이다. 따라서 시드 재실행은 읽기 전용 점검이 아니다.
- 6단계 당시의 재현 조건은 Docker `mongo:7`, 루프백 `127.0.0.1:27018`, WiredTiger 캐시 0.25GB, 컨테이너 메모리 제한 1GB, 시드 후 및 측정 전 컨테이너 재시작이었다. 이전 결과가 현재 환경에 그대로 재현된다는 뜻은 아니다. Docker VM/OS 파일 캐시와 실제 디스크 읽기는 통제하지 않는다.
- **현재 측정기의 주의점:** MongoDB 상태 읽기·키 표본 생성 등 일부 초기 예외는 결과 JSON 생성 전에 종료할 수 있다. 진행률 이벤트는 제공하지 않는다. 예열과 300회 측정이 끝난 뒤 원자료·요약이 기록되므로 웹 화면은 측정 중 정확한 퍼센트나 조건별 실시간 수치를 보장할 수 없다. 이 사실은 로컬 서버의 오류·상태 설계에 반영해야 한다.

## 채택한 준비 범위와 실행 전제

- **채택한 범위:** 수동 터미널 준비를 시연의 필수 전제로 두지 않는다. 로컬 웹 화면/서버에 전용 준비 동작을 두어 Docker MongoDB 기동, 필요 시 시드 생성, 실행 전 재시작을 지원한다. 준비 실패와 준비 중 상태도 화면에서 확인한다. 시드 생성은 매 실행에 자동 반복하지 않는다.
- **안전 경계:** 준비 동작은 전용 컨테이너·고정된 로컬 설정만 대상으로 하며, 기존의 이름 충돌 컨테이너나 다른 DB/컬렉션을 임의로 삭제·덮어쓰지 않는다. **이번 준비에서 새로 만든 빈 전용 볼륨에만** 최초 시드를 자동 생성한다. 기존 데이터가 없거나 잘못됐을 때는 재생성의 삭제 영향을 명시한 **별도 확인 동작**을 거친다. 시드 점검·생성 중복 요청을 막는다. 구체적인 Docker 소유권·수명주기는 [설계](design.md)와 구현 전 TC에서 검증한다.

1. Python 실행 환경에 선택 의존성 `examples/requirements-mongo.txt`가 설치되고 Docker·MongoDB에 닿을 수 있어야 한다. 일반 제품 실행에는 이 의존성을 요구하지 않는다. 실행 서버는 Mongo URI를 브라우저 임의 입력으로 받지 않고 로컬 설정으로 고정한다.
2. 시드 확인은 **읽기 전용**으로 수행한다. 대상 DB·컬렉션의 문서 수 1,000,001개(`demo` 포함), `item-0`/`item-999999` 및 측정 키 표본의 예상 값과 저장 크기·캐시 한도를 확인한다. 문서 수만 맞는 기존 컬렉션을 정상 시드로 간주하지 않는다. 확인된 데이터 없음·값/건수 불일치만 `seed_required`로 안내한다. 연결·쿼리 실패는 검사 실패, 캐시/컨테이너 설정 불일치는 자원 실패, 저장 크기 하한 미달은 측정 조건 불충족으로 구별하며 시드 삭제를 해결책으로 안내하지 않는다. 저장 크기 하한 2배는 **7단계의 추가 기준으로 채택**했으며 6단계의 확정 조건으로 소급하지 않는다. 실제 환경에서 적정성 검증 후 필요한 경우 재검토한다.
3. 로컬 서버가 측정 요청에 앞서 **시드 값 검사 → 해당 실행의 MongoDB 재시작 → 기동·설정 확인**을 수행한다. 준비와 재시작은 측정 구간 밖이며, 실패하면 측정기를 시작하지 않는다. 재시작 뒤에는 문서 표본을 다시 읽어 캐시를 채우지 않는다. 측정기 자체가 재시작 뒤 MongoDB 메타데이터를 읽는 현재 경로는 유지한다. 재시작은 시드 생성이 아니며 브라우저 클릭마다 컬렉션을 지우지 않는다. 준비가 오래 걸리더라도 측정 시간과 혼동하지 않도록 준비 상태와 측정 실행 상태를 구분한다.
4. 각 실행은 고유 ID 및 별도 로컬 출력 경로를 가져 6단계 원자료와 이전 웹 실행을 덮어쓰지 않는다. 원자료·서버 로그는 자동 삭제하지 않으며 구체 경로·관리 방식은 [설계](design.md)에 따른다.

### 준비 작업과 자원 수명주기

1. `준비` 버튼은 Docker 사용 가능 여부를 확인하고, 시연용 고정 이름·식별 표지가 있는 전용 MongoDB 컨테이너만 생성/시작한다. `mongo:7`, 루프백 포트 `27018`, `--memory 1g`, `--wiredTigerCacheSizeGB 0.25`, **전용 이름 있는 볼륨**을 사용한다. 같은 이름의 표지 없는 컨테이너, 다른 서비스가 점유한 포트, 기존 볼륨/데이터의 소유권 불명은 충돌 오류로 보여주고 임의 삭제·강제 종료하지 않는다. 이미지 받기와 시드 생성은 시간이 걸릴 수 있으므로 준비 단계에서 따로 표시한다.
2. 시작 후 읽기 전용으로 시드를 검사한다. 정상 시드는 다시 생성하지 않고 `준비 완료`로 표시한다. **이번 요청으로 생성한 새 빈 전용 볼륨**은 최초 `seed_mongo.py` 실행까지 `준비`에 포함한다. 이미 있던 볼륨의 시드가 비어 있거나 불일치하면 자동 재생성하지 않고 `시드 재생성`을 별도 버튼으로 제공한다. 대상 컬렉션 삭제와 예상 규모(약 1GB)를 알려 확인을 받은 다음에만 실행한다. 시드 작업 중에는 측정을 받지 않는다. 완료 시 다시 검사하고 실패 시 불완전 상태와 로그를 남긴다. 임의 사용자 DB에 대해 실행할 수 없도록 서버가 URI/DB 이름을 고정한다.
3. `비교 실행`을 누를 때마다 준비 완료 여부와 시드 값을 재시작 **전에** 확인하고 전용 MongoDB를 한 번 재시작한다. 재시작 뒤에는 기동·설정만 확인하고 측정기를 호출하며 문서 표본을 다시 읽지 않는다. 재시작 전 시드 불일치 또는 재시작 뒤 기동·설정 확인 실패면 해당 실행은 `준비 실패`가 되고 성능 수치를 만들지 않는다. 재시작과 검사는 측정 구간 밖이며 준비와 측정이 겹치지 않게 한 작업만 허용한다.
4. **정리 버튼/API는 이번 단계에 넣지 않는다.** 화면을 닫거나 브라우저를 새로고침해도 Docker 컨테이너·볼륨·시드가 삭제되지는 않는다. 재시연 때 재시드를 피하도록 볼륨을 유지하고 서버 종료 시 전용 컨테이너·볼륨을 자동 중지·삭제하지 않는다. 자원이 남는다는 사실과 전용 자원의 안전한 수동 정리 방법을 화면·실행 안내에 명시한다. 다른 Docker 자원은 건드리지 않는다.

## 화면과 로컬 실행 서버의 계약

| 단계 | 화면에 보이는 내용 | 서버/원자료 대응 |
| --- | --- | --- |
| 준비 전·준비 중 | 전용 준비 동작, Docker/MongoDB 기동·시드 점검·새 전용 볼륨 최초 시드·기존 볼륨 재생성 확인의 상태 및 오류 안내 | 측정기와 별도 준비 작업. 기존 데이터 재생성 여부는 별도로 확인하고, `benchmark.py`의 측정 결과로 위장하지 않음 |
| 요청 수락 | 실행 버튼 비활성화, 실행 ID와 `대기/실행 중` 표시 | 같은 시점에는 실행 하나만 수락; 다른 요청은 `이미 실행 중`으로 거부하고 기존 실행을 덮지 않음 |
| 실행 중 | 경과 중이라는 상태만 표시. 퍼센트/조건별 측정값은 표시하지 않음 | 별도 프로세스 실행 및 상태 조회. 측정기는 진행 이벤트를 내지 않음 |
| 완료 | 해당 실행의 3조건 비교 그래프(중앙값 ms·P90 ms), 각 성공/실패 수, 예열 5회·측정 100회/조건, 키 분산·순차 실행·값 획득 타이머, MongoDB·캐시 조건과 실행 환경/시점 | 원자료 `results.json`의 `summary.no_cache/miss/hit.*` → HTTP 응답 `result.conditions.no_cache/miss/hit.{median_ms,p90_ms,successes,failures}`에 대응. `rounds`, `warmup_per_condition`, `timer`, `mongo_before/after`, `python`, `platform`, `sources_sha256` 및 사전 검사 범위/순서도 출력 경로/실행 ID로 연결. `mongo_after`가 오류 객체이면 수치는 숨기지 않고 사후 환경 정보 확인 불가를 밝힘 |
| 실패/중단 | 오류 단계·간단한 원인, 실패 수, 원자료가 있으면 원자료 경로/ID. **불완전 결과를 정상 비교 그래프로 표시하지 않음** | 비정상 종료/시간 초과/결과 파일 부재·손상/`aborted`/`summary.complete != true`를 실패로 분류. 남아 있는 원자료는 보존하고 실패 회차 및 서버 로그를 조사 가능하게 함 |

- 화면의 성공 판정은 프로세스 종료 코드 0 **및** 해당 실행 원자료의 `summary.complete == true`, 세 조건의 정상 집계, 측정기·자식 서버 회수 확인이 모두 필요하다. 회수 미확정이면 수치가 있어도 성공으로 표시하지 않고 새 작업을 차단한다. 오류를 0ms로 대체하거나 성공한 표본만의 중앙값을 전체 100회 완료 수치로 제시하지 않는다. 빈 결과/초기 오류는 실패 수를 임의 300으로 만들지 않는다.
- 준비 요청/상태 조회 → 측정 요청/상태 조회 → 결과 조회의 로컬 HTTP 계약을 둔다. 아래 URL·필드·오류 코드는 7단계의 채택된 상세 계약이다. 최소 구분은 `준비 중/실패`, `이미 실행 중`, `측정 중`, `성공`, `실패/시간 초과`, **회수 불확실 시 복구 필요**다. 준비·측정의 동시 실행은 막고, 회수 불확실 상태에서는 조회만 허용한다. 새로고침 후에도 같은 실행 ID로 상태를 다시 확인할 수 있어야 한다. 결과는 **그 실행의** 값만 보여주고 과거 6단계 값을 자동 혼합하지 않는다.
- 실행 서버와 화면은 루프백(`127.0.0.1`)에만 바인딩하고 임의 원격 주소·공개 배포를 지원하지 않는다. 로컬 페이지 이외의 웹사이트가 로컬 실행 요청을 유발하지 않도록 요청 출처/권한 경계를 설계·검증한다. 실행 요청은 고정된 측정 명령과 설정만 사용하고 임의 명령·출력 경로를 브라우저에서 받지 않는다.
- 유한한 전체 실행 시간 제한을 두고 초과 시 측정기와 자식 서버를 회수한다. 강제 종료 전에 정상 종료를 시도하며, 남은 프로세스·원자료 상태도 실패 결과에 남긴다. 기존 측정기의 자체 서버 종료만으로 외부 시간 제한의 자식 회수가 보장된다고 가정하지 않는다. 제한값과 프로세스 정리 방법은 설계·TC에서 검증한다.
- 결과 하단에는 **한 로컬 호스트의 순차 HTTP 전체 흐름 비교**임을 명시하고, OS/Docker 파일 캐시 및 동시 부하·원격 DB·디스크 I/O가 통제/측정되지 않았다는 한계를 함께 표시한다. 사전 시드 표본 읽기는 재시작 전이며 내부 캐시 재초기화 뒤에도 OS/Docker 파일 캐시에 영향이 남을 수 있다. 6단계와 동일한 캐시 상태라고 단정하지 않고 검사 키·범위·순서를 실행 기록과 연결한다. 시드·재시작·서버 기동·상태 준비·표시 시간은 측정 수치에 넣지 않는다.

### 요청·상태·오류 형식 (제품 HTTP API와 별개)

아래 경로와 JSON은 **7단계 로컬 시연 서버의 채택 계약**이다. 확정된 제품 API의 상태 코드/본문을 변경하지 않는다. 화면은 같은 로컬 서버에서 제공한다. 쓰기 요청에는 외부 사이트의 로컬 실행 유발을 막는 요청 출처 확인 및 서버 시작마다 보안 난수로 만든 토큰을 적용한다. `Host`·있는 경우 `Origin`은 실제 제공 주소 `127.0.0.1:<port>`만 허용한다(`localhost` 별칭 불허); CORS 허용 헤더는 보내지 않는다. 서버는 브라우저 입력으로 Docker 명령·Mongo URI·파일 경로를 받지 않는다.

| 요청 | 정상 응답 | 실패·중복 응답 |
| --- | --- | --- |
| `GET /api/setup` | `200`에 `state`(`not_ready|preparing|seed_required|ready|failed|recovery_required` 중 하나), `step`, `message`, `active_job`, `last_run_id`, 자원 상태; 준비 중에는 같은 상태를 조회 | Docker 미설치·접속/시드 오류를 분류; 회수 불확실 시 `recovery_required`와 복구 안내 |
| `POST /api/setup` (`{}` JSON) | 작업 의도 저장 성공 뒤 `202`와 위 준비 상태; 전용 컨테이너 생성/시작·시드 검사, 이번에 새로 만든 전용 빈 볼륨에는 최초 시드 생성 | 다른 준비·측정 작업 중 `409 BUSY`; 회수 불확실 시 `409 RECOVERY_REQUIRED`; 최초 기록 실패 `500 RECORD_UNAVAILABLE`(작업 미시작); Docker 자원 충돌은 수락된 준비 작업의 실패 상태로 보고 |
| `POST /api/setup/seed` (`{"confirm_replace":true}` JSON) | 작업 의도 저장 성공 뒤 `202` 준비 상태; 대상 컬렉션 삭제 후 시드 생성·재검사 | 확인 없으면 `400 CONFIRMATION_REQUIRED`; 작업 중 `409 BUSY`; 회수 불확실 시 `409 RECOVERY_REQUIRED`; 정상 시드·미확인 상태는 `409 SEED_NOT_REQUIRED`; 최초 기록 실패 `500 RECORD_UNAVAILABLE`; 자원 불일치는 수락 뒤 실패 상태 |
| `POST /api/runs` (`{}` JSON) | 작업 의도 저장 성공 뒤 `202 {"run_id":"…","state":"preparing"}`; 시드 검사·재시작 후 측정 시작 | 시드 미준비 `409 NOT_READY`, 다른 작업 중 `409 BUSY`, 회수 불확실 시 `409 RECOVERY_REQUIRED`, 최초 기록 실패 `500 RECORD_UNAVAILABLE`(실행 ID 미반환) |
| `GET /api/runs/{run_id}` | `200`에 `run_id`, `state`(`preparing|running|succeeded|failed|timed_out`), 시작/종료 시점, `step`, `error`(실패 시), `result`(성공 시) | 없는 ID는 `404 RUN_NOT_FOUND` |

모든 실패 본문은 예컨대 `{"error":{"code":"BUSY","message":"현재 준비 또는 측정 중입니다."}}`로 일관되게 표현한다. 상태 조회의 `failed`는 작업이 수락된 후 실패한 경우이고, 요청 단계의 `409` 등과 다르다. Docker 검사처럼 오래 걸리는 충돌 판정은 요청 수락 뒤 준비 작업의 실패로 보고한다. 오류 메시지에는 Mongo URI의 자격 정보나 임의 내부 경로·명령 전체를 노출하지 않는다. 초기 시드 오류처럼 측정기 결과 JSON이 생성되지 않은 실패도 서버가 기록하고 조회 가능하게 한다. 실행 ID는 추측하기 어려운 값으로 만들고, 실행별 원자료·작업 기록은 서버 재시작 뒤에도 같은 ID로 조회하도록 보존한다.

**작업 기록·복구 계약:** 같은 사용자·Docker 컨텍스트·고정 자원 이름을 쓰는 **모든 checkout**은 저장소 바깥의 동일한 잠금과 **공유 복구 기록**을 사용한다. 어느 checkout에서 시작하든 공유 기록의 미종결·미확정 작업을 먼저 확인하고 차단한다. 준비·시드·측정의 작업 ID·종류·미완료 의도와 복구에 필요한 신원을 checkout별 상세 기록뿐 아니라 공유 기록에도 Docker 조작/자식 프로세스 생성 **전에 내구 저장**하며, 어느 쪽이든 최초 기록 실패 시 시작하지 않는다. 시작 뒤 PID/PGID·시작 시각·작업 표지를 갱신한다. 이후 기록 실패, 손상·미종결 기록, 참조한 상세 기록의 접근 불가, 잔존/회수 불확실 시 `recovery_required`를 유지한다. 공유 기록이 처음부터 없으면 기존 전용 자원 부재를 읽기 전용으로 확인한 뒤에만 초기화한다. 작업 실패 종결이나 잠금 해제만으로 차단을 해제하지 않는다. 대상 작업과 자식 그룹의 신원·종료를 확인하고 **공유 기록 및 접근 가능한 상세 기록에 확인 결과를 내구 저장한 후** `not_ready`로 돌아간다. 식별·확인·해제 증거 저장이 불가능하면 조회만 허용하고 계속 차단한다. 화면의 안내 확인이나 서버 재시작은 복구 증거가 아니다. 수동 측정기와의 동시 사용은 운영상 금지한다. A checkout 중단 뒤 B checkout 시작, A 기록 접근 불가, 해제 증거 저장 실패는 구현 전 TC로 검증한다.

`succeeded.result`의 최소 표시 데이터는 `conditions`의 `no_cache/miss/hit` 각각에 `median_ms`, `p90_ms`, `successes`, `failures`를 두고, `environment`에 Python/OS·Mongo 설정·시드 크기·측정 시점, `method`에 5회 예열·100회 측정/조건·순차 키 분산·값 획득 구간을 둔다. 이 숫자는 **해당 실행의** 결과 JSON에서 읽어야 한다. `failed`/`timed_out`은 원자료 JSON이 파싱되고 표시할 수치·필드가 유효할 때만 실제 성공·실패 수를 `partial`로 표시하며 완결 비교 그래프를 만들지 않는다. 파일 존재만으로 수치를 만들지 않는다. 종료 코드 0의 손상·불완전 결과는 `RESULT_INVALID`, 시작 실패·비정상 종료·파일 부재는 `BENCHMARK_FAILED`, 제한 시간 초과는 `timed_out`으로 구분하며 회수 미확정은 준비 상태 `recovery_required`로 별도 차단한다. 서버는 출력 파일의 존재뿐 아니라 JSON 구조와 실행 ID별 경로, 종료 코드, `summary.complete`와 조건별 건수를 확인한다.

## 결정: 실행 환경 준비 책임

**B안 채택:** 전용 로컬 준비 명령/버튼에서 Docker 기동·필요 시 시드 생성·측정 전 재시작을 지원한다. 수동 준비를 필수로 요구하는 A안은 시연 운영이 오히려 복잡하다는 이유로 선택하지 않았다. **정리 버튼은 제외한다:** 화면을 닫을 때 사람이 버튼을 누르지 않을 수도 있으므로 정리를 보장하는 수단이 아니다. 이 두 범위 선택만으로 자동 삭제·보호 정책이 정해진 것은 아니었으며, 위 상세 계약은 이후 별도로 채택했다.

위 자원 정책·HTTP 형식은 **7단계 구현 기준으로 채택**했다. 자원 식별·중단/시간 초과 때 측정기 자식 서버까지 회수, 시드 재생성의 삭제 영향, 수동 볼륨 정리 안내, 로컬 페이지 외 요청 차단, 실행 ID와 원자료의 연결은 실제 구현·TC에서 확인할 항목이다. 준비/측정 실패·중복 클릭·서버 재시작을 검증할 TC를 구현 전에 작성한다. 유한 시간 제한의 제안 숫자는 [설계](design.md)의 잠정 시작값으로 채택하며 실제 실행 결과에 따라 조정할 수 있다. 설계 채택은 실행 검증 통과가 아니다.

# 7단계 구현 전 테스트 케이스 — 로컬 준비·실시간 성능 비교

- **상태:** 채택된 계약에 대한 구현 전 TC. 독립 계약 대응 검토에서 차단 지적 2건과 비차단 보완을 반영했으며, 수정본의 별도 재점검·테스트 코드·Docker 시연·측정 실행 결과는 아직 없다.
- **근거:** [D-0008](../../decisions/0008-live-benchmark-contract.md), [실행·화면 계약](execution-screen-contract.md), [설계](design.md), [7단계 개요](overview.md), [6단계 검증](../06-integration-performance/verification.md#3-성능-비교-실행), [산출물 가이드](../iteration-deliverables.md). 7단계의 별도 `REQ-07` 문서는 없으므로 새 ID를 소급해서 만들지 않는다. 아래 `계약` 칸의 절은 위 두 문서의 채택된 조항을 가리킨다.
- **유형:** `U`는 한 책임 경계의 단위 검증(가짜 Docker/DB/측정기·결과 파일 가능), `I`는 로컬 HTTP·작업 기록·프로세스·자원 연결 통합 검증, `E`는 실제 Docker MongoDB와 브라우저를 포함한 시연, `R`은 코드·증거 검토 전용(실행 TC 수에서 제외). 각 행의 기대값은 계획이며 통과 여부는 실제 실행 뒤 `verification.md`에 기록한다. 기존 1~6단계의 TC를 새 번호로 재판정하지 않는다.

## 공통 시험 전제와 격리

- 별도 언급이 없으면 **전용 시험 Docker 컨텍스트와 독립 출력·공유 기록 경로**에서 시작하고, 기존 사용자 컨테이너·볼륨·데이터를 정리 대상으로 삼지 않는다. 자원 충돌은 시험용 가짜 Docker 인터페이스 또는 격리된 명시적 시험 자원으로 만든다. `seed_mongo.py`의 실제 호출은 테스트용 신규 전용 볼륨이나 명시적으로 폐기 가능한 시험 컬렉션에만 허용한다. 재생성 버튼의 확인은 실제 데이터 삭제 승인과 다르므로 기존 데이터가 있는 호스트에서 무심코 실행하지 않는다.
- 상태/경합/기록 실패는 주입 가능한 파일 쓰기·프로세스·Docker 경계와 배리어를 사용한다. 요청의 도착 순서만으로 배타성을 주장하지 않고, 공유 잠금 취득, 양쪽 의도 내구 저장, Docker 조작/자식 생성, 회수 증거 저장의 순서를 관찰한다. `202`와 `500`은 이 순서의 실제 관측과 대조한다. 테스트 이중물의 통과는 실제 OS·Docker 동작의 증거가 아니므로 E 사례로 다시 확인한다.
- HTTP에서는 상태 코드·오류 `code`·JSON 값/타입·`Content-Type: application/json`·`Cache-Control: no-store`를 확인한다. 쓰기 요청은 실제 페이지의 시작별 토큰, `Host=127.0.0.1:<port>`, 같은 출처 `Origin`, `Content-Type: application/json`을 쓰며 `{}` 또는 명시한 확인 본문을 전송한다. 의도적 거부 요청은 한 조건씩 바꾼다. `GET /`은 HTML과 `frame-ancestors 'none'` CSP를 확인한다. 서버의 실제 리스닝 주소는 루프백만 허용한다.
- 결과 파일 시험은 **시험 실행 ID에 대응하는 경로**에 유효한 원자료를 생성한 뒤 한 필드씩 변형한다. 정상 원자료는 기존 `benchmark.py`의 구조(`command`, `summary`, `rounds`, `warmup_per_condition`, `aborted`, `mongo_before/after`, `records`, `warmup`, `timer`, `percentile`, `key_seed`, `key_space`, `sources_sha256` 등)를 따른다. 임의 JSON 스텁이나 파일 존재만으로 성공을 증명하지 않는다. 측정기의 코드/통계 규칙을 바꾸지 않는다.

**계약 대응 검토와 반영:** 별도 설계 검증 역할이 이 TC와 계약·설계의 직접 영향 경계를 대조해 **조건부**로 판정했다. 차단 지적은 I-003(c)의 중단 직후 `seed_required` 기대(복구 차단을 먼저 적용해야 함), I-016의 측정/시드 시간 초과·생성 실패를 섞은 기대였다. 위 행에서 복구 확인 전후와 작업별 결과를 분리했다. 기존 자원 충돌의 공유 기록 전제(I-002/003), 확인값 검사 순서(I-004), 초기화용 읽기 전용 확인(I-010), 유효 POST의 복구 우선(I-011~012), 엄격한 원자료 타입·경로 반례(U-004), 실제 ID 충돌 주입(I-015)도 보완했다. **수정본 전체의 별도 재점검이나 동작 검증을 뜻하지 않는다.**

**계획한 범위:** U 5개, I 17개, E 3개, R 3개(검토 전용). 구현 중에는 한 동작씩 테스트 RED→GREEN으로 연결하고, 실제 서버/DB/브라우저 결과와 장애 주입 방법·격리 조건·미실행/실패를 `verification.md`에 남긴다. 특히 E 사례의 Docker 사용과 시드 재생성은 안전한 시험 자원 확인 없이는 실행하지 않는다. 이 문서의 작성 자체는 구현·검증 완료가 아니다.

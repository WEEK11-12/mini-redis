## 이 단계의 문서 길잡이

`overview.md`는 이 단계의 상태와 문서로 가는 입구다. **요구사항 → 설계 → 구현 전 테스트 계획 → 실제 구현 → 실행·검토 결과**의 순서로 읽는다. 뒤 문서는 앞 문서의 기준을 따르며, 실행 결과 기록은 테스트 계획을 대신하지 않는다. 아직 작성하지 않은 파일은 빈 양식이나 유효하지 않은 링크로 만들지 않는다.

| 문서 | 역할·연결 관계 |
| --- | --- |
| [요구사항 명세 (`requirements.md`)](requirements.md) | 확정된 이번 범위와 인수 조건. D-0006을 따르며 실행 확인은 별도다. |
| [설계 문서 (`design.md`)](design.md) | TTL 설정·갱신·제거, 단조 시간 만료 판단, 순차 주기 정리·재시도 및 저장소·HTTP 경계. 독립 설계 검토와 보완 부분 초점 재확인 결과 포함. |
| 테스트 케이스 (`test-cases.md`; 작성 전) | 확정된 요구사항 ID와 설계 경계를 연결할 구현 전 단위·통합 검증 계획. 통과 결과가 아니다. |
| 구현 기록 (`implementation.md`; 작성 전) | 실제 코드 변경과 설계 대비 구현 선택·실행 방법. |
| 검증 기록 (`verification.md`; 작성 전) | 실제 실행 명령·조건·결과와 검토 범위, 미실행 항목. |

전체 단계의 현재 위치는 [진행 현황](../../plans/progress.md), 단계별 파일 형식의 공통 기준은 [산출물 가이드](../../plans/iteration-deliverables.md)를 참고한다.

## 진행 체크리스트

[공통 진행 순서](../../plans/implementation-units.md#진행-체크리스트)에 맞춰 **요구사항 명세 → 설계 → 설계 검토 → 구현 전 TC → 구현 → 테스트·결과 확인** 순서로 관리한다. 아래 항목은 아직 완료 증거가 아니며, 해당 문서를 작성·검토하거나 실행한 뒤에만 체크한다.

- [x] [요구사항 명세 (`requirements.md`)](requirements.md)의 TTL·무효화 입력 계약과 인수 조건을 확인해 범위를 확정한다. (실행 인수 확인은 별도)
- [x] 채택한 무효화 계약을 바탕으로 TTL 설정·갱신·제거의 HTTP 경로·응답, 만료 판단·정리 시점과 저장소·HTTP 경계를 [설계 문서](design.md)에 정한다. 기존 `PUT` 본문과 공유 HTTP 응답 계약은 유지한다.
- [x] 설계를 요구사항·기존 저장소 공개 연산·D-0003의 만료 응답 계약과 대조해 독립 검토한다. 차단 발견 없음, 비차단 보완 부분의 초점 재확인 완료. ([설계 문서](design.md#6-검증-지점과-구현-위임))
- [ ] 구현 전에 만료 직전·직후, 없는 키, 무효화 후 재조회, 기존 값과 덮어쓰기의 경계를 요구사항 ID와 연결해 테스트 케이스 (`test-cases.md`; 작성 전)에 기록한다. (목록 작성과 테스트 통과는 별개)
- [ ] 확정된 계약에 맞춰 저장소·HTTP 연결부를 구현하고 실제 변경을 구현 기록 (`implementation.md`; 작성 전)에 남긴다.
- [ ] 제어 가능한 시간 조건의 단위 테스트, 실제 저장소를 사용하는 HTTP 통합 테스트와 기존 회귀 테스트를 실행하고 명령·조건·결과를 검증 기록 (`verification.md`; 작성 전)에 남긴다.
- [ ] 남은 위험·후속 동시성 검토의 선행 조건을 확인하고 [진행 현황](../../plans/progress.md)을 갱신한다.

## 목표와 범위

보관 기간이 지난 키를 유효한 값처럼 반환하지 않고, 명시적 무효화 이후에도 오래된 값을 재사용하지 않도록 한다. 기존 `HashTableStore`와 HTTP 경로에 이 동작을 연결하는 것이 이번 단위의 목표다. [D-0003](../../decisions/0003-http-response-contract.md)에 따라 만료 키의 조회는 `404 KEY_NOT_FOUND`, 존재 확인은 `200`·`{"exists": false}`, 삭제는 `200`·`{"deleted": false}`다. 이 외부 응답 계약은 이미 채택됐지만 실제 만료 동작은 아직 구현·검증되지 않았다.

TTL은 기존 `PUT`과 별도 연산으로 설정·갱신·제거하고 양의 정수 초만 허용한다. 일반 `PUT`은 기존 TTL을 해제하며, 명시적 키 단위 무효화는 기존 `DELETE`를 따른다([D-0006](../../decisions/0006-ttl-invalidation-contract.md)). 별도 `/keys/{key}/ttl` 요청의 경로·본문·응답, 단조 시간의 만료 경계, 접근 시 및 순차 주기 정리는 [설계](design.md)에 정했다. 동시성 위험 점검·방어는 5단계, 전체 종단 간 검증과 캐시 사용·미사용 성능 비교는 6단계다. Optional 영속성은 이번 범위에 포함하지 않는다.

## 1. 요구사항 명세 — 범위 확인 완료

이번 단위의 `REQ-04-001`~`REQ-04-006`과 인수 조건은 [4단계 요구사항 명세서](requirements.md)에 유지한다. 과제의 만료·무효화 요구와 D-0003의 만료 응답, [D-0006의 채택 계약](../../decisions/0006-ttl-invalidation-contract.md)을 반영했다. 범위 확정과 실제 인수 조건 통과는 별개다. 전체 단위 명세는 [요구사항 색인](../README.md)에서 찾는다.

## 2. 설계 — 계약 작성 완료

[설계 문서](design.md)는 기존 값 `PUT`을 바꾸지 않고 TTL 전용 경로에 JSON 객체로 양의 정수 초를 설정·갱신하거나 TTL만 제거하는 계약을 정한다. 저장소가 단조 시간으로 기한을 판단하고 서버의 기존 순차 실행 스레드가 요청 사이 고정 1초 목표 간격으로 정리하며, 정리 실패는 다음 주기에 재시도한다. 1초는 성능상 최적값으로 검증된 수치가 아니다. 값·기한 소유권, 만료 키의 미존재 처리와 동기 오류의 상태 보존 범위는 해당 문서에 둔다.

## 3. 설계 검토 — 완료

설계 검증 에이전트의 독립 검토에서 요구사항·기존 HTTP 계약, 만료 경계·실패 불변조건, 순차 서버의 유휴 정리 가능성, 라우팅·도식에 **구현 착수를 막는 확정 설계 오류는 발견되지 않았다**. 큰 정수 TTL의 HTTP 파싱, 정리 콜백의 예외 격리·다음 시도 시점, 경로 회귀 TC에 대한 비차단 의견을 [설계 문서](design.md#6-검증-지점과-구현-위임)에 반영했다. 해당 보완의 초점 재확인에서 세 의견은 문서상 해소됐고 새 직접 충돌은 발견되지 않았다. 이는 전체 구현·테스트의 승인이나 실행 결과가 아니다.

## 4. 구현 — 미착수

구현 범위와 파일 경로는 설계·TC 확정 후 정하고 실제 변경만 구현 기록 (`implementation.md`; 작성 전)에 남긴다. 기존 2·3단계의 구현 완료를 4단계의 기능 완료로 간주하지 않는다.

## 5. 테스트·결과 확인 — 미실시

구현 전 계획은 테스트 케이스 (`test-cases.md`; 작성 전)에, 실제 실행과 독립 검토 결과는 검증 기록 (`verification.md`; 작성 전)에 분리한다. 가능하면 제어 가능한 시간원으로 경계 시각을 검증하고 실제 저장소와 HTTP 요청을 연결해 확인한다.

| 검증 대상 | 실행 시 확인할 관찰 결과 |
| --- | --- |
| 만료 경계 | 만료 직전·직후의 조회 결과가 확정된 시간 규칙과 일치하고 만료 값이 반환되지 않는다. |
| 기존 HTTP 응답 | 만료 키의 조회·존재 확인·삭제가 D-0003의 미존재 응답과 일치한다. |
| 명시적 무효화 | 선택한 방식으로 무효화한 뒤 재조회에서 오래된 값이 나오지 않으며, 없는 키의 결과도 확정된 계약과 일치한다. |
| 덮어쓰기·회귀 | 만료 전후 같은 키를 다시 저장해도 옛 만료 정보가 새 값을 잘못 무효화하지 않고 기존 저장소·HTTP 동작이 유지된다. |

## 다음 확인 지점

[요구사항 명세](requirements.md)와 [검토된 설계 계약](design.md)을 연결해 구현 전 `test-cases.md`를 작성한다. 특히 만료 경계, 큰 정수 TTL 입력, 유휴 정리와 한 차례 실패 후 다음 주기 재시도, 기존 2·3단계 회귀를 포함한다. 현재는 4단계 TC·구현·실행 검증 결과가 없다.

# 4단계 테스트 케이스 — 만료와 명시적 무효화

- 상태: 구현 전 TC 목록; 테스트 코드·실행 결과 아님
- 근거: [요구사항](requirements.md), [설계](design.md), [D-0006](../../decisions/0006-ttl-invalidation-contract.md), [3단계 HTTP 경계](../03-http-api/design.md#2-기본-http-인터페이스와-입력-계약), [산출물 가이드](../iteration-deliverables.md)
- 유형: `U`는 `HashTableStore` 단위, `I`는 실제 저장소를 연결한 HTTP/서버 통합. 요구사항 칸의 축약 번호도 `REQ-04-`를 뜻한다(예: `REQ-04-001, 002` → `REQ-04-001`, `REQ-04-002`). 각 행의 번호는 향후 테스트 구현과 검증 기록에서 유지한다. 아직 함수명·보조 훅·실행 명령은 확정하지 않는다. 특별한 언급이 없으면 새 저장소/서버에서 시작하며, 시간 테스트에는 저장소에 공급하는 정수 나노초 단조 시간원을 제어한다. 기준 시각 `t`, TTL `n`초의 기한은 `t + n × 10⁹` ns다. 서버 루프 주기 관찰은 저장소 시간원과 별개일 수 있으므로 실제 주기/제어 가능한 서버 시간 조건을 명시해 검증한다.

## 코드 검토·실행 범위

- 테스트 코드 대응: `TC-04-U-001~014` → `tests/test_expiration_store.py`의 `test_u_001~014`, `TC-04-I-001~015` → `tests/test_expiration_http.py`의 `test_i_001~015`. 검토 지적에 대응한 카운터 실패 회귀 `test_counter_failure_does_not_commit_expired_or_direct_removal`는 별도 보완 테스트다. `clock`, `_remove_expired`, `_replace`는 실제 구현의 시험 접점으로 사용했지만 공개 계약은 아니다. 실행·독립 판정은 [검증 기록](verification.md)에 분리한다.
- 별도 실행 단언으로 연결되지 않은 세부 조건: I-013의 요청·정리 비중첩 및 지연 주기의 보상 호출 없음, I-014의 진단 출력 실패·실패 기록과 다음 주기 재시도는 기존 공식 테스트가 전부 단언하지 않는다. 독립 보완 계측에서 확인한 결과와 한계는 [검증 기록](verification.md)에 남겼다. 실행 TC 수만으로 이 조건까지 통과했다고 판정하지 않는다.
- `REQ-04-005` 코드 검토(실행 TC 수에 포함하지 않음): HTTP가 버킷을 직접 다루지 않고 저장소 공개 연산만 호출하는지, 기존 키·값·본문 계약과 순차 `HTTPServer`를 유지하는지 확인한다. 서버 루프의 정리는 요청 사이에서만 실행되며 독립 작업 스레드가 없고, 종료 시 더 실행되지 않는지도 확인한다. 근거는 구현 후 `mini_redis/store.py`, `mini_redis/http_api.py`의 실제 변경 경로와 서버 수명 처리에 남긴다.
- 실패 주입/호출·본문 읽기 관찰에 필요한 내부 접점은 **임시 시험 접점**이다. 메서드 이름·보조 도구·정리 진단 출력의 형식은 공개 계약으로 고정하지 않는다. 정확히 1초에 정리가 완료될 것, 저장과 TTL 설정의 두 HTTP 요청이 원자적일 것, 서버 재시작 후 데이터 복구, 동시성 방어, 전체 성능 우위는 이번 인수 범위가 아니다.
- 각 TC의 테스트 코드 대응과 실행 명령·환경·실제 결과·미실행은 구현 후 `verification.md`에 기록한다. 이 목록은 실행 성공 또는 독립 승인 증거가 아니다.

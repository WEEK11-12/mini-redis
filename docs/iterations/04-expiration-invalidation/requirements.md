# 4단계 요구사항 명세서 — 만료와 명시적 무효화

- 상태: 4단계 범위·인수 조건 확정 — 구현·실행 및 제한 독립 재검토 결과는 [검증 기록](verification.md) 참조
- 적용 범위: 기존 해시 테이블 저장소와 HTTP 사용 경로에서 보관 기간 만료 및 명시적 무효화의 동작을 제공·검증한다. 동시성 방어(5단계), 전체 종단 간·성능 비교(6단계), Optional 영속성은 이번 인수 범위가 아니다.
- 근거: [과제 원문](../../assignment.md), [1단계 공유 계약](../01-scope-and-contract/overview.md), [D-0003 기본 HTTP 계약](../../decisions/0003-http-response-contract.md), [D-0005 HTTP 경계](../../decisions/0005-http-api-boundary.md), [D-0006 TTL·무효화 계약](../../decisions/0006-ttl-invalidation-contract.md), [2단계 저장소 요구사항](../02-hash-table/requirements.md), [3단계 HTTP 요구사항](../03-http-api/requirements.md), [4단계 개요](overview.md), [구현 단위 가이드](../../plans/implementation-units.md)

## 식별·상태

- ID는 `REQ-04-001`처럼 단계 번호와 일련번호로 고정한다. **명세**는 기대 동작, **인수 조건**은 나중에 실행으로 확인할 기준이다. 범위 확정은 구현·테스트 통과의 증거가 아니다.
- [D-0006](../../decisions/0006-ttl-invalidation-contract.md)에 따라 기존 `PUT` 본문은 문자열 `value` 필드 하나만 허용한다. TTL은 별도 연산으로 설정·갱신·제거한다. 구체적인 경로·메서드·응답과 만료 시각 계산·물리적 정리는 설계에서 정한다.
- 구현 전 TC 목록은 설계 검토 후 [테스트 케이스](test-cases.md)에 기록했다. 실제 변경과 실행 결과는 각각 [구현 기록](implementation.md)·[검증 기록](verification.md)에 남겼다. [단계별 산출물 가이드](../../plans/iteration-deliverables.md)를 따른다.

## 기능 요구사항

### REQ-04-001 — 보관 기간을 지정할 수 있는 캐시

- **명세:** 외부에서 기존 `PUT`과 별개의 연산으로 키의 보관 기간을 설정한다. TTL은 양의 정수 초만 허용하며 `0`·음수·분수는 잘못된 입력으로 거부하고 기존 상태를 유지한다. 유효한 키·문자열 값(빈 문자열 포함)과 기존 `PUT`의 `value` 한 필드 계약은 그대로다. 별도 TTL 연산의 경로·메서드·본문과 실패 응답은 설계에서 정한다.
- **인수 조건:** 저장된 키에 별도 연산으로 TTL을 지정하면 유효 기간 안에는 값(빈 문자열 포함)이 조회되고 지정한 기간이 지난 뒤에는 `REQ-04-002`의 미존재 결과가 된다. 양의 정수 초가 아닌 TTL 입력은 거부되며 기존 값·만료 상태가 바뀌지 않는다. 기존 `PUT /keys/{key}`는 TTL 필드를 허용하지 않고, TTL 없는 저장은 만료되지 않는다. 저장과 TTL 설정은 두 HTTP 요청 사이의 원자성을 보장하지 않는다.
- **근거:** [과제 원문 만료 항목](../../assignment.md#중점-포인트), [구현 단위 가이드 4단계](../../plans/implementation-units.md#4-만료와-명시적-무효화), [D-0005 PUT 본문 제약](../../decisions/0005-http-api-boundary.md#결정과-이유), [D-0006 TTL 입력 계약](../../decisions/0006-ttl-invalidation-contract.md#결정과-이유).

### REQ-04-002 — 만료 키의 조회·존재 확인·삭제

- **명세:** 만료된 키는 값을 반환하지 않으며 외부에서는 없는 키와 동일하게 다룬다. `GET /keys/{key}`는 `404`·`{"error": {"code": "KEY_NOT_FOUND"}}`, `GET /keys/{key}/exists`는 `200`·`{"exists": false}`, `DELETE /keys/{key}`는 `200`·`{"deleted": false}`다. 유효한 빈 문자열 값은 만료 전까지 존재하는 값이다. 기존 HTTP 최종 응답의 `Cache-Control: no-store` 계약을 유지한다.
- **인수 조건:** 제어된 시간 조건에서 만료 전의 조회·존재 확인은 유효한 값·`true`를, 만료된 뒤의 조회·존재 확인·삭제는 위의 상태·본문을 반환한다. 같은 시각의 경계 포함 여부와 내부 물리적 제거 시점은 설계에서 정해 TC로 확인한다. 빈 값의 만료와 원래 없던 키를 외부에서 동일하게 취급하되, 만료 전 빈 값은 `200`·`{"value": ""}`로 구별한다.
- **근거:** [D-0003 기본 연산·만료 응답](../../decisions/0003-http-response-contract.md#결정), [REQ-02-002 조회 구분](../02-hash-table/requirements.md#req-02-002--조회-결과-구분), [REQ-03-002~004](../03-http-api/requirements.md#req-03-002--조회미존재-구별).

### REQ-04-003 — 같은 키의 변경과 만료 상태

- **명세:** 같은 키에 TTL 없이 기존 `PUT`으로 다시 저장하면 이전 TTL을 해제하고 최신 값으로 덮어쓴다. 별도 연산으로 기존 TTL을 갱신하거나 TTL만 제거할 수 있으며, TTL만 제거할 때 값은 유지한다. 만료 후 같은 키를 재저장해도 이전 값·만료 정보가 새 값에 적용되지 않는다. 별도 연산의 경로·메서드·응답은 설계에서 정한다.
- **인수 조건:** TTL이 있는 키에 일반 `PUT`을 한 뒤 옛 만료 시각이 지나도 최신 값이 조회된다. TTL 갱신 후에는 새 보관 기간에 맞게 만료되고, TTL만 제거한 뒤에는 값이 그대로 조회되며 이전 TTL 시각에도 사라지지 않는다. 만료 후 같은 키를 재저장한 경우 예전 값은 재출현하지 않는다.
- **근거:** [REQ-02-001 저장·덮어쓰기](../02-hash-table/requirements.md#req-02-001--저장과-덮어쓰기), [REQ-03-001 HTTP 저장·덮어쓰기](../03-http-api/requirements.md#req-03-001--저장덮어쓰기의-외부-호출), [D-0006 TTL 변경 계약](../../decisions/0006-ttl-invalidation-contract.md#결정과-이유).

### REQ-04-004 — 명시적 무효화

- **명세:** 키 단위 명시적 무효화는 기존 `DELETE /keys/{key}`로 수행하며 별도 무효화 API는 추가하지 않는다. 유효한 키를 삭제하면 `200`·`{"deleted": true}`, 없는 키·이미 만료된 키는 `200`·`{"deleted": false}`다.
- **인수 조건:** 유효한 키를 `DELETE`한 뒤 조회는 `404 KEY_NOT_FOUND`, 존재 확인은 `200`·`{"exists": false}`다. 없는 키·만료 키의 삭제는 `false`이고 다른 키의 값은 유지된다. 삭제된 옛 값은 다시 나타나지 않는다.
- **근거:** [과제 원문 무효화 항목](../../assignment.md#중점-포인트), [D-0003 DELETE·만료 결과](../../decisions/0003-http-response-contract.md#결정), [D-0006 무효화 결정](../../decisions/0006-ttl-invalidation-contract.md#결정과-이유), [REQ-02-004 저장소 삭제](../02-hash-table/requirements.md#req-02-004--삭제), [REQ-03-004 HTTP 삭제](../03-http-api/requirements.md#req-03-004--삭제).

## 연결·검증 요구사항

### REQ-04-005 — 기존 책임 경계와 계약 유지

- **명세:** TTL·무효화 동작은 기존의 직접 구현한 저장소와 HTTP 처리부의 연결을 통해 제공한다. HTTP 계층은 버킷을 직접 조작하지 않고, 기존 키·값 제한과 최종 HTTP 응답의 `Cache-Control: no-store`를 유지한다. 기존 `PUT` 본문·라우팅을 바꾸지 않는다.
- **인수 조건:** 코드 검토에서 저장소 공개 경계를 통한 연산과 기존 저장소 사용을 확인한다. TTL 없는 기존 저장·조회·존재 확인·삭제, 빈 값, 오류·응답 헤더의 회귀 결과가 기록된다. 새로운 TTL 입력이 잘못됐을 때 성공 응답이나 기존 값·TTL 상태 손상으로 둔갑하지 않는다.
- **근거:** [1단계 책임 경계](../01-scope-and-contract/overview.md#확인된-공유-계약과-책임-경계), [D-0005 HTTP 경계](../../decisions/0005-http-api-boundary.md#결정과-이유), [REQ-03-006 응답 헤더](../03-http-api/requirements.md#req-03-006--http-응답의-캐시-방지), [REQ-03-008 저장소 연결](../03-http-api/requirements.md#req-03-008--저장소-연결과-통합-검증).

### REQ-04-006 — 만료·무효화 검증

- **명세:** 확정된 만료·무효화 동작의 경계와 상태 변경은 저장소 단위 테스트 및 실제 저장소를 이용하는 HTTP 통합 테스트로 확인하고 기존 2·3단계 회귀를 유지한다.
- **인수 조건:** 만료 직전·직후, 원래 없는 키, 빈 값, 무효화 후 재조회, 같은 키의 변경·재저장에 대응하는 TC를 작성하고 실행 명령·조건·실제 결과를 기록한다. 시간 의존 검증은 가능하면 제어 가능한 시간원을 사용한다. 미실행 항목은 통과로 적지 않는다.
- **근거:** [과제 원문 품질 항목](../../assignment.md#품질), [구현 단위 가이드 4단계](../../plans/implementation-units.md#4-만료와-명시적-무효화), [산출물 가이드의 테스트 경계](../../plans/iteration-deliverables.md#단계에-따른-테스트-경계).

## 확정된 범위와 설계에 남긴 선택

기존 `PUT`과 별도 TTL 설정·갱신·제거, 양의 정수 초 입력, 일반 `PUT`의 TTL 해제, 기존 `DELETE`를 통한 키 단위 무효화는 [D-0006](../../decisions/0006-ttl-invalidation-contract.md)에 채택했다. 별도 TTL 연산의 정확한 HTTP 경로·메서드·본문·성공/오류 응답(없는 키 포함), 시간원 종류·만료 시각 경계, 만료 항목의 물리적 정리 방식과 내부 자료 표현은 설계에서 정한다. 값 저장과 TTL 설정의 두 요청 간 원자성은 이번 계약에서 보장하지 않는다. 원자성이 필요한 사용 사례가 확인되면 이 계약을 재검토한다.

# 3단계 테스트 케이스 — HTTP 연결과 API 응답 재사용

- 상태: 구현 전 검증 계획 — `tests/test_http_api.py`에 임시 실행 접점의 테스트 코드 작성, 제품 동작 검증 전
- 근거: [요구사항](requirements.md), [설계](design.md), [D-0003](../../decisions/0003-http-response-contract.md), [D-0005](../../decisions/0005-http-api-boundary.md), [산출물 가이드](../../plans/iteration-deliverables.md)
- 유형: `I`는 외부 HTTP 요청과 실제 `HashTableStore`의 통합 검증, `E`는 별도 로컬 원본 API·Mini Redis·one-shot 클라이언트의 사용 사례. 별도 명시가 없으면 새 서버의 빈 저장소에서 시작한다. I-011·014·015·017·018·020과 I-021의 실패 PUT은 대상 키에 정상 PUT으로 구별 가능한 기존 값을 먼저 저장하고, 거부·실패 후 새 연결의 GET으로 동일 값을 확인한다. 응답 본문은 명시한 JSON 구조와 값으로 비교한다. `tests/test_http_api.py`의 `test_i_###`·`test_e_###`가 각각 같은 번호의 TC에 대응한다. 서버의 파일·실행 명령이 설계에서 미확정이므로 테스트 파일 상단의 모듈·팩터리·CLI 접점은 **임시 가정**이며 실제 구현에서 맞춘다. 실행 결과와 TC별 코드·명령은 구현 후 `verification.md`에 기록한다.

## 코드 검토·기존 회귀와 범위

- `REQ-03-008` 코드 검토: HTTP 처리부가 `HashTableStore.set/get/exists/delete`만 사용하고 버킷을 직접 조작하거나 다른 핵심 키-값 저장소로 대체하지 않는지 확인한다. 원본 API·클라이언트가 Mini Redis와 다른 프로세스인지, 클라이언트가 저장소 내부를 직접 쓰지 않는지도 확인한다. 이는 HTTP 응답만으로 증명하지 않는다.
- `REQ-03-008` 회귀: 기존 [2단계 저장소 단위 TC](../02-hash-table/test-cases.md)를 재실행하되 여기서 새 3단계 TC로 재번호화하지 않는다. 실행 명령·환경·실제 결과는 `verification.md`에 분리해 기록한다.
- 결함 주입·저장소 호출 관찰을 위한 구현 내부 접점은 **임시 테스트 접점**이며 공개 API 계약이 아니다. 파싱 전에 서버가 거부한 요청과 중간 계층이 정규화한 점 경로의 원래 응답은 인수 보장 밖이다. TTL·무효화, 동시성 방어, 영속성, 성능 비교는 후속 단계 범위다.
- 테스트 코드의 I-008의 별도 키 길이 제한 부재와 `REQ-03-008`의 버킷 비조작·실제 단일 스레드 구조는 코드 검토 항목이다. I-019는 짧은 본문의 EOF 경로를 작성했으며 **읽기 타임아웃 경로는 초 값 확정 후 별도 확인**한다. E-004의 미정의 데이터 ID는 고정 ID one-shot CLI의 외부 입력이 아니므로 원본 구현의 처리만 검토한다. 실제 본문별 하위 사례·소켓 동작은 제품 구현 후 검증한다.

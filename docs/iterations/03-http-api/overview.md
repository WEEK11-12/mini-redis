## 이 단계의 문서 길잡이

`overview.md`는 이 단계의 상태와 문서로 가는 입구다. **요구사항 → 설계 → 구현 전 테스트 계획 → 실제 구현 → 실행·검토 결과**의 순서로 읽는다. 뒤 문서는 앞 문서의 기준을 따르며, 실행 결과 기록은 테스트 계획을 대신하지 않는다. 작성 전인 결과 파일은 빈 양식으로 만들지 않는다.

| 문서 | 역할·연결 관계 |
| --- | --- |
| [요구사항 명세 (`requirements.md`)](requirements.md) | 확정된 이번 범위와 인수 조건. 1단계 공유 계약과 D-0005를 따른다. 실행 인수 확인은 별도다. |
| [설계 문서 (`design.md`)](design.md) | 요구사항에 대응하는 HTTP·저장소 연결, 키·오류·예시 흐름과 선택 근거. 독립 설계 검토의 지적을 반영했다. |
| [테스트 케이스 (`test-cases.md`)](test-cases.md) | 요구사항 ID와 설계 경계를 연결한 구현 전 검증 계획. 테스트 코드·통과 결과와 구분한다. |
| [구현 기록 (`implementation.md`)](implementation.md) | 실제 코드와 설계 대비 구현 선택·실행 방법. |

전체 단계의 현재 위치는 [진행 현황](../../plans/progress.md), 단계별 파일 형식의 공통 기준은 [산출물 가이드](../../plans/iteration-deliverables.md)를 참고한다.

## 진행 체크리스트

[공통 진행 순서](../../plans/implementation-units.md#진행-체크리스트)에 맞춰 **요구사항 명세 → 설계 → 설계 검토 → 구현 전 TC → 구현 → 테스트·결과 확인** 순서로 관리한다. 설계 완료는 구현이나 인수 조건의 실행 검증을 뜻하지 않는다.

- [x] [요구사항 명세 (`requirements.md`)](requirements.md)의 목표·범위와 관찰 가능한 완료 조건을 확인한다. (실행 인수 확인은 별도)
- [x] 키의 URL 표현·입력 검증·오류 매핑·HTTP 실행 구조 및 API 응답 재사용 사례를 [설계 문서 (`design.md`)](design.md)에 확정한다. (공통 HTTP 경계는 [D-0005](../../decisions/0005-http-api-boundary.md), 단계별 예시는 설계 문서 4절)
- [x] 설계가 D-0003과 저장소 공개 계약을 충족하는지 독립 검토하고 지적된 전송 경계를 반영한다. ([설계 검토 결과](design.md#8-설계-검토-결과와-구현에-위임한-부분); 구현 결과 검토 아님)
- [x] 구현 전에 실제 저장소를 사용하는 HTTP 통합 TC와 API 응답 재사용 경로를 요구사항 ID에 연결해 [테스트 케이스 (`test-cases.md`)](test-cases.md)에 기록한다. (목록 작성만 완료)
- [x] HTTP 처리부·사용 사례를 구현하고 실제 변경을 [구현 기록 (`implementation.md`)](implementation.md)에 남긴다.
- [x] 수정 요청 3건을 반영하고 영향 범위 9개·독립 probe 8개를 확인했다. 이후 최신 HTTP 32개와 저장소 24개를 독립 실행해 3단계 범위를 승인받았다 ([검증 기록 (`verification.md`)](verification.md)).
- [x] 고정 포트 수동 시연은 미실시로 남기고 TTL·무효화(4단계), 동시성(5단계), 성능 비교(6단계)를 [진행 현황](../../plans/progress.md)에 분리했다.

## 목표와 범위

직접 구현한 `HashTableStore`를 HTTP 처리부와 연결해 외부에서 저장·조회·존재 확인·삭제를 호출할 수 있게 한다. 간단한 원본 API의 응답을 Mini Redis에 저장하고 다음 요청에서 재사용하는 사례를 실제 요청으로 확인한다. HTTP 처리부는 저장소의 공개 연산만 호출하고 버킷 내부를 직접 조작하지 않는다. 이번 범위와 인수 조건은 [3단계 요구사항 명세](requirements.md)에서 확인했다.

[D-0003](../../decisions/0003-http-response-contract.md)의 기본 응답, [D-0004](../../decisions/0004-http-key-no-slash.md)의 슬래시 제외, [D-0005](../../decisions/0005-http-api-boundary.md)의 추가 키·라우팅·본문 경계가 공유 기준이다. 원본 API 예시는 [설계 문서 4절](design.md#4-외부-사용-예제의-흐름과-실패)에 둔다. TTL 설정과 실제 만료·무효화는 4단계, 동시성 위험 점검·방어는 5단계, 캐시 사용·미사용 성능 비교와 전체 종단 간 검증은 6단계에서 다룬다. 이 후속 동작을 이번 단계에서 검증한 것으로 표시하지 않는다.

## 1. 요구사항 명세 — 범위 확인 완료

이번 단위의 요구사항·고정 ID·인수 조건은 별도 [3단계 요구사항 명세서](requirements.md)에만 유지한다. `REQ-03-001`~`REQ-03-008`은 외부 저장·조회·존재 확인·삭제, 입력·내부 오류 구별, 응답 캐시 방지, 원본 API 응답 재사용, 실제 저장소 연결·통합 검증을 다룬다. D-0005의 추가 HTTP 경계와 이 단계의 예시 관찰 방식을 반영했다. 범위 확정과 실행을 통한 인수 확인은 별개다. 전체 단위의 명세는 [요구사항 색인](../README.md)에서 찾는다.

## 2. 설계 — 문서 작성·계약 확정 완료

구조와 선택 근거는 [설계 문서](design.md)에 유지한다. 단일 프로세스의 순차 `HTTPServer`, 저장소 공개 연산과 HTTP 처리부의 분리, 제한된 HTTP 키·라우팅과 엄격한 `PUT` 입력, Mini Redis 밖의 로컬 원본 API·one-shot 클라이언트의 재사용 경로를 정했다. 공통 HTTP 경계는 [D-0005](../../decisions/0005-http-api-boundary.md)에 기록했고 원본 API 예시의 선택은 [설계 문서 4절](design.md#4-외부-사용-예제의-흐름과-실패)에 유지한다. 구현 파일 배치·포트·구체적인 타임아웃 값은 구현에 위임한다.

## 3. 설계 검토 — 문서 계약 검토 완료

[D-0003](../../decisions/0003-http-response-contract.md)의 기본 연산·오류 응답과 2단계 저장소 공개 계약을 대상으로 독립 검토했다. 구조 재설계를 요구하는 확정 차단 결함은 발견되지 않았고 `HEAD` 응답의 본문 생략, 중복·비정상 `Content-Length` 거부를 [설계 문서](design.md#8-설계-검토-결과와-구현에-위임한-부분)에 반영했다. 표준 HTTP 핸들러의 미지원 메서드 기본 응답과 원시 경로·연결 경계는 구현 전 TC와 실제 요청에서 확인해야 한다. 문서 계약 검토는 구현·테스트 승인 범위가 아니다.

## 4. 구현 — 3단계 범위 승인

HTTP 처리부와 별도 원본 API·one-shot 클라이언트를 구현했다. 변경 경로·실행 방법은 [구현 기록 (`implementation.md`)](implementation.md)에 있다. 구현자 확인은 최종 인수 판정이 아니다.

## 5. 테스트·결과 확인 — 최신 공식 테스트·독립 검토 통과

구현 전 TC와 테스트 코드는 [테스트 케이스 (`test-cases.md`)](test-cases.md)에 연결된다. 독립 검토의 수정 요청 3건을 반영한 최신 리비전에서 HTTP 32개·저장소 24개를 검증 담당이 실행해 모두 통과했고 3단계 범위를 승인했다. 명령·조건·제외 범위는 [검증 기록 (`verification.md`)](verification.md)에 있다.

| 검증 대상 | 실행 시 확인할 관찰 결과 |
| --- | --- |
| 저장·조회·존재 확인·삭제 | 외부 요청의 결과가 D-0003의 상태·본문과 일치하고 덮어쓰기·빈 값·미존재가 구별된다. |
| 입력·실패 경계 | 잘못된 키·본문이 거부되고 기존 값이 유지되며, 제어된 내부 오류는 성공·미존재로 둔갑하지 않는다. |
| API 응답 재사용 | 첫 요청에서 원본 호출·저장, 두 번째 요청에서 같은 값 사용과 원본 호출 횟수 불변을 확인한다. |
| 저장소 연결 | 실제 `HashTableStore`를 통한 외부 요청과 기존 저장소 단위 테스트의 재실행 결과를 구분해 확인한다. |

## 다음 확인 지점

3단계의 실제 HTTP 연결과 원본 API 재사용을 완료했다. 다음 단위에서는 TTL·무효화의 계약과 상태 변경 경계를 다룬다. 고정 포트 수동 시연은 선택적 재현 확인으로 미실시 상태를 유지하며, 3단계의 실제 별도 프로세스 사용 사례는 임시 포트의 공식 테스트로 검증했다.

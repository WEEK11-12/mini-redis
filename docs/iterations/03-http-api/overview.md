## 목표와 이번 단계의 경계

직접 구현한 `HashTableStore`를 HTTP 처리부와 연결해 외부에서 저장·조회·존재 확인·삭제를 호출할 수 있게 한다. 간단한 API의 응답을 Mini Redis에 저장하고, 다음 요청에서 재사용하는 사례를 실제 요청으로 확인한다. HTTP 처리부는 요청 해석과 응답 변환을 담당하고 저장소의 버킷 내부를 직접 조작하지 않는다.

[D-0003](../../decisions/0003-http-response-contract.md)의 경로·정상/오류 응답과 `Cache-Control: no-store`가 이번 단계의 공유 기준이다. 2단계 저장소의 공개 연산 `set/get/exists/delete`와 입력 오류를 연결한다. HTTP 키의 슬래시 제외는 [D-0004](../../decisions/0004-http-key-no-slash.md), 재사용 검증은 작은 예시 API와 원본 호출 횟수 관찰을 따른다. 다른 문자의 URL 표현·라우팅 세부, 요청 본문 검증과 오류 매핑, 실행 도구 및 예시 API의 구체적 요청 형태는 **아직 정하지 않았다**.

TTL 설정과 실제 만료·무효화는 4단계, 동시성 위험 점검·방어는 5단계, 캐시 사용·미사용 성능 비교와 전체 종단 간 검증은 6단계에서 다룬다. 이번 단계에서 만료·동시성 동작이 검증된 것으로 표시하지 않는다.

## 이 단계의 문서 길잡이

`overview.md`는 상태와 문서 입구다. **요구사항 → 설계·검토 → 구현 전 테스트 계획 → 실제 구현 → 실행·검토 결과** 순서로 기록하며, 아직 없는 결과 파일을 빈 양식으로 만들지 않는다.

| 문서 | 역할·작성 시점 |
| --- | --- |
| [요구사항 명세 (`requirements.md`)](requirements.md) | 기존 계약에서 확인된 범위와 `REQ-03-001`~`REQ-03-008` 초안. 미결정 사항을 확인한 뒤 범위·인수 조건을 확정. |
| 설계 문서 (`design.md`) | HTTP·저장소 연결과 입력·오류·사례의 계약 및 선택 근거를 정할 때 작성·검토. |
| 테스트 케이스 (`test-cases.md`) | 설계 검토 뒤 구현 전에 요구사항에 연결된 통합 TC를 계획. 실행 결과와 구분. |
| 구현 기록 (`implementation.md`) | 실제 코드·테스트 변경이 생기면 변경 경로와 역할을 기록. |
| 검증 기록 (`verification.md`) | 실제 요청·테스트 명령, 환경, TC별 결과와 남은 위험을 기록. |

작성된 문서는 여기에서 링크로 연결한다. 전체 상태는 [진행 현황](../../plans/progress.md), 파일별 기준은 [단계별 산출물 가이드](../../plans/iteration-deliverables.md)를 따른다.

## 진행 체크리스트

[공통 진행 순서](../../plans/implementation-units.md#진행-체크리스트)를 이 단위에 적용한다. 아래 항목은 **예정 작업**이며 체크하지 않았다.

- [ ] [요구사항 명세 (`requirements.md`)](requirements.md)의 초안을 검토하고 목표·범위·미결정 사항 및 관찰 가능한 완료 조건을 확정한다.
- [ ] 키의 URL 표현·입력 검증·오류 매핑·HTTP 실행 구조 및 API 응답 재사용 사례를 설계 문서 (`design.md`)에 구체화한다. TTL·동시성 정책은 선결정하지 않는다.
- [ ] 설계가 D-0003과 저장소 공개 계약을 충족하는지 검토하고 차단 쟁점을 해소한다. (설계 문서 `design.md`)
- [ ] 구현 전 테스트 케이스 (`test-cases.md`)에 실제 저장소를 사용한 HTTP 통합 TC와 API 응답 재사용 경로를 요구사항 ID에 연결한다.
- [ ] HTTP 처리부·사용 사례를 구현하고, 실제 변경을 구현 기록 (`implementation.md`)에 남긴다.
- [ ] 외부 요청으로 네 기본 연산과 빈 값/미존재·잘못된 입력·재사용 경로를 확인하고, 2단계 저장소 단위 테스트도 재실행한다. 명령·환경·결과는 검증 기록 (`verification.md`)에 남긴다.
- [ ] 결과·남은 위험과 4단계로 넘길 계약을 확인하고 [진행 현황](../../plans/progress.md)을 갱신한다.

## 설계에서 확인할 사항

1. **키 경로 세부 설계:** 슬래시 포함 키는 제외한다. `/keys/{key}`의 인코딩·디코딩, 원시/인코딩 슬래시가 들어온 요청의 라우팅·오류, 다른 문자와 길이의 허용 범위는 설계에서 구체화한다.
2. **HTTP 실행·오류:** 사용할 Python HTTP 도구·실행 방식, 잘못된 JSON/누락·비문자열 값/저장소 예외의 응답 코드와 오류 식별자를 어떻게 정할까? 이미 채택한 D-0003의 상태·본문 형식을 유지한다.
3. **재사용 사례의 세부 설계:** 작은 예시 API의 데이터·요청 형태·캐시 키·문자열 값 표현은 설계에서 정한다. 첫 요청에서 원본 호출, 재요청에서 호출 횟수 불변을 확인한다. 성능 측정 조건은 6단계에서 정한다.

## 다음 확인 지점

우선 [요구사항 명세 (`requirements.md`)](requirements.md)의 나머지 범위·인수 조건을 검토한다. 슬래시 제외와 예시 API 검증 방식은 확인했으며, 다른 URL 표현·오류 세부는 설계에서 정한다. 현재 HTTP 코드·통합 TC의 실행 결과는 없다.

# 3단계 요구사항 명세서 — 외부 HTTP 사용과 API 응답 재사용

- 상태: 초안 — 예시 API·원본 호출 횟수 관찰 및 HTTP 키의 슬래시 제외 확인; 전체 범위·세부 설계 검토 전
- 적용 범위: HTTP 요청을 2단계 해시 테이블 저장소에 연결하고 API 응답을 저장·재사용하는 기능 사례. 실제 만료·무효화(4단계), 동시성 방어(5단계), 성능 비교·전체 검증(6단계)은 제외한다.
- 근거: [과제 원문](../../assignment.md), [1단계 공유 계약](../01-scope-and-contract/overview.md), [D-0002 Python·HTTP API](../../decisions/0002-python-http-interface.md), [D-0003 기본 HTTP 계약](../../decisions/0003-http-response-contract.md), [D-0004 HTTP 키 제약](../../decisions/0004-http-key-no-slash.md), [2단계 저장소 요구사항](../02-hash-table/requirements.md), [3단계 개요](overview.md)

## 식별·상태

- ID는 `REQ-03-001`처럼 단계 번호와 일련번호를 사용한다. 아래 **명세**는 이번 단계에서 기대하는 동작이고 **인수 조건**은 실행으로 확인할 기준이다. 현재 인수 조건을 통과했다는 뜻은 아니다.
- 기존 문서에 명시된 범위와 응답, 작은 예시 API·원본 호출 횟수 관찰 방식과 HTTP 키의 슬래시 제외를 반영했다. 다른 문자의 허용 범위·인코딩·라우팅은 설계에서 검토하며, 승인되지 않은 선택을 확정하지 않는다.
- 구현 전 통합 TC는 설계 검토 뒤 `test-cases.md`에, 실제 구현·검증 결과는 작업 후 `implementation.md`·`verification.md`에 각각 기록한다. 현재는 두 파일 모두 작성 전이다.

## 기능 요구사항

### REQ-03-001 — 저장·덮어쓰기의 외부 호출

- **명세:** HTTP `PUT /keys/{key}`에 `{"value": "..."}`로 문자열 값을 보내면 같은 키의 값을 저장하거나 덮어쓴다. 빈 문자열 값도 허용하며, 성공 응답은 `200`·`{"stored": true}`다.
- **인수 조건:** 외부 HTTP 요청으로 값을 저장·재저장한 뒤 같은 키를 조회하면 마지막 값만 나온다. 빈 문자열을 저장한 키도 존재하는 값으로 조회된다.
- **근거:** [D-0003 기본 연산 계약](../../decisions/0003-http-response-contract.md#결정), [REQ-02-001](../02-hash-table/requirements.md#req-02-001--저장과-덮어쓰기).

### REQ-03-002 — 조회·미존재 구별

- **명세:** `GET /keys/{key}`는 값이 있으면 `200`·`{"value": "..."}`를 반환한다. 없는 키는 `404`·`{"error": {"code": "KEY_NOT_FOUND"}}`를 반환한다. 빈 문자열 값은 미존재로 취급하지 않는다.
- **인수 조건:** 저장된 일반 값과 빈 문자열은 각각 `200`으로 정확히 조회되고, 저장하지 않았거나 삭제한 키는 `404`와 `KEY_NOT_FOUND`로 구별된다.
- **근거:** [D-0003 기본 연산 계약](../../decisions/0003-http-response-contract.md#결정), [REQ-02-002](../02-hash-table/requirements.md#req-02-002--조회-결과-구분).

### REQ-03-003 — 존재 확인

- **명세:** `GET /keys/{key}/exists`는 저장된 키에 `200`·`{"exists": true}`, 없는 키에 `200`·`{"exists": false}`를 반환한다.
- **인수 조건:** 일반 값 또는 빈 문자열 값의 키는 `true`, 저장하지 않았거나 삭제한 키는 `false`다. 없는 키도 오류 응답이 아니다.
- **근거:** [D-0003 기본 연산 계약](../../decisions/0003-http-response-contract.md#결정), [REQ-02-003](../02-hash-table/requirements.md#req-02-003--존재-확인).

### REQ-03-004 — 삭제

- **명세:** `DELETE /keys/{key}`는 실제 삭제했으면 `200`·`{"deleted": true}`, 키가 없으면 `200`·`{"deleted": false}`를 반환한다.
- **인수 조건:** 저장된 키의 첫 삭제는 `true`, 같은 키의 재삭제와 없는 키의 삭제는 `false`다. 삭제 후 조회는 `404`이고 다른 키는 그대로 조회된다.
- **근거:** [D-0003 기본 연산 계약](../../decisions/0003-http-response-contract.md#결정), [REQ-02-004](../02-hash-table/requirements.md#req-02-004--삭제).

### REQ-03-005 — 입력 거부와 내부 오류 구별

- **명세:** HTTP 키에는 슬래시(`/`)를 허용하지 않는다. 빈 키, 슬래시가 포함된 키, 누락되거나 문자열이 아닌 값 등 계약에 맞지 않는 요청은 정상 저장·조회 결과로 처리하지 않는다. 구분 가능한 잘못된 입력은 `400`과 `{"error": {"code": "..."}}` 형식으로 반환한다. 예상하지 못한 서버 내부 오류는 `500`과 같은 오류 형식으로 구별하고 내부 세부 정보를 노출하지 않는다. `KEY_NOT_FOUND` 외의 세부 오류 코드는 미정이다.
- **인수 조건:** 대표적인 잘못된 요청에서 `400`과 공통 오류 형식을 확인하고, 이전에 저장된 정상 값이 변하지 않는다. 슬래시가 포함된 HTTP 키는 서버 검증을 우회해 저장되지 않는다. 원시/인코딩 슬래시가 경로 매칭에 미치는 영향과 구체적인 오류 응답은 설계·통합 TC에서 확인한다. 제어된 내부 실패에서는 정상 성공이 아닌 `500`과 공통 오류 형식을 확인하며 내부 예외의 세부 내용은 노출되지 않는다.
- **근거:** [D-0003 입력·오류 계약](../../decisions/0003-http-response-contract.md#결정), [D-0004 HTTP 키 제약](../../decisions/0004-http-key-no-slash.md), [REQ-02-005](../02-hash-table/requirements.md#req-02-005--잘못된-입력-거부).

### REQ-03-006 — HTTP 응답의 캐시 방지

- **명세:** API 응답에는 `Cache-Control: no-store`를 넣어 HTTP 중간 캐시와 서비스 내부의 키-값 캐시를 구분한다.
- **인수 조건:** 정상 조회·저장 응답과 미존재·입력 오류 응답에서 해당 헤더를 확인한다. 다른 응답 범위는 설계·TC에서 검토한다.
- **근거:** [D-0003 기본 HTTP 계약](../../decisions/0003-http-response-contract.md#결정).

### REQ-03-007 — API 응답 저장·재사용 기능 사례

- **명세:** 프로젝트 안에 작은 예시 API를 두고 그 응답 값을 Mini Redis에 저장한다. 같은 데이터에 대한 후속 요청에서는 저장된 값을 재사용한다. 예시 데이터·요청 형태, 캐시 키·문자열 값 표현은 설계에서 정한다.
- **인수 조건:** 같은 데이터의 첫 요청에서는 원본 API가 호출되어 결과가 저장되고, 두 번째 요청에서는 저장된 결과를 얻는다. 원본 API의 호출 횟수를 관찰하여 두 번째 요청에서 호출 횟수가 늘지 않았음을 확인한다. 구체적인 입력·기대 결과는 설계·TC에서 정한다.
- **근거:** [과제 원문 품질 항목](../../assignment.md#품질), [구현 단위 가이드 3단계](../../plans/implementation-units.md#3-외부-사용-경로와-활용-사례), 확인된 3단계 예시 API·원본 호출 횟수 관찰 방식.

## 연결·검증 요구사항

### REQ-03-008 — 저장소 연결과 통합 검증

- **명세:** HTTP 처리부는 요청·응답 변환을 맡고, 키-값 연산은 기존의 직접 구현한 저장소를 사용한다. 외부 HTTP 요청과 실제 저장소를 연결한 기능 테스트로 이번 단계의 동작·경계를 확인하고 기존 저장소 단위 테스트를 유지한다.
- **인수 조건:** 코드 검토에서 HTTP 처리부가 저장소 버킷을 직접 조작하거나 다른 핵심 키-값 저장소로 대체하지 않음을 확인한다. 실제 저장소를 이용한 외부 요청 테스트에서 `REQ-03-001`~`REQ-03-007`의 확정된 인수 조건을 확인하고, 저장소 단위 테스트의 재실행 명령·조건·실제 결과를 기록한다. 미실행 조건은 완료로 표시하지 않는다.
- **근거:** [D-0002 책임 경계](../../decisions/0002-python-http-interface.md#결정과-영향), [1단계 공유 계약](../01-scope-and-contract/overview.md#확인된-공유-계약과-책임-경계), [단계별 산출물 가이드](../../plans/iteration-deliverables.md#단계에-따른-테스트-경계).

## 확정된 경계와 설계에서 정할 사항

HTTP 키의 슬래시 제외는 [D-0004](../../decisions/0004-http-key-no-slash.md)에서 확정했다. 클라이언트가 입력 검사 기능을 제공할 수는 있지만, HTTP 서버의 키 검증을 대체할 수 없다. 구분 가능한 잘못된 키 입력은 D-0003의 `400` 계약을 따른다. 원시/인코딩 슬래시의 라우팅·경로 불일치 처리와 다른 문자(공백·유니코드 등)의 허용·URL 표현은 설계·통합 TC에서 구체화한다. 저장소 자체의 키 계약은 변경하지 않는다.

작은 예시 API와 원본 호출 횟수 관찰 방식도 확인했다. 구체적인 예시 데이터·요청 형태·캐시 키 및 문자열 값 표현은 설계에서 정한다.

오류 코드의 세부 이름, 잘못된 JSON·본문 구조의 처리, 프레임워크·실행 방식은 설계에서 제안·검토할 수 있다. 이 문서가 임의로 확정하지 않는다. 실제 만료 키의 응답 계약은 [D-0003](../../decisions/0003-http-response-contract.md)에 이미 정해졌지만, 만료 동작 구현·검증은 4단계다.

# 1단계: 범위와 공유 계약

- 상태: 완료 — 범위·계약 확정. 구현·테스트 완료가 아님
- 근거: [과제 원문](../../assignment.md), [구현 단위 가이드](../implementation-units.md), [진행 현황](../README.md)

여러 애플리케이션이 함께 쓸 **가벼운 범용 인메모리 캐시**를 하루 안에 구현·검증한다. 첫 단위에서는 전체를 상세 설계하는 대신, 후속 작업이 공유해야 할 범위와 인터페이스만 정했다. 사원 데이터 캐싱은 사용 예시이지 기능을 특정 업무에 한정하지 않는다.

## 진행 체크리스트

[공통 진행 순서](../implementation-units.md#진행-체크리스트) 중 이 단위에 해당하는 항목을 확인했다.

- [x] 과제의 필수·Optional 항목을 구분하고 후속 작업 단위에 배치했다. ([과제 원문](../../assignment.md), 아래 범위 표)
- [x] Python·HTTP API를 선택하고 외부 사용 경로를 정했다. ([D-0002](../../decisions/0002-python-http-interface.md))
- [x] 키·값, 기본 연산, 빈 값·미존재·만료 응답을 확인했다. ([D-0003](../../decisions/0003-http-response-contract.md))
- [x] HTTP 처리부와 저장소의 책임 및 저장소 연산의 최소 결과를 확인했다. (아래 경계)
- [x] 과제 대응과 최소 경계를 확정하고 2단계 착수 조건을 확인했다. ([진행 현황](../README.md))

이 단위에는 코드 구현·실행 테스트가 **해당 없음**이다. 후속 단위의 구현·검증 완료를 의미하지 않는다.

## 범위와 후속 작업

과제의 비선택 항목은 모두 구현·검증 대상이다. 아래 표는 **작업 배치**이며 실행 결과가 아니다.

| 과제에서 필요한 결과 | 다룰 단위 |
| --- | --- |
| 해시 테이블 직접 구현, 저장·조회·삭제와 주요 함수 설명 | 2, 6 |
| 외부 사용 HTTP API와 API 응답 저장·재사용 사례 | 3 |
| 보관 기간 만료 처리와 데이터 무효화 | 4 |
| 동시성 문제를 막기 위한 구조 검토·필요한 방어 | 5 |
| 단위·기능 테스트, 엣지 케이스, 캐시 사용·미사용 성능 비교 | 2~6 |
| 서버 중단 시 데이터 보존 | **Optional** — 필수 완료 기준에서 제외, 구현 여부는 미결정 |

조회 결과와 존재 여부를 호출자가 구분해 받을 수 있어야 한다. **존재 확인**은 과제 원문에 명시된 연산은 아니지만 이번 사용 요구에 포함한다.

## 확인된 공유 계약과 책임 경계

- **외부 인터페이스:** Python 서버의 HTTP API. 기본 경로·상태 코드·JSON 응답·오류 형식과 `Cache-Control: no-store`는 [D-0003](../../decisions/0003-http-response-contract.md)을 따른다. HTTP 처리부는 요청 해석·응답 변환을 맡고 해시 테이블의 버킷 조작은 맡지 않는다.
- **키·값:** 비어 있지 않은 문자열 키와 문자열 값. 빈 문자열 값은 유효하지만 빈 키는 거부한다. 빈 값과 미존재는 다른 결과로 다룬다.
- **저장소:** HTTP와 독립적인 직접 구현 해시 테이블이 저장·조회·존재 확인·삭제를 맡는다. 저장은 같은 키를 덮어쓰고 성공 시 별도 결과가 없다. 조회는 `(True, 문자열 값)` 또는 `(False, None)`으로 빈 값과 미존재를 구분한다. 존재 확인·삭제는 각각 존재 여부·실제 삭제 여부를 불리언으로 반환하고 잘못된 키·값은 거부한다. 구체적인 함수명과 오류 전달 방식은 2단계에서 정한다.
- **만료:** 만료된 키는 외부에서 없는 키처럼 응답하고 값을 반환하지 않는다. 내부 제거 시점·시간 계산은 4단계에서 정한다.

# 2단계 요구사항 명세서 — 해시 테이블 저장소

- 상태: 범위 확정 — 설계 문서 검토 완료, 구현·인수 조건 실행 검증 전
- 적용 범위: HTTP와 독립적인 저장소. 외부 HTTP 연결(3단계), TTL·무효화(4단계), 동시성 방어(5단계)는 제외한다.
- 근거: [과제 원문](../../assignment.md), [1단계 공유 계약](../01-scope-and-contract/overview.md), [D-0003 기본 계약](../../decisions/0003-http-response-contract.md), [2단계 진행](overview.md)

## 식별·추적 규칙

- ID는 `REQ-02-001` 형태로, 단계 번호와 단계 내 일련번호를 사용한다. 내용을 수정해도 ID를 재사용·재번호화하지 않는다. 새 요구는 새 ID를 부여한다.
- 각 항목의 **명세**는 저장소가 보여야 할 동작, **인수 조건**은 관찰 가능한 확인 기준이다. 테스트 실행 전에는 인수 조건을 충족했다고 표시하지 않는다.
- 아래 항목의 **범위**는 확정했다. 인수 조건은 그 범위를 검증 가능하게 풀어 쓴 것이며, 실제 충족 여부는 아직 검증하지 않았다.
- 코드·테스트 연결과 결과는 구현·실행 뒤 [2단계 진행 문서](overview.md#5-테스트결과-확인--미실시)에 ID별로 추가한다. 전체 단계 목록은 [요구사항 색인](../README.md)에서 찾는다.

## 기능 요구사항

### REQ-02-001 — 저장과 덮어쓰기

- **명세:** 저장소는 비어 있지 않은 문자열 키에 문자열 값을 저장한다. 빈 문자열 값도 저장할 수 있다. 같은 키에 다시 저장하면 기존 값을 덮어쓰며 저장 성공 시 별도의 반환 결과는 없다.
- **인수 조건:** 키에 저장한 값을 조회하면 그 값이 반환된다. 같은 키에 두 번 저장하면 마지막 값만 조회되고, 삭제 한 번으로 그 키가 없어지며 이전 값이 다시 나타나지 않는다. 빈 문자열도 조회 시 존재하는 값으로 반환된다.
- **근거:** 1단계 저장소 최소 계약과 과제의 저장 기능.

### REQ-02-002 — 조회 결과 구분

- **명세:** 조회는 키가 존재하면 `(True, 문자열 값)`, 존재하지 않으면 `(False, None)`을 반환한다.
- **인수 조건:** 빈 문자열을 저장한 키의 조회 결과는 `(True, "")`, 저장하지 않았거나 삭제한 키는 `(False, None)`이다.
- **근거:** 1단계 저장소 최소 계약.

### REQ-02-003 — 존재 확인

- **명세:** 존재 확인은 키의 존재 여부를 불리언으로 반환한다.
- **인수 조건:** 문자열 값 또는 빈 문자열 값이 저장된 키는 `True`, 저장하지 않았거나 삭제한 키는 `False`다.
- **근거:** 1단계에 포함된 존재 확인 계약.

### REQ-02-004 — 삭제

- **명세:** 삭제는 실제로 키를 제거했는지를 불리언으로 반환한다. 다른 키의 값은 변경하지 않는다.
- **인수 조건:** 저장된 키의 첫 삭제는 `True`, 같은 키의 재삭제와 없는 키의 삭제는 `False`다. 삭제한 키의 재조회는 `(False, None)`이고 다른 키는 유지된다.
- **근거:** 1단계 저장소 최소 계약과 과제의 삭제 기능.

### REQ-02-005 — 잘못된 입력 거부

- **명세:** 저장소는 빈 문자열 키, 문자열이 아닌 키, 저장 시 문자열이 아닌 값 및 값 누락을 유효한 저장소 연산으로 받아들이지 않는다. 잘못된 입력은 유효한 미존재·빈 값 결과와 구별한다.
- **인수 조건:** 빈 키·문자열 아닌 키/값·값 누락으로 호출하면 정상 성공 결과가 나오지 않으며, 이전에 저장된 유효한 키의 조회 결과는 변하지 않는다. 예외의 구체적인 유형과 함수 인자 형태는 설계에서 결정해 테스트한다.
- **근거:** 1단계 키·값 계약 및 2단계 확인 범위.

### REQ-02-006 — 충돌한 키의 독립성

- **명세:** 서로 다른 키가 같은 버킷 위치에 대응되더라도 각각 별도의 값으로 보관되고, 한 키의 덮어쓰기·삭제가 다른 키를 바꾸지 않는다.
- **인수 조건:** 동일 버킷으로 매핑되는 두 키를 저장한 뒤 각각 조회할 수 있다. 하나를 덮어쓰거나 삭제한 뒤 다른 하나의 조회·존재 확인 결과는 유지된다.
- **근거:** 해시 테이블 직접 구현 요구 및 2단계 확인 범위.

## 구현 제약 및 검증 요구사항

### REQ-02-007 — 직접 구현한 저장소

- **명세:** 핵심 키-값 보관은 Python `dict`에 위임하지 않고, 저장소가 해시 계산·키 비교·충돌 처리를 직접 수행한다. HTTP 요청 해석은 이 저장소의 책임이 아니다.
- **인수 조건:** 코드 검토에서 저장·조회·삭제가 저장소의 버킷 및 키 비교 경로를 사용함을 확인할 수 있고, 주요 연산의 입력→처리→출력을 설명할 수 있다. 단위 테스트는 HTTP 서버 없이 실행된다.
- **근거:** [과제 원문](../../assignment.md), [1단계 책임 경계](../01-scope-and-contract/overview.md#확인된-공유-계약과-책임-경계).

### REQ-02-008 — 저장소 단위 테스트

- **명세:** 이번 단계의 저장·조회·존재 확인·삭제, 덮어쓰기, 빈 값·미존재, 충돌, 잘못된 입력을 단위 테스트로 검증한다.
- **인수 조건:** 각 기능 요구사항 ID에 대응하는 테스트가 실행되고, 실행 명령·환경·실제 통과/실패 결과를 기록한다. 미실행 항목은 완료로 표시하지 않는다.
- **근거:** [과제 원문 품질 항목](../../assignment.md), [2단계 완료 기준](../../plans/implementation-units.md).

## 후속 단위와의 경계

- 키의 URL 경로 표현과 추가 제약, HTTP 오류 응답 매핑은 3단계에서 다룬다. 저장소 오류의 구체적 타입은 2단계 설계에서 정한다.
- 만료·무효화와 동시성 방어는 각각 4·5단계에서 다룬다. 이번 명세의 미존재 결과는 해당 기능이 붙을 때에도 공유 계약과 일치해야 한다.
- 해시 알고리즘, 충돌 처리 방식, 용량·확장 정책, 함수명은 요구사항이 아니라 [2단계 설계](design.md)에서 결정한다.

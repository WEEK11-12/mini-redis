## 진행 체크리스트

[공통 진행 순서](../../plans/implementation-units.md#진행-체크리스트)에 맞춰 **요구사항 명세 → 설계 → 설계 검토 → 구현 전 TC → 구현 → 테스트·결과 확인** 순서로 진행한다. 테스트에서 누락이나 실패가 드러나면 해당 요구사항·설계·구현으로 돌아가 수정한다. 현재 위치는 설계 검토·TC 초안 작성 후 구현 전이다.

- [x] 요구사항의 범위·경계 사례·완료 조건을 확정한다. ([요구사항 명세](requirements.md) — 범위 확정; 인수 테스트는 미실시)
- [x] 충돌 처리, 용량·확장, 입력 오류 표현과 연산의 입출력을 설계한다. ([설계 문서](design.md))
- [x] 설계가 1단계 계약과 요구사항을 충족하는지 검토하고 막는 쟁점을 확인한다. (아래 설계 검토 — 문서 계약 한정)
- [x] 구현 전에 요구사항·설계 경계에 연결된 단위 TC를 [test-cases.md](test-cases.md)에 작성한다. 테스트 코드는 `tests/test_store.py`에 준비했으며 구현·실행 검증 전이다. ([산출물 가이드](../../plans/iteration-deliverables.md))
- [ ] 확정된 범위의 해시 테이블과 기본 연산을 구현하고 `implementation.md`에 실제 변경을 기록한다. (아래 구현)
- [ ] 저장·조회·삭제·존재 확인과 충돌·경계 사례의 단위 테스트를 실제 실행하고 명령·조건·결과를 남긴다. (아래 테스트·결과 확인)
- [ ] 주요 연산 흐름과 남은 문제를 검토하고 [진행 현황](../../plans/progress.md)을 갱신한다.

## 목표와 범위

HTTP와 독립적으로 동작하는 **직접 구현한 해시 테이블 저장소**를 만들고, 기본 연산과 충돌·경계 상황을 단위 테스트로 확인한다. 이번 단계의 범위는 [2단계 요구사항 명세](requirements.md)로 확정했다. 체이닝·결정적 자체 해시·부하율 기반 확장을 선택했고 [설계 문서](design.md)의 계약 검토를 마쳤다.

HTTP 연결은 3단계, TTL·만료와 무효화의 상세 동작은 4단계, 동시성 방어는 5단계에서 다룬다. 후속 기능을 포기한다는 뜻이 아니다.

## 1. 요구사항 명세 — 범위 확인 완료

이번 단위의 요구사항·고정 ID·인수 조건은 별도 [2단계 요구사항 명세서](requirements.md)에만 유지한다. `REQ-02-001`~`REQ-02-008`은 저장·조회·존재 확인·삭제·입력 검증·충돌 독립성·직접 구현·단위 테스트를 다룬다. 범위 확정과 각 인수 조건의 실행 검증은 별개다. 전체 단위의 명세는 [요구사항 색인](../README.md)에서 찾는다.

## 2. 설계 — 문서 작성·검토 완료

상세 계약과 선택 근거는 [설계 문서](design.md)에 유지한다. 체이닝, 결정적 자체 문자열 해시, 초기 버킷 8개, 부하율 1 초과 예정 시 두 배 확장, 자동 축소 없음, 표준 입력 예외를 선택했다. 공개 인터페이스와 상태·실패 계약을 문서화하고 독립 검토의 보완 의견 및 초점 재검토 결과를 반영했다.

## 3. 설계 검토 — 문서 계약 검토 완료

설계 검증 에이전트의 독립 검토에서 구현 착수를 막는 확정 설계 오류는 발견되지 않았다. 저장 실패 보장의 적용 범위와 상위 구현 가이드의 미결정 상태 표기를 보완했고, 초점 재검토에서 두 지적 모두 해소됐으며 수정으로 인한 직접적인 새 충돌은 발견되지 않았다. [설계 문서](design.md)의 보장 범위는 동기 `Exception`(메모리 할당 실패 포함)으로 한정한다. 초점 재검토는 변경 부분의 직접 영향에 한정하며, 구현·테스트 성공 판정은 아니다.

## 4. 구현 — 미착수

검토된 설계에 맞춰 HTTP와 분리된 저장소만 구현한다. [구현 전 TC](test-cases.md)와 `tests/test_store.py`의 계약 테스트 초안을 준비했다. 실제 파일·함수와 구현 선택은 작업 뒤 `implementation.md`에 기록한다. 저장소 구현 근거는 아직 없다.

## 5. 테스트·결과 확인 — 미실시

| 검증 대상 | 실행 시 확인할 관찰 결과 |
| --- | --- |
| 저장·조회·덮어쓰기 | 저장한 값과 마지막으로 덮어쓴 값을 조회한다. |
| 빈 값·미존재·존재 확인 | `""`의 존재와 없는 키의 부재를 구별한다. |
| 삭제 | 있던 키는 한 번만 실제 삭제되며 다른 키는 유지된다. |
| 해시 충돌 | 실제 같은 버킷에 놓이는 서로 다른 키가 갱신·삭제 후에도 독립적이다. |
| 용량 경계·재배치 | 새 키 저장 결과 부하율이 정확히 1이면 확장하지 않고, 초과하면 두 배 확장한 뒤에도 기존 키·값이 유지된다. |
| 잘못된 입력 | 빈 키·문자열 아닌 키/값·값 누락을 거부하고 저장 상태는 유지된다. |
| 저장·확장 실패 | 제어된 동기 예외가 발생하면 기존 키·값·항목 수·버킷 수가 유지되고 이후 연산을 사용할 수 있다. |

테스트 도구·명령, 실행 환경·조건, TC별 실제 결과와 남은 실패를 **실행 후에만** `verification.md`에 기록한다. 결과 검토에서 설계·구현을 다시 살펴야 할 때는 위 절로 되돌아간다. 주요 연산을 설명할 수 있는지도 함께 확인한다.

## 다음 확인 지점

1. [구현 전 TC](test-cases.md)와 계약 테스트 코드의 임시 접점을 검토하고, 구현에서 확정할 이름·내부 관찰 지점을 맞춘다.
2. TC별 실패 확인·구현·통과 확인을 반복하고 변경 내용을 `implementation.md`에 남긴다.
3. 저장·확장 실패 보존을 포함해 단위 테스트를 실제 실행하고 `verification.md`에 결과를 기록한다. 현재 인수 조건의 실행 결과는 없다.

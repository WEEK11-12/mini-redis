## 목표와 범위

HTTP와 독립적으로 동작하는 **직접 구현한 해시 테이블 저장소**를 만들고, 기본 연산과 충돌·경계 상황을 단위 테스트로 확인한다. 이번 단계의 범위는 [2단계 요구사항 명세](requirements.md)로 확정했다. 설계 방식은 아직 선택하지 않았다.

HTTP 연결은 3단계, TTL·만료와 무효화의 상세 동작은 4단계, 동시성 방어는 5단계에서 다룬다. 후속 기능을 포기한다는 뜻이 아니다.

## 1. 요구사항 명세 — 범위 확인 완료

이번 단위의 요구사항·고정 ID·인수 조건은 별도 [2단계 요구사항 명세서](requirements.md)에만 유지한다. `REQ-02-001`~`REQ-02-008`은 저장·조회·존재 확인·삭제·입력 검증·충돌 독립성·직접 구현·단위 테스트를 다룬다. 범위 확정과 각 인수 조건의 실행 검증은 별개다. 전체 단위의 명세는 [요구사항 색인](../README.md)에서 찾는다.

## 2. 설계 — 선택지 검토 중

아래는 **제안**이며 채택된 설계가 아니다. 1단계 저장소 계약은 유지한다. 충돌이 일어나는 두 키의 갱신·삭제가 다른 키에 영향을 주지 않아야 한다.

| 선택 지점 | 대안과 비용 | 이번 범위의 제안 |
| --- | --- | --- |
| 충돌 처리 | **체이닝:** 버킷마다 항목 목록을 두어 키를 직접 비교한다. 삭제가 직관적이나 목록의 추가 메모리가 든다. **개방 주소법:** 배열의 다음 빈 칸을 탐색해 저장한다. 별도 목록이 적지만 삭제 후 탐색 경로를 지킬 장치가 필요하다. | 작은 구현과 충돌·삭제 설명을 우선해 체이닝. |
| 해시 계산 | **직접 계산하는 결정적 문자열 해시:** 계산 과정을 설명·테스트하기 쉽지만 입력 분포와 충돌에 주의한다. **Python 내장 `hash`:** 별도 구현이 간단하지만 해시 계산 자체를 설명할 직접 구현 범위가 줄고 프로세스별 결과가 달라질 수 있다. | 문자열의 문자값을 순회해 해시를 직접 계산. 구체적인 계산식·인코딩은 설계 확정 시 명시. |
| 용량·확장 | **고정 크기:** 구현이 간단하지만 항목이 늘면 한 버킷의 탐색 비용이 커질 수 있다. **부하율 기준 확장:** 재배치 코드와 검증이 추가되지만 크기가 늘어도 버킷이 과도하게 길어지는 것을 완화한다. | 작은 초기 용량과 부하율 기준 2배 확장·재배치. 정확한 크기·임계값은 설계 확정 시 명시. |
| 입력 오류 | **`ValueError`/`TypeError`:** 잘못된 값/타입을 나누어 HTTP 계층에서 변환하기 쉽다. **하나의 사용자 정의 예외:** 호출 경계는 단순하지만 별도 타입·매핑이 필요하다. | 표준 예외로 구분. 키·값의 누락은 호출 시 인자 누락 오류와 구별할지 함수 시그니처와 함께 명시. |

설계가 선택되면 함수명·입출력, 검증 순서, 해시·버킷 불변 조건, 덮어쓰기·삭제·확장 시 항목 수 변화와 주요 연산의 입력→처리→출력 흐름을 이 절에 기록한다. 현재 채택된 세부 설계는 없다.

## 3. 설계 검토 — 미실시

선택한 설계가 1단계 저장소 계약 및 위 요구사항을 충족하는지, 충돌·덮어쓰기·삭제 뒤에도 키를 정확히 찾는지, 후속 HTTP·TTL 연결을 막는 가정이 없는지 점검한다. 발견된 문제는 설계나 요구사항으로 되돌려 수정한다. 검토 결과는 아직 없다.

## 4. 구현 — 미착수

검토된 설계에 맞춰 HTTP와 분리된 저장소만 구현한다. 파일·함수와 실제 변경 내용은 구현 후 기록한다. 현재 구현 근거는 없다.

## 5. 테스트·결과 확인 — 미실시

| 검증 대상 | 실행 시 확인할 관찰 결과 |
| --- | --- |
| 저장·조회·덮어쓰기 | 저장한 값과 마지막으로 덮어쓴 값을 조회한다. |
| 빈 값·미존재·존재 확인 | `""`의 존재와 없는 키의 부재를 구별한다. |
| 삭제 | 있던 키는 한 번만 실제 삭제되며 다른 키는 유지된다. |
| 해시 충돌 | 같은 버킷의 서로 다른 키가 갱신·삭제 후에도 독립적이다. |
| 잘못된 입력 | 빈 키·문자열 아닌 키/값·값 누락을 거부하고 저장 상태는 유지된다. |

테스트 도구·명령, 실행 환경·조건, 실제 결과와 남은 실패를 **실행 후에만** 기록한다. 결과 검토에서 설계·구현을 다시 살펴야 할 때는 위 절로 되돌아간다. 주요 연산을 설명할 수 있는지도 함께 확인한다.

## 다음 확인 지점

1. 위 설계 선택지와 추천 조합을 비교·선택하고 세부 계약을 적는다.
2. 설계를 요구사항·1단계 계약에 대조해 검토한다.
3. 검토한 설계에 따라 구현·테스트를 실제 실행하고 결과를 기록한다. 현재 실행 결과는 없다.

## 진행 체크리스트

[공통 진행 순서](../../plans/implementation-units.md#진행-체크리스트)에 따라 아래를 먼저 확인한다. 현재는 **요구사항 초안 검토** 단계다.

- [ ] 저장소 기본 연산·입력·경계 사례와 이번 단위의 제외 범위를 사용자와 확인한다.
- [ ] 충돌 처리, 용량·확장, 입력 오류·결과 표현을 설계하고 저장소 계약과 맞는지 검토한다.
- [ ] 해시 테이블 및 기본 연산을 구현한다.
- [ ] 저장·조회·삭제, 덮어쓰기, 충돌, 빈 값·미존재·잘못된 입력의 단위 테스트를 실행하고 명령·결과를 기록한다.
- [ ] 설명 가능한 주요 연산 흐름, 남은 문제와 3단계 HTTP 연결 조건을 사용자와 확인하고 [진행 현황](../../plans/progress.md)을 갱신한다.

## 이번 단위의 목표

HTTP와 독립적으로 동작하는 **직접 구현한 해시 테이블 저장소**를 만들고, 기본 연산과 충돌·경계 상황을 단위 테스트로 확인한다. HTTP 연결은 3단계, TTL·만료와 무효화의 상세 동작은 4단계, 동시성 방어는 5단계에서 다룬다. 이 구분은 후속 기능을 포기한다는 뜻이 아니다.

## 요구사항 초안 — 사용자 확인 전

- 비어 있지 않은 문자열 키와 문자열 값(빈 문자열 허용)을 저장한다. 같은 키에 다시 저장하면 기존 값을 덮어쓴다.
- 조회는 존재하는 값(빈 문자열 포함)과 미존재를 구분한다. 존재 확인은 불리언, 삭제는 실제 삭제 여부를 반환한다. 빈 키나 잘못된 값 타입은 거부한다. [1단계 최소 경계](../01-scope-and-contract/overview.md)를 따른다.
- 해시 계산·충돌 처리·키 비교를 직접 구현한 저장소가 맡는다. 기본 키-값 보관을 Python의 `dict`에 위임해 직접 구현 요구를 대체하지 않는다.
- 저장·조회·삭제, 같은 키 덮어쓰기, 서로 다른 키의 충돌, 빈 값·미존재·잘못된 입력을 단위 테스트로 확인한다. 해시 테이블 설계 원리와 주요 연산 흐름을 설명할 수 있어야 한다.

## 다음 확인 지점

1. 사용자가 위 2단계 요구사항 초안의 범위·경계 사례를 확인하고 필요한 변경을 말한다.
2. 그 뒤 충돌 처리, 테이블 크기·확장, 입력 검증과 결과 표현 등 이 단위에 필요한 설계를 비교·선택한다. 1단계에서 확정한 공유 계약은 임의로 바꾸지 않는다.
3. 설계 검토 후 구현하고 단위 테스트를 실제 실행해 명령·조건·결과를 기록한다. 아직 실행 결과는 없다.

# 구현 단위와 검증 계획

현재 자동 테스트 57개를 U7 구현 후 실행해 통과했다. U1~U7의 합의한 필수 범위 T-01~T-16을 확인했다. T-16 시간 비교는 자동 검색과 분리해 실제 HTTP 각 20회로 실행했다. 단위 테스트 통과가 모든 입력·스케줄의 안정성을 증명하지는 않는다.

[요구사항](REQUIREMENTS.md) → 이 문서의 테스트 ID·통과 조건 → [실행 이력](../history/README.md) → [현재 작업 인계](../WORKLOG.md) 순서로 연결한다. 자동 실행 파일·명령은 [tests 안내](../tests/README.md)를 따른다.

## 단위별 현재 상태

| 단위 | 범위 | 관련 요구 | 상태·실행 기록 |
| --- | --- | --- | --- |
| U1 | 저장·조회·삭제·충돌 | R-01, R-02, R-11 | 6개 통과, 연결 보존 확인. [U1](../history/U1-storage.md) |
| U2 | 입력·FNV 검산·확장 | R-01, R-03, R-04, R-09 | 10개 추가·당시 총 16개 통과. [U2](../history/U2-input-and-resize.md) |
| U3 | TTL·접근 만료 | R-05, R-09 | 10개 추가·당시 총 26개 통과, 만료/삭제 의미 확인. [U3](../history/U3-ttl.md) |
| U4 | 청소·커서·작업자 생명주기 | R-06, R-07, R-10 | 15개 추가·당시 총 41개. 이후 집중 1개와 별도 부하 PASS. [U4](../history/U4-cleanup.md) |
| U5 | 요청 겹침·락·확장·청소 일관성 | R-07 | 새 2개와 기존 U4 사례 재사용, 필수 3항목 PASS. [U5](../history/U5-concurrency.md) |
| U6 | Flask·Waitress HTTP | R-08, R-09, R-10 | API 7개·서버 3개 PASS. [U6](../history/U6-http.md) |
| U7 | 캐시 활용·성능 비교 | R-12, R-13 | 동작 3개·미사용/Miss/Hit 각 20회 PASS. [U7](../history/U7-cache.md) |

테스트 ID는 시나리오 묶음이다. T-07처럼 여러 메서드가 같은 ID를 검증하거나, U5가 U4 테스트를 재사용할 수 있다. 단위·ID·테스트 메서드 개수가 일대일로 대응하지 않는다. 이력의 16·26·41개는 당시 누적 수이며 현재 수 57개와 구분한다.

## T-01~T-06 — 기본 저장소

| 테스트 ID | 입력·상황 | 기대 결과 | 잡으려는 오류 |
| --- | --- | --- | --- |
| T-01 | 새 키 저장 후 조회 | 동일 문자열 | 저장·탐색 연결 실패 |
| T-02 | 같은 키 덮어쓰기 | 최신 값, 키 수 유지 | 같은 키를 중복 노드로 추가 |
| T-03 | 저장 키 삭제 후 조회 | None | 체인에서 실제 제거하지 않음 |
| T-04 | 없는 키 조회·삭제 | None / False, 상태 유지 | 없음과 빈 값 혼동·불필요 예외 |
| T-05 | 같은 버킷의 서로 다른 키 저장 | 각각의 값 | 버킷 번호만 보고 덮어쓰기 |
| T-06 | 충돌 체인의 첫·중간·끝 삭제 | True, 나머지 모두 조회 가능 | 연결 끊김·잘못된 헤드 변경 |


충돌은 실제 버킷 계산으로 확인하고, FNV 자체는 T-08의 독립 기준값으로 검증한다. 실행한 함수로 기대값까지 만들지 않는다.

T-07~T-16은 합의한 범위에서 통과했다. U6의 네 묶음은 정상/TTL·입력 거부와 보존·실제 Waitress 통신·생명주기다. T-16은 상품 1개·원본 50ms 대기, 화면 TTL 1초·측정 TTL 60초, 미사용/Miss/Hit 각 20회 순차 요청으로 합의했다. 동일 데이터·경로·원본 횟수가 통과 조건이며 시간 배속 목표는 없다. 만료는 주입 시간으로 1초 직전·같음을 확인했다. 표에 있다는 이유로 일괄 구현하거나 성공 기록을 미리 만들지 않는다.

## 선택 실행과 전체 확인

- 작업 중에는 필수 사례의 목적·입력·예상 결과를 먼저 설명하고 필요한 항목 전부를 확인한다. 검사 수를 하나로 제한하지 않는다.
- 추가 실험은 해결할 구체적 위험이 있을 때 이유를 논의한다. 임의로 검사 범위를 늘리지 않는다.
- 제품 기능 변경은 작은 실패 → 최소 구현 → 재검증으로 진행한다. 기존 구현을 확인하는 테스트는 일부러 버그를 만들 필요가 없다.
- 단위 종료 시 history/에 실제 결과·실패 원인·수정·재검증·사용자 확인·남은 한계를 요약한다.
- U7 구현 후 전체 자동 테스트 57개를 실행했고, 사용자 스크린샷 요청 뒤 로그 보관용으로 한 번 추가 실행해 57개 PASS를 확인했다. 매 사례 뒤 전체를 반복하지 않았고 10,000키 부하도 재실행하지 않았다.

## 부하 실험의 위치와 한계

명시 실행: `python -m tests.load_cleanup`. 자동 unittest 검색에 포함하지 않는다.

기록된 단일 실행에서는 고정 주입 시간·실제 100ms 작업자로 10,000키 중 만료 7,000개를 회수하고 유효 3,000개를 보존했다. 약 17.94초·164회차였다. [조건과 해석](../history/U4-cleanup.md), [회차별 측정](../history/U4-cleanup-load-result.json)을 함께 읽는다. 이번 커밋 검토에서는 저장된 수치의 일관성만 확인했다. HTTP 부하·한계 스트레스·일반 서버 성능 결과가 아니다.

Python 3.13.14·표준 unittest로 검증했다. Flask 3.1.3·Waitress 3.0.2는 .venv에 설치해 실제 HTTP 테스트를 통과했다. Windows 실제 Ctrl+C 키 입력은 미검증이며 진입점의 인터럽트·오류는 주입해 종료를 확인했다.

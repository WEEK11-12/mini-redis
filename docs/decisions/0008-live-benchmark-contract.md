## 배경과 판단 기준

7단계는 저장된 6단계 결과를 보여주는 정적 화면이 아니라 브라우저에서 새로운 MongoDB 원본·Mini Redis 성능 비교를 시작하고 결과를 확인하는 로컬 시연이다. 수동 터미널 준비를 필수로 두지 않으면서, 시드 명령의 컬렉션 삭제·측정기 자식 프로세스 잔존·원자료 혼동을 막아야 한다. 제품 코드와 기존 측정 규칙은 변경하지 않는다.

## 결정과 이유

- 웹에서 전용 Docker MongoDB 기동, 필요 시 시드 생성, 측정 전 재시작을 지원하는 B안을 채택한다. 수동 준비만 하는 방식은 이 시연의 운영을 오히려 복잡하게 한다는 판단이다.
- 정리 버튼/API는 넣지 않는다. 화면을 닫기 전에 버튼을 누른다는 보장이 없으므로 삭제를 보장하는 수단이 아니다. 컨테이너·볼륨은 서버 종료 때 자동 중지·삭제하지 않고 남는 자원과 안전한 수동 정리를 안내한다.
- [7단계 실행·화면 계약](../iterations/07-live-benchmark-ui/execution-screen-contract.md)의 준비·시드 재생성 확인, 전용 자원 소유 확인, 실행별 원자료, 로컬 HTTP 요청·상태·오류, 복구 차단 및 성공·실패 표시 기준을 **7단계 구현 기준으로 채택**한다. 원자료와 공유 복구 기록의 위치·선후 관계 등 구체 설계는 [설계](../iterations/07-live-benchmark-ui/design.md)를 따른다. 6단계의 측정·집계 규칙이나 제품 HTTP API는 변경하지 않는다.
- 측정 전 읽기 검사·재시작은 측정 타이머 밖이지만 파일 캐시 영향을 완전히 제거한다고 주장하지 않는다. 추가 저장 크기 하한(캐시 한도의 2배)은 7단계의 기준이며 6단계 결과에 소급 적용하지 않는다. 시간 제한 숫자는 첫 구현의 잠정 시작값으로 채택하고 실제 실행 근거로 조정할 수 있다.

## 영향과 검증

브라우저는 실제 그 실행의 원자료에서 검증된 수치만 표시하고, 실패·불완전 결과를 성공 비교 그래프로 만들지 않는다. 미종결 작업이나 프로세스 회수 불확실 상태에서는 준비·시드·측정을 차단한다. 구현 전에 계약에 연결된 테스트 케이스를 작성하고, Docker 자원 소유·시드 삭제 경계·서버 비정상 종료 및 서로 다른 checkout의 복구 기록·요청 보호·원자료 대응을 실제로 검증한다. 전체 설계 검토는 조건부 적합이었고 차단 지적의 수정은 해당 범위 제한 재점검에서 설계 수준 비차단이었다. **이 결정은 수정본 전체의 독립 재승인이나 구현·Docker·성능 측정 검증 완료를 뜻하지 않는다.**

## 재검토 조건

로컬 단일 사용자 시연을 넘어 다중 사용자·원격 배포를 지원하거나, 공유 자원과 복구 기록의 안전성을 실제로 보장할 수 없거나, 실측에서 추가 저장 크기·시간 제한 기준이 목적을 방해하면 관련 계약을 다시 검토한다.

# D-0003: 공유 캐시의 기본 HTTP 계약

## 배경과 판단 기준

여러 애플리케이션에서 캐시를 사용할 때 빈 값, 없는 키, 잘못된 요청과 내부 오류를 구분해야 한다. 하루 안에 구현·검증할 수 있도록 HTTP 상태 코드와 간단한 JSON 결과를 사용한다. 모든 연산을 같은 본문 형태로 강제하지 않고 오류 표현만 공통으로 둔다.

## 결정

- **키는 비어 있지 않은 문자열**이고, 값은 우선 **문자열**로 제한한다. 빈 문자열 `""`은 유효한 값이지만 유효한 키는 아니다. 값 필드 누락은 빈 값과 다른 잘못된 입력이다. 키의 추가 제약과 URL 경로 인코딩은 별도로 정한다.
- 정상 결과는 연산별 JSON 본문으로 반환한다. 오류는 `{"error": {"code": "..."}}` 형태로 구분한다. 서버 내부 세부 오류를 그대로 노출하지 않는다.
- 기본 연산의 HTTP 계약은 아래와 같다. 만료된 키는 없는 키와 같은 응답을 사용하고, 만료된 값을 유효한 값으로 반환하지 않는다.

| 요청 | 상황 | 응답 |
| --- | --- | --- |
| `PUT /keys/{key}` + `{"value": "..."}` | 저장·덮어쓰기 성공 | `200` · `{"stored": true}` |
| `GET /keys/{key}` | 키에 저장된 값이 있음(빈 문자열 포함) | `200` · `{"value": "..."}` |
| `GET /keys/{key}` | 키가 없거나 만료됨 | `404` · `{"error": {"code": "KEY_NOT_FOUND"}}` |
| `GET /keys/{key}/exists` | 존재 확인(만료 시 `false`) | `200` · `{"exists": true/false}` |
| `DELETE /keys/{key}` | 키가 있었음 / 없거나 만료됨 | 각각 `200` · `{"deleted": true}` / `{"deleted": false}` |
| 해당 요청 | 잘못된 입력 | `400` · 공통 오류 본문 |
| 해당 요청 | 예상하지 못한 서버 내부 오류 | `500` · 공통 오류 본문 |

- API 응답에는 `Cache-Control: no-store`를 붙여 HTTP 중간 캐시의 저장과 서비스 내부 캐시의 동작을 혼동하지 않도록 한다.
- 결과 본문이 필요한 저장·삭제 응답에는 `200`을 사용한다. `204 No Content`는 본문이 없으므로 위 표의 해당 응답에는 사용하지 않는다.

## 영향과 남은 설계

- 빈 문자열 조회의 `200` 응답과 없는 키 조회의 `404` 응답은 다르다. 존재 확인에서 없는 키는 오류가 아니라 `200`과 `false`다. 삭제 시 없는 키도 `200`과 `false`로 구분한다.
- 이 결정 당시 정하지 않은 항목: 키의 경로 인코딩·추가 제한, HTTP 프레임워크, 오류 코드의 세부 목록, TTL 입력·실제 제거 방식, 무효화의 세부 방식, 동시성 구조와 배포 형태.
- 후속 [D-0004](0004-http-key-no-slash.md)에서 HTTP 키의 슬래시 제외를, [D-0005](0005-http-api-boundary.md)에서 추가 문자·인코딩·라우팅·본문 경계를 정했다. 3단계 원본 API 활용 사례는 [해당 단계 설계](../iterations/03-http-api/design.md#4-외부-사용-예제의-흐름과-실패)에 둔다.
- 단위 테스트와 외부 HTTP 기능 테스트에서 빈 키와 빈 값, 미존재·만료 키의 조회·존재 확인·삭제, 입력 오류를 각각 확인한다. 테스트 실행 결과는 아직 없다.

## 재검토 조건

HTTP 경로·데이터 표현이 실제 사용 사례를 지원하지 못하거나 만료·무효화 설계에서 다른 응답 계약이 필요한 경우 재검토한다.

## 배경과 판단 기준

3단계의 `PUT /keys/{key}`는 문자열 `value` 필드 하나만 허용한다. 보관 기간 설정을 이 본문에 추가하면 기존 입력 계약을 변경해야 한다. 만료·무효화 기능을 외부에서 사용할 수 있게 하면서 기존 저장 API의 동작을 유지하고, 오래된 만료 정보가 덮어쓴 값을 뜻밖에 제거하지 않도록 한다.

## 결정과 이유

- **TTL 입력:** 기존 `PUT`의 `{"value": "..."}` 계약은 변경하지 않는다. TTL 설정·갱신은 별도 연산으로 제공하고, TTL만 명시적으로 제거하는 연산도 제공한다. 구체적인 HTTP 경로·메서드·본문·성공/실패 응답은 4단계 설계에서 정한다.
- **단위·입력:** 외부 TTL 값은 양의 정수 초만 허용한다. `0`, 음수, 분수는 잘못된 입력으로 거부하며 기존 상태를 바꾸지 않는다. 입력의 구체적 표현·오류 코드는 설계에서 정한다.
- **저장·덮어쓰기:** 기존 `PUT`에서 TTL을 지정하지 않은 저장은 만료 없는 값을 저장한다. 같은 키를 다시 `PUT`하면 이전 TTL을 해제하고 최신 값으로 덮어쓴다. 이후 별도 TTL 설정 연산으로 새 보관 기간을 줄 수 있다. 지난 만료 정보가 새 값에 적용돼서는 안 된다.
- **명시적 무효화:** 키 단위 무효화는 기존 `DELETE /keys/{key}`로 수행하고 새 무효화 API는 추가하지 않는다. 삭제·만료 키의 외부 응답은 [D-0003](0003-http-response-contract.md)을 유지한다.

별도 TTL 연산은 기존 `PUT`과 TTL 설정을 **하나의 원자적 HTTP 요청으로 보장하지 않는다**. 두 요청 사이의 상태가 허용되지 않는 사용 사례라면 이 선택을 재검토해야 한다. 이는 5단계의 동시성 위험 점검·방어가 완료됐다는 의미가 아니다.

## 영향과 검증

4단계 요구사항·설계와 저장소/HTTP 연결에 새 TTL 설정·갱신·제거 동작이 필요하다. 기존 `PUT`의 본문 제한과 키·값·오류·`no-store` 계약은 유지한다. TTL이 있는 키에 일반 `PUT` 후 만료가 사라지는지, TTL만 제거해도 값이 유지되는지, 양의 정수 초 이외 입력에서 기존 값·만료 상태가 보존되는지, 만료·삭제 응답이 기존 계약과 맞는지 검증한다. 이 결정은 구현·테스트 완료가 아니다.

## 재검토 조건

값 저장과 TTL 지정의 원자성이 필요한 사용 사례가 생기거나, 분수·다른 단위의 TTL, 기존 만료 기한을 유지하는 덮어쓰기, 별도 무효화 동작이 필요해지면 재검토한다.

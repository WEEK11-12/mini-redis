## 배경과 판단 기준

[D-0005](0005-http-api-boundary.md)는 3단계에서 저장소의 순차 호출을 유지하기 위해 순차 `HTTPServer`를 선택했다. 5단계에서는 여러 HTTP 클라이언트의 접수·해석을 병렬화할 수 있으면서도 공유 캐시 명령의 처리 주체를 한 스레드로 유지할 경계를 정한다. 저장소에 대한 외부 사용은 HTTP 경로를 기준으로 하며, 여러 스레드가 같은 저장소 객체를 직접 호출하는 별도 API는 이번 보장 범위가 아니다.

## 결정과 이유

- HTTP 연결 접수·요청 해석은 별도 스레드에서 병렬 처리할 수 있다. 이 허용은 요청 해석의 처리량 목표나 특정 스레드·큐 구현을 확정하지 않는다.
- `HashTableStore`의 상태를 읽거나 바꿀 수 있는 모든 명령(조회·존재 확인·저장·삭제·TTL 설정/제거·만료 제거·주기 정리)은 **한 명령 실행 스레드**에서 차례로 처리한다. 조회 중 만료 제거가 가능하므로 조회도 예외로 두지 않는다. HTTP 요청 처리 스레드는 저장소를 직접 호출하지 않는다.
- HTTP 요청의 접수·해석을 병렬로 하더라도 공유 상태 명령의 완료 순서는 단일 실행 주체가 정한다. 네트워크 도착 순서의 처리를 보장하지 않는다. 기존 값 저장과 별도 TTL 요청 간 원자성은 [D-0006](0006-ttl-invalidation-contract.md)의 비보장 계약을 유지한다.
- 여러 스레드의 `HashTableStore` 직접 호출에 대한 안전성은 이번 범위에 포함하지 않는다. 명령 실행 외부의 저장소 직접 사용은 순차 호출 전제다.

기존 순차 HTTP 서버를 유지하거나 요청 해석부만 병렬화할 구체적 방식, 명령 전달·응답 대기·종료 및 오류 처리와 정리 실행 시점은 5단계 설계에서 결정한다. 단일 스레드 실행을 단순 락 직렬화(요청마다 서로 다른 스레드가 락을 잡아 명령을 실행)와 혼동하지 않는다.

## 영향과 검증

[D-0005](0005-http-api-boundary.md)의 **순차 `HTTPServer` 실행 구조** 부분은 이 결정에 따라 재검토하며 다른 HTTP 계약은 유지한다. 요청 처리와 명령 실행 경계를 분리하는 경우, 요청 처리 스레드가 저장소에 직접 진입하지 않는지와 만료 정리가 같은 실행 스레드에서만 일어나는지 확인한다. 겹치는 HTTP 요청의 상태·응답이 유효한 명령 순서와 일치하는지, 기존 API의 상태·본문·`Cache-Control: no-store`와 2~4단계 회귀가 유지되는지 검증한다. 이 기록은 설계 세부·코드 변경이나 검증 완료를 의미하지 않는다.

## 재검토 조건

명령을 여러 실행 스레드에서 처리해야 할 필요가 생기거나, 직접 병렬 저장소 사용을 공식 지원하거나, 별도 TTL 요청과 저장을 하나의 원자적 요청으로 묶어야 하는 사용 사례가 확인되면 실행·저장소 계약을 다시 검토한다.

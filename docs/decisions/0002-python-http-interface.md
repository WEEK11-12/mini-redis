## 배경과 판단 기준

가벼운 범용 인메모리 캐시를 하루 안에 구현·검증해야 한다. 여러 애플리케이션 서버가 같은 캐시에 접근하는 사용 장면을 상정한다. C 수준의 최적화나 전용 캐시 프로토콜의 세밀한 조작보다, 과제의 비선택 항목을 구현해 동작을 검증할 수 있는지가 우선이다.

## 검토한 선택지

- **언어:** C 또는 Python. C의 성능·메모리 제어 가능성보다 이번 범위의 구현·검증 가능성을 우선한다. 성능 차이를 측정한 결정은 아니다.
- **외부 접근:** 각 앱에 저장소 라이브러리를 내장하는 방식만으로는 별도 프로세스가 동일한 메모리 캐시를 공유할 수 없다. 네트워크로 요청하는 HTTP API를 선택한다. 별도 전용 명령 프로토콜은 이번 선택에 포함하지 않는다.

## 결정과 영향

1. 핵심 저장소와 외부 인터페이스를 **Python**으로 구현한다. 해시 테이블은 과제에 따라 직접 구현하며 Python의 내장 사전을 핵심 저장소로 대신하지 않는다.
2. 여러 애플리케이션에서 접근할 수 있도록 **HTTP API**를 제공한다. 클라이언트 라이브러리를 나중에 덧씌울 수는 있지만 이번 결정의 필수 산출물은 아니다.
3. HTTP 요청 처리와 저장소 내부 구현의 경계를 둔다. 기본 연산의 엔드포인트와 응답 형식은 후속 [D-0003](0003-http-response-contract.md)에서 정했다. 프레임워크, 런타임 버전, 동시성 구조와 배포 방식은 이후 설계에서 정한다. ‘별도의 전용 캐시 서버를 정교하게 만든다’는 범위 확정도 아니다.

## 검증 및 재검토 조건

- 외부 HTTP 호출에서 저장·조회·존재 확인·삭제 및 빈 값과 미존재의 구분을 확인한다. 과제의 API 응답 재사용 사례와 캐시 미사용 대비 성능 비교를 실제로 실행한다.
- 구현 중 필수 기능과 동시성 요구를 충족하기 어렵거나 측정 결과가 다른 구현을 요구하면 기술·인터페이스 선택을 재검토한다.

## 기록 규칙

- 다른 작업 단위에도 영향을 주거나 나중에 바꾸는 비용이 큰 선택 중, 선택 이유를 다시 이해할 가치가 있는 것만 별도 기록한다. 오래 고민했거나 이후 주요 의존성이 될 선택에 집중한다.
- 한 단위 안에서 끝나는 세부 요구사항·설계·구현·테스트는 해당 이터레이션에 남긴다. 연결된 기본 계약의 세부 사항은 기존 결정에 모으고, 단순한 진행·수정 이력은 새 결정으로 만들지 않는다.
- 결정 문서와 이터레이션 문서에 같은 본문을 복제하지 않는다. 결정에는 선택 이유와 영향, 이터레이션에는 적용 범위·실제 설계·구현·검증을 적고 서로 링크한다.
- 모든 기록은 필수 `카테고리` 필드로 주된 결정 영역을 표시하고, 목록에도 같은 분류를 적는다. 카테고리와 관계없이 결정 번호는 전체에서 연속으로 부여하고 기존 식별자는 유지한다.
- 여러 영역에 걸친 결정은 결정할 질문이 속한 주 카테고리 하나를 정하고, 다른 영역에 대한 영향은 본문에 적는다. 같은 결정을 카테고리별로 중복 기록하지 않는다.
- 배경에는 현재 목표·제약·판단 기준과 해당 결정에 직접 필요한 근거를 쓴다.
- 파일명은 `0004-<topic>.md`처럼 고유한 연속 번호와 영어 소문자 주제를 사용한다. 새 번호는 기존 기록을 확인한 뒤 부여한다.
- 상태는 `제안`, `채택`, `기각`, `보류`, `대체됨` 중 하나다. 선택 확정 전에는 `제안`이다.
- 선택이 확정되면 `채택`으로 전환하고 목록도 갱신한다. 날짜·선택 이유·확인 근거를 지어내지 않는다.
- 실질적인 대안만 비교한다. 대안이 없거나 이미 정해진 원칙이라면 그 사실을 적는다. 억지로 후보를 만들지 않는다.
- 채택된 기록은 이후 새 선택으로 대체할 수 있다. 이전 기록을 `대체됨`으로 표시하고 새 기록과 양방향 연결한다.
- 거절·보류한 중요한 제안도 맥락이 필요하면 남긴다. 모든 사소한 편집을 기록할 필요는 없다.

## 카테고리

| 카테고리 | 주된 결정 대상 |
| --- | --- |
| 프로젝트 진행 | 역할 분담, 반복 방식, 문서·협업 컨벤션 |
| 요구사항 | 제작 목표, 구현 범위, 기능·품질의 완료 조건 |
| 설계 | 아키텍처, 인터페이스 계약, 데이터·동시성·만료 정책 |
| 구현 | 구현 기법, 구체적 라이브러리·도구 선택, 코드 구성 |
| 검증 | 테스트 전략, 검증 도구·환경, 성능 측정 방법 |

## 양식

```markdown
# D-0004: <결정 주제>

- 카테고리: <프로젝트 진행 / 요구사항 / 설계 / 구현 / 검증 중 하나>
- 상태: 제안
- 작성일: YYYY-MM-DD
- 결정일: 미결정
- 결정자: 사용자
- 확인 근거: 사용자 확인 전
- 관련 문서: <요구사항·설계 등 상대 링크>
- 대체 관계: 없음

## 배경과 결정할 질문
<무엇을 왜 지금 정해야 하는가>

## 판단 기준
<목표, 제약, 중요하게 보는 비용과 위험>

## 대안 비교
| 대안 | 이점 | 비용·위험 | 적합한 조건 |
| --- | --- | --- | --- |
| <대안> | ... | ... | ... |

## 권고안 (채택 전)
<검토 중인 권고와 이유. 채택된 결정과 구분>

## 결정과 이유
<선택 전에는 미결정. 확인되지 않은 이유는 미확인>

## 영향과 검증
<바뀌는 범위, 감수하는 한계, 확인할 결과>

## 재검토 조건
<어떤 가정·요구가 바뀌면 다시 판단할 것인가>
```

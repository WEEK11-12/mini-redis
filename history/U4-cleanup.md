# U4 — 능동 청소·진행 커서·스레드 생명주기

기록 작성 당시 상태: 로컬 구현·테스트 완료, 핵심 코드 사용자 검토 대기. 커밋·푸시 미실행. 관련 요구 R-06·R-07·R-10, 테스트 T-11·T-12와 청소/갱신 겹침 사례. U5 전체 동시 요청 검증을 완료했다는 뜻은 아니다.

## 먼저 합의한 여섯 항목

사용자가 다음을 필수 테스트로 확정하고 구현을 요청했다.

1. 만료 키만 삭제하고 유효 키 보존.
2. 회차당 최대 100키·100버킷 방문 제한.
3. 여러 번 나누어도 이전 위치부터 뒤쪽까지 검사.
4. 커서 대상 삭제·테이블 확장 후 잘못된 노드 접근 없이 진행.
5. TTL 갱신과 청소가 겹쳐도 새 값 보존.
6. 스레드 하나만 시작하고 종료 신호로 정상 종료.

## 실제 코드 배치와 선택

- mini_redis/store.py의 cleanup: 공용 저장소 락 안에서 청소 한 회분을 실행한다. CleanupResult로 키 검사 수·버킷 방문 수·삭제 수를 반환해 제한을 검증한다. 공개 HTTP 통계 API를 추가한 것이 아니다.
- 커서: 버킷 번호·다음 노드·앞 노드. 앞 노드를 기억하면 긴 체인의 삭제를 위해 매번 시작부터 재탐색하지 않아도 된다. 그 대신 삭제·삽입 때 앞 노드 참조까지 보정해야 한다.
- _unlink: 요청 삭제·접근 만료·청소 삭제가 공통 사용한다. 커서 대상 삭제면 다음 노드로, 앞 노드 삭제면 그 이전 노드로 보정한다. 진행 중 버킷의 새 헤드 삽입도 앞 노드 정보를 고친다.
- _resize: 새 배열로 교체한 뒤 커서 전체를 처음으로 초기화한다. 옛 노드를 계속 검사하지 않는다.
- mini_redis/expiration.py: ExpirationWorker가 Event.wait(0.1) 후 cleanup을 반복한다. import·생성만으로 시작하지 않으며 start를 반복 호출해도 같은 인스턴스에서 스레드를 추가하지 않는다.
- stop은 Event를 설정하고 관리용 락을 놓은 뒤 join한다. 저장소 락을 잡지 않는다. 작업 중이면 끝난 뒤 종료하고, 대기 중이면 신호에 깨어난다.

스레드 인스턴스는 시작/종료 한 주기를 소유한다. 종료한 같은 인스턴스를 start해서 재시작하는 기능은 제공하지 않는다. 새 서버 실행은 새 작업자를 만든다. 실제 서버 진입점과 finally 연결은 U6에 남아 있다.

100ms는 작업 사이 대기 목표다. 락 대기·청소 시간이 더해지므로 정확한 주기나 100ms 내 전부 회수를 보장하지 않는다. 회차당 버킷 수는 같은 버킷에서 이어 시작한 경우에도 1회로 센다. 작은 테이블은 한 바퀴를 돌면 회차를 끝내 같은 키를 반복 검사하지 않는다. 반복 확장은 뒤쪽 회수를 지연시킬 수 있다.

## 실제 실패와 구현 결과

명령: `python -m unittest discover -s tests -v`.

청소 테스트를 먼저 추가한 첫 실행은 기존 26개와 새 12개, 총 38개였다. 하위 사례 포함 오류 13개·종료 코드 1이었다. 원인은 cleanup 메서드와 expiration 모듈 미구현이다. 삭제 알고리즘에서 발견한 실제 제품 버그라고 표현하지 않는다.

청소·커서 보정·작업자 구현 후 38개가 통과했다. 이어 테스트 자체의 검출력을 검토했다. 동시 작업에서 예외가 별도 스레드에만 출력되고 테스트가 통과하지 않도록 예외·청소 결과를 수집하고 실제 삭제 1개도 확인하게 보완했다. 갱신 선행 순서와 설정 경계 사례도 추가했다. 최종 전체 41개 PASS, 종료 코드 0이다. 이 중 U4는 15개, 기존 U1~U3 회귀는 26개다.

## 여섯 항목을 어떻게 확인했나

| 항목 | 실제 입력·절차 | 결과 |
| --- | --- | --- |
| 만료/유효 구분 | 가짜 시간에서 만료·유효 TTL·무기한을 섞음 | 만료 1개만 제거, 유효 2개 유지 |
| 키 수 제한 | 256버킷에서 같은 버킷의 101개 만료 키 | 첫 회차 검사·삭제 100개, 다음 회차 나머지 1개 |
| 빈 버킷 제한 | 확장 후 모든 키 삭제, 빈 버킷 256개 | 각 회차 방문 100개, 위치 100→200→44 |
| 순회 진행 | 200개 만료 키와 유효 키, 제한된 청소 반복 | 만료 200개 회수, 유효 1개 유지 |
| 위치 변경 | 부분 청소 후 대상·앞 노드 삭제, 접근 만료, 새 헤드 삽입, 확장 | 연결·키 개수 보존, 옛 커서 초기화 |
| 청소 선행 갱신 | 만료 판정 직후 락을 가진 청소를 Event로 대기, 갱신의 락 진입 시도 확인 | 갱신은 대기, 청소 후 새 값 저장·보존 |
| 갱신 선행 | 만료 키에 새 TTL 저장 뒤 청소 | 새 만료 시각 전 삭제 0개, 새 경계에서 삭제 1개 |
| 작업자 생명주기 | import시 Thread.start 감시, start 두 번, 요청 없는 실제 작업자 | import 시작 없음, 같은 스레드, 만료 키 회수 |
| 종료 | 간격을 60초로 둔 대기 상태에서 stop, 테스트 스레드가 저장소 락 보유 | 2초 안에 종료, 간격 종료나 저장소 락을 기다리지 않음 |

2초는 정확한 응답 성능 목표가 아니라 테스트가 무한정 멈추지 않도록 둔 상한이다. 실제 시간의 정밀한 100ms 주기나 성능 향상을 측정한 것은 아니다. 스레드 순서는 임의 sleep 대신 Event·실제 락 진입 관측으로 맞췄다.

cleanup의 양의 정수 검사량과 작업자 주기의 양수·유한 숫자 조건도 잘못된 입력으로 상태가 바뀌지 않는지 확인했다. 설정 인자는 단위 테스트에서 작은 한도·긴 대기를 재현하려는 용도이며 기본 운영값은 합의한 100키·100버킷·0.1초다.

## 함께 읽을 핵심 코드

1. cleanup의 with self._lock 안에서 _expired와 _unlink가 연속 실행되는 부분.
2. _unlink의 커서 보정과 set의 새 헤드 삽입 보정.
3. ExpirationWorker._run의 Event.wait와 stop의 join 위치.

## 남은 범위

U5의 다양한 동시 요청·확장 조합, U6의 Flask·Waitress와 진입점 정리, U7 캐시·부하·성능은 아직 미실행이다. 작업자 내부의 예상 밖 예외 발생 시 자동 재시작은 구현하지 않았다. 실제 서버에서 종료·오류 전파를 연결하는 것은 U6에서 확인한다. 단위 테스트 통과가 무제한 입력·실행 스케줄에서 안전하다는 증명은 아니다.

## 필수 흐름에 집중한 버그·부하 검증

사용자가 검사 수를 늘리기보다 필수 동작을 함께 확인하고 작업 종료 시 과정을 요약하길 요청했다. 이번에는 아래 두 실행만 했다. 기존 41개 전체 테스트는 재실행하지 않았다. 제품 코드 수정 없이 실제 결과를 확인했다.

### 1. 버그 테스트 — 멈춘 위치·중간 삭제·연결 보존

명령: `python -m unittest tests.test_cleanup_focus -v`

- 입력: 같은 버킷의 A → q → a. A와 a는 무기한, q만 TTL 1ms.
- 첫 회차: 키 1개 검사 후 중단. 삭제 0개, 다음 노드 q와 앞 노드 A 유지.
- 시간을 만료 경계로 이동한 다음 회차: q만 삭제, A → a 연결, 노드 수 2.
- 다음 회차: a부터 이어 검사. 삭제 0개, 유효한 두 값 그대로.
- 실제 결과: 테스트 1개 PASS, 종료 코드 0. 이 입력에서 제품 버그가 발견되지 않았으므로 수정 내역은 없다.

### 2. 부하 테스트 — 실제 청소 작업자와 10,000개 키

명령: `python -m tests.load_cleanup`

- Python 3.13.14, Windows-11-10.0.22631-SP0.
- 문자열 키 10,000개, 값은 각 UTF-8 128바이트, 버킷 16,384개.
- 만료 7,000개·유효 3,000개로 상태를 고정하기 위해 주입 시간을 사용했다. 실제 작업자·0.1초 대기·락·커서·삭제는 그대로 실행했다. 실제 시간을 1ms 기다려 만료시킨 실험과 구분한다.
- 완료 신호를 기다리는 30초는 무한 대기를 막는 테스트 상한이며 성능 합격 목표가 아니다.
- 청소가 끝난 직후 먼저 노드 수 3,000을 확인했다. 이어 유효 3,000개의 원래 값을 전부 조회하고 만료 키가 반환되지 않는지 확인했다. 조회로 만료 노드를 치운 뒤 청소 성공으로 오해하지 않도록 순서를 정했다.

| 실제 측정 | 결과 |
| --- | --- |
| 판정 | PASS / 종료 코드 0 |
| 청소 회차 | 164회 |
| 회수한 만료 키 | 7,000개 |
| 보존한 유효 키·값 | 3,000개 |
| 작업자 시작~회수 완료·종료 | 17.941초 |
| 한 회차의 최대 키 검사 | 78개, 제한 100개 이하 |
| 한 회차의 최대 버킷 방문 | 100개, 제한 100개 이하 |
| 한 회차 청소 호출의 최대 관측 시간 | 0.273ms |

시간은 단일 실행의 관측값이고 처리량 한계나 p99·HTTP 응답 성능이 아니다. 청소 호출 시간은 이 실험의 경합 없는 호출을 측정했다. 동시 요청을 보내거나 메모리 한계까지 밀어붙인 스트레스 테스트는 하지 않았다.

100ms마다 100버킷씩 검사하므로 16,384버킷을 한 바퀴 돌려면 약 164회가 필요하다. 따라서 전체 회수 시간이 100ms보다 긴 것은 이 구조에서 예상되는 결과다. 실제 주기에는 대기 스케줄링과 작업 시간이 더해진다.

### 작업 종료 요약

- 정상 흐름: 다음 위치 유지 → 만료만 제거 → 앞뒤 연결 보존 → 제한된 회차 반복을 확인했다.
- 발견한 제품 버그·수정: 이번 두 실행에서는 없음.
- 원본 측정과 회차별 수치: [부하 결과 JSON](U4-cleanup-load-result.json).
- 코드: tests/test_cleanup_focus.py, 명시적으로 실행하는 tests/load_cleanup.py. 부하 스크립트는 일반 unittest 검색에 포함하지 않는다.
- 남은 점: 유입·갱신 요청이 있는 부하, HTTP 지연, 한계 스트레스는 미검증이다. 사용자 확인 후에만 다음 검증 범위를 정한다.

# U5 — 요청이 겹칠 때 락과 데이터 일관성

기록 작성 당시 상태: 합의한 필수 세 항목을 모두 확인했다. 아래 첫 실행과 후속 필수 실행을 구분해 기록한다. 제품 코드 변경·커밋·푸시 없음. 관련 요구 R-07, 테스트 T-13의 일부다.

## 먼저 확인한 개념과 범위

여러 요청은 겹쳐 들어올 수 있지만 저장소 작업은 공용 락 안에서 하나씩 실행한다. 락은 동시 접근을 막으며 요청 도착 순서대로 실행되는 FIFO까지 보장하지 않는다. 사용자와 이 차이를 확인한 뒤 검증을 요청받았다.

U5 필수 범위는 다른 키의 저장·조회·삭제, 동시 신규 저장 중 확장, 요청과 청소의 겹침이다. 첫 실행에서는 첫 사례만 확인했고, 사용자 정정 후 남은 필수 항목까지 실행했다. 모든 경우나 스케줄을 검증했다고 표현하지 않는다.

## 기대 동작과 입력

- 작업 스레드 4개가 각각 서로 다른 키 2개를 저장: 총 8개와 정확한 값.
- 각 스레드가 자신의 키를 조회: 저장한 값과 일치.
- 각 스레드가 첫 번째 키 하나를 삭제: True, 남은 4개와 그 값 보존.
- 작업들은 저장소 락을 사용하고 동시에 보호 구간 안에 2개가 들어가지 않음.

키 8개는 첫 확장 경계인 13개보다 작다. 이 사례에서는 확장이나 TTL을 섞지 않아 실패 원인을 좁혔다. 값 조회·삭제는 각 단계의 저장 완료를 확인한 뒤 진행한다. 같은 키에 대한 순서 의존 결과를 단정하지 않는다.

## 실제 절차

코드: tests/test_concurrency.py.

1. 실제 저장소 락을 유지한 관찰 래퍼를 테스트에만 연결한다. 제품 코드는 바꾸지 않는다.
2. 테스트 주 스레드가 원래 락을 잠시 보유한다. Barrier로 작업 스레드 4개를 출발시킨다.
3. 네 스레드가 모두 락 진입을 시도했음을 Event로 확인한다. 이때 내부 진입 0회, 완료한 작업 0개를 확인한다.
4. 테스트가 락을 반환한 뒤 저장·조회·삭제·최종 조회를 단계별로 완료한다. Future.result로 작업 스레드의 예외를 테스트 주 스레드에 전달한다.
5. 서로 다른 호출 스레드 4개, 저장소 진입 총 30회, 관찰한 최대 동시 진입 1개를 확인한다. 진입 횟수는 8회 저장 + 8회 조회 + 4회 삭제 + 8회 최종 조회 + 2회 노드 수 확인이다.

관찰 래퍼는 원래 Lock의 acquire/release를 그대로 사용한다. 테스트가 mutex의 구현 자체를 증명하는 것은 아니며, 이번 호출 경로가 그 락에 진입하고 의도한 결과를 보존하는지 검사한다. 3초 timeout은 무한 대기를 막는 테스트 가드이지 응답 성능 목표가 아니다.

## 실행·실제 결과

명령:

```powershell
python -m unittest tests.test_concurrency.ConcurrencyTests.test_t13_distinct_keys_wait_then_store_read_delete -v
```

테스트 1개 PASS, 종료 코드 0.

| 확인 | 실제 결과 |
| --- | --- |
| 락 반환 전 | 4스레드의 진입 시도, 내부 진입 0회, 완료 0개 |
| 저장·첫 조회 | 8개 모두 정확한 값 |
| 삭제·최종 조회 | 삭제 4개 True, 남은 4개 값 보존, 삭제 키 None |
| 보호 구간 | 30회 진입, 최대 동시 진입 1개, 마지막 활성 0개 |

제품 버그는 발견되지 않았다. 따라서 구현 수정·수정 후 재검증을 꾸미지 않는다. 기존 전체 테스트와 부하 테스트는 이번에 재실행하지 않았다.

## 이번 작업 요약과 다음 논의

공용 락이 요청을 대기시키고 반환 후 작업들이 끝나는 것, 다른 키 데이터와 노드 수가 유지되는 것을 한 사례에서 확인했다. 이후 아래 후속 실행에서 확장과 청소 겹침도 확인했다. HTTP 동시 연결, 같은 키의 모든 실행 순서, 최대 부하·교착 상태의 부재는 아직 검증한 것이 아니다.

## 남은 필수 항목 실행과 단위 요약

사용자는 검사 개수를 하나로 제한한 것이 아니라, 꼭 확인해야 할 항목은 모두 확인하되 선택적 검사를 늘리지 말라는 뜻이라고 정정했다. 이 원칙을 AGENTS에도 반영했다.

### 신규 저장과 확장

명령: `python -m unittest tests.test_concurrency.ConcurrencyTests.test_t13_new_writes_preserved_across_resize -v`

4개 스레드가 Barrier에서 출발해 각각 10개 키를 저장했다. 실제 결과는 노드 40개, 버킷 64개, 40개 값 모두 일치. 13번째·25번째 신규 키에서 필요한 확장을 거친 상태를 확인했다. 테스트 1개 PASS, 종료 코드 0이다. 모든 실행 스케줄을 재현했다는 의미는 아니다.

### 청소와 갱신 겹침

이미 U4에서 만든 필수 테스트를 재사용했다. 같은 시나리오의 테스트를 새로 중복 작성하지 않았다.

명령: `python -m unittest discover -s tests -p test_cleanup.py -k renewal_waits_for_atomic_check_and_delete -v`

청소가 락 안에서 만료 여부를 확인한 지점에 Event로 멈추고 갱신 요청의 진입 시도를 관찰했다. 갱신은 기다렸고, 청소 삭제 뒤 새 값과 새 TTL이 저장됐다. 실제 청소 삭제 1개, 새 값 조회 성공, 노드 수 1. 테스트 1개 PASS, 종료 코드 0이다.

### 단위 종료 요약

| 필수 항목 | 결과 |
| --- | --- |
| 다른 키 요청과 락·저장·조회·삭제 | 앞선 첫 실행 PASS |
| 여러 신규 저장과 테이블 확장 | 이번 실행 PASS |

제품 버그는 발견되지 않았고 제품 코드 수정도 없었다. 이번에는 남은 필수 테스트 두 개만 실행했다. 전체 테스트나 추가 부하는 재실행하지 않았다. 커밋·푸시는 하지 않았다. 다음 U6에서는 Flask·Waitress 입력 변환·저장소 연결·실제 서버의 시작/종료를 구현하며 필수 검증을 먼저 정한다.

# 단위별 구현·테스트 이력

실행하는 코드는 tests/, 기대 동작·검증 계획은 docs/, 실제 구현·실패·수정·재검증 과정은 history/에 둡니다. 문서가 있다는 이유로 실행·통과를 주장하지 않습니다.

## 단위별 상태

| 단위 | 내용 | 실제 결과 | 사용자 확인 |
| --- | --- | --- | --- |
| [U1](U1-storage.md) | 저장·조회·삭제·충돌 | 순차 테스트 6개 통과 | 연결 보존 이해 확인, 다음 단위 진행 요청 |
| [U2](U2-input-and-resize.md) | 입력 검사·FNV 검산·확장 | 10개 추가, U1 포함 총 16개 통과 | 결과 설명 후 다음 작업 진행 요청 |
| [U3](U3-ttl.md) | TTL·접근 만료 | 10개 추가, 총 26개 통과 | 만료/청소 차이 확인, 다음 단위 진행 요청 |
| [U4](U4-cleanup.md) | 청소·커서·생명주기 | 기존 전체 41개 통과, 이후 집중 버그 1개·10,000키 부하 별도 통과 | 정상 흐름과 필수 결과 설명 후 U5 진행 요청 |
| [U5](U5-concurrency.md) | 요청 겹침·락·일관성 | 필수 세 항목 PASS, 청소 겹침은 기존 테스트 재사용 | 단위 결과 요약 보고 |
| U6 | Flask·Waitress HTTP | 미구현·미실행 | 해당 단위 전에 논의 |
| U7 | 캐시 활용·성능 비교 | 미구현·미실행 | 해당 단위 전에 논의 |

각 파일은 해당 단위의 실행 당시 기록입니다. 이전 단위의 미구현 목록이 현재도 미구현이라는 뜻은 아니며 최신 상태는 [WORKLOG](../WORKLOG.md)와 [테스트 계획](../docs/TESTING.md)을 확인합니다. 후속 수정·회귀 검증은 해당 단위 파일에 구분해서 이어 적습니다. 아직 실행하지 않은 단위의 성공 기록을 미리 만들지 않습니다.

현재 커밋 검토에서 자동 테스트 44개를 한 번 재실행해 통과했다. 아래 개별 이력은 각 실행 당시 결과이며 10,000키 부하를 이번에 다시 실행한 것은 아니다.

## 기록 순서

1. 목적·관련 요구/테스트 ID·사용자와 합의한 기대 동작
2. 실제 입력·실행 환경·명령
3. 기대 결과와 실제 결과, 판정
4. 원인·검토한 해결책·선택 이유·수정
5. 재검증 결과·회귀 검사
6. 사용자와 확인한 내용·남은 한계·다음 논의

미구현으로 인한 예상 실패, 실제 제품 버그, 환경 오류, 의도적인 고장 검출 실험은 구분합니다. 실패가 없으면 실패나 수정 이력을 만들어내지 않습니다. 초기 수치·예상 성능과 실측 결과도 구분합니다.

# 6. Python의 메모리 관리와 영속성

## 언어 변경이 해결한 것과 남긴 것

이전에는 C·MSVC로 문자열·노드를 직접 할당하고 해제하려 했다. 현재는 Python + Flask + Waitress로 변경했다. 해시 충돌·TTL·동시 요청·캐시와 테스트가 이번 학습의 중심이므로 수동 메모리 관리 부담을 줄이기 위한 선택이다.

Python도 RAM을 사용한다. C와 같은 성능·메모리 비용이라는 뜻은 아니며 언어 선택만으로 개발 속도나 성능 우위를 확정하지 않는다. 문자열은 불변 객체이므로 조회한 문자열을 C의 임시 버퍼 주소처럼 다룰 필요가 없다. 실제 저장소는 dict로 대신하지 않고 직접 만든다.

## 자동 관리로도 남는 문제

- 삭제한 노드를 청소 커서가 계속 참조하면 불필요하게 남거나 잘못된 검사를 할 수 있다.
- 노드·키·값과 JSON 처리에는 메모리가 필요하다. 입력 제한은 전체 저장소 용량 제한이 아니다.
- 잘못된 입력은 변경 전에 거부해야 한다. 자동 메모리 관리가 논리 오류를 막지 않는다.
- 메모리 부족·리해싱 실패의 복구 보장은 별도로 정의하고 검증해야 한다. 입력 검증 실패와 MemoryError를 혼동하지 않는다.

같은 키의 값을 바꾸거나 노드를 삭제하는 작업은 락 안에서 연결·키 개수·TTL·커서를 함께 유지한다. 전체 리해싱의 일시적 메모리와 대기 시간도 측정 대상이다.

## 종료 후 복구는 별개

프로세스의 메모리를 올바르게 정리해도 디스크에 데이터를 저장한 것이 아니다. 이번 초기 구현에는 영속성이 없으므로 정상 종료·강제 종료 모두 재시작하면 빈 저장소다.

실제 Redis의 RDB 스냅샷은 특정 시점의 상태를, AOF는 변경 명령을 기록하는 방식이다. 각각 저장 비용·디스크 반영 정책·재생 시간·손실 범위가 다르다. 필수 기능 검증 후 선택 과제로 검토하며 지금 복구를 보장하지 않는다.

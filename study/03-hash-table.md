# 3. 키를 찾는 해시 테이블

키를 하나씩 전부 비교하면 데이터가 많아질수록 조회 비용이 커집니다. 해시 테이블은 키를 숫자로 바꾸고 그 숫자로 저장 위치를 정해 후보를 줄입니다.

## 조회의 흐름

```text
키의 바이트열
  → 해시 함수
  → 해시값 % 버킷 수
  → 해당 버킷
  → 실제 키 비교
  → 일치하는 값 또는 없음
```

**해시값이나 버킷 번호가 같다고 같은 키는 아닙니다.** 마지막에 실제 키가 일치하는지 확인해야 합니다. 같은 키를 다시 저장하면 값 교체이고, 다른 키가 같은 위치로 계산되면 충돌입니다.

평균 O(1) 탐색이라는 설명은 적절한 분산과 적재율을 가정한 항목 수 기준의 설명입니다. 문자열 해시 계산과 비교·복사에는 문자열 길이에 따른 비용이 추가됩니다. 충돌이 한 버킷에 몰리면 그 버킷의 조회는 길어집니다.

## FNV-1a 64비트

Mini Redis는 FNV-1a 64비트를 사용하기로 했습니다. 문자열의 각 바이트를 현재 해시값에 XOR하고 정해진 소수를 곱하는 과정을 반복합니다.

| 항목 | 64비트 FNV-1a 값 |
| --- | --- |
| 초기값(offset basis) | 14695981039346656037 |
| 곱하는 소수(FNV prime) | 1099511628211 |
| 반복 순서 | 바이트 XOR → 소수 곱셈 |
| 계산 범위 | 64비트 범위, 즉 2의 64제곱을 법으로 하는 연산 |

선택 이유는 구현이 작고 계산 과정을 설명·검증하기 쉽기 때문입니다. Python은 정수 크기가 자동 확장되므로 각 곱셈 결과에 64비트 마스크를 적용하고 UTF-8 바이트를 처리해야 합니다. 검증할 때는 FNV-1과 FNV-1a의 연산 순서를 혼동하지 않았는지도 확인해야 합니다.

FNV는 비암호학적 해시입니다. 악의적으로 고른 키의 충돌을 막는 보안 수단으로 보지 않습니다. 실사용 공개 서버의 입력 제한과 보호 정책은 별도 문제입니다.

## 충돌 처리: 체이닝과 개방 주소법

| 방식 | 충돌한 항목의 위치 | 삭제 시 생각할 점 |
| --- | --- | --- |
| 체이닝 | 같은 버킷의 목록에 보관 | 목록의 연결과 청소 커서를 보존하고 노드를 분리 |
| 개방 주소법 | 정해진 탐색 규칙으로 다른 칸에 보관 | 삭제로 다른 키의 탐색 경로가 끊기지 않아야 함 |

이번 프로젝트는 **버킷 배열 + 연결 리스트 체이닝**을 선택했습니다. 충돌한 항목과 삭제 과정을 직접 따라가기 쉽기 때문입니다. 개방 주소법은 연속된 공간을 사용해 메모리 접근이나 할당 비용 측면에서 유리할 수 있지만, 삭제 표시와 탐색 규칙을 함께 관리해야 합니다.

다음은 해시 계산 결과를 가정한 그림입니다. 실제 FNV 결과를 나타내는 테스트 데이터가 아닙니다.

```text
bucket[2] → (cat, A) → (dog, B) → (bird, C)
```

`dog`를 지울 때는 `cat`의 다음 항목이 `bird`를 가리키게 한 다음 `dog` 노드를 목록에서 분리합니다. Python의 메모리 회수는 런타임이 맡지만 청소 커서 등 불필요한 참조는 남기지 않아야 합니다. 첫 항목이면 버킷의 시작 주소를, 끝 항목이면 이전 항목의 다음 주소를 바꿔야 합니다.

## 적재율과 확장

```text
적재율 = 저장된 키 개수 / 버킷 개수
```

사용 중인 버킷의 비율이 아닙니다. 체이닝에서는 한 버킷에 여러 항목이 있으므로 적재율이 1보다 커질 수도 있습니다.

우리의 초기 정책은 버킷 16개이며, **신규 키를 넣어 적재율이 0.75를 초과하면 2배 확장**하는 것입니다.

| 저장 키 수 | 버킷 수 | 결과 |
| --- | --- | --- |
| 12 | 16 | 12/16 = 0.75, 유지 |
| 13번째 신규 키 | 16 → 32 | 기준 초과로 확장 |
| 기존 키 덮어쓰기 | 유지 | 키 수가 늘지 않음 |

버킷 수가 바뀌면 `해시값 % 버킷 수`도 바뀔 수 있으므로 기존 항목을 새 버킷에 다시 배치해야 합니다. 이것이 리해싱입니다. 단순히 배열 뒤에 빈칸만 붙여서는 조회 위치가 맞지 않습니다.

0.75와 2배는 이번 프로젝트의 초기 선택입니다. 체이닝의 필수 공식이나 실제 Redis의 고정 정책을 뜻하지 않습니다. 공간을 늘려 평균 탐색 후보를 줄이려는 선택이며, 확장해도 모든 충돌이 사라지는 것은 아닙니다.

## 확장의 비용

새 버킷을 준비하고 항목을 재배치하는 동안 메모리와 실행 시간이 필요합니다. 이번에는 한 번에 재배치하는 기본 방식을 우선합니다. 공용 락 안에서 이 작업이 길어지면 다른 요청이 기다리므로 확장 중 응답 지연을 측정해야 합니다.

Python에서도 메모리 부족과 재배치 실패는 별도 문제입니다. 복구 보장과 실패 주입 범위는 확장 단위에서 확인하며, 리해싱 후 청소 커서는 처음부터 다시 시작합니다.

## 확인할 질문

- 다른 두 키가 같은 버킷에 들어갔는데 왜 기존 값을 덮어쓰면 안 되는가?
- 12번째 키와 13번째 신규 키의 차이는 무엇인가?
- 확장 직후 모든 키를 다시 조회해야 하는 이유는?

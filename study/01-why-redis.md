# 1. Redis는 왜 필요한가

프로그램의 객체나 맵에 값을 넣어도 RAM을 사용합니다. Redis를 이해하려면 메모리의 속도뿐 아니라 **누가 그 데이터에 접근하고 수명을 관리하는지**를 생각해야 합니다.

## 프로그램 내부의 값과 별도 저장소

한 웹 서버가 자신의 메모리에 상품 정보를 저장했다고 가정합니다. 그 서버는 다음 조회에서 값을 재사용할 수 있지만, 다른 웹 서버가 같은 메모리 공간을 직접 읽을 수는 없습니다.

```text
앱 서버 A → A의 로컬 맵
앱 서버 B → B의 로컬 맵
```

서버마다 사본이 있으면 원본 상품이 변경됐을 때 여러 사본을 갱신하거나 삭제해야 합니다. 별도 저장소를 두면 여러 앱이 같은 창구로 접근할 수 있습니다.

```text
앱 서버 A ─┐
           ├→ 공통 저장소
앱 서버 B ─┘
```

접근 지점이 모였다고 원본과 캐시의 일관성이 자동으로 해결되지는 않습니다. 어떤 시점에 값을 갱신하고 무효화할지는 앱과 저장소 사이의 약속이 필요합니다.

## Redis의 역할

Redis는 키로 데이터에 접근하고 여러 자료형과 명령을 제공하는 데이터 저장소입니다. 캐시, 세션, 카운터 등 여러 용도로 사용합니다. 이번 프로젝트는 그중 문자열 키·값의 저장과 만료, 외부 접근에 집중합니다.

예를 들어 캐시에 `product:7`의 응답을 보관하면 원본 데이터를 매번 다시 만들거나 가져오는 일을 줄일 수 있습니다. 로그인 세션처럼 일정 시간이 지나면 유효하지 않아야 하는 상태도 저장소의 만료 기능과 연결할 수 있습니다.

## 언제 유리하고 언제 비용이 생기는가

| 선택 | 이점 | 부담 |
| --- | --- | --- |
| 앱 안의 로컬 캐시 | 네트워크 왕복 없이 접근 | 여러 프로세스의 사본 관리 필요 |
| 별도 공통 저장소 | 여러 앱이 같은 상태와 만료 정책을 사용 | 네트워크, 연결, 장애 처리가 필요 |

단일 앱이 작은 값을 잠깐 재사용하는 상황에서는 로컬 캐시가 더 단순할 수 있습니다. 원본 조회가 이미 싸다면 별도 저장소를 거치는 비용이 더 클 수도 있습니다. Redis를 사용하면 항상 빨라진다고 주장할 수 없습니다.

## DBMS와의 관계

Redis를 둔다고 기존 DBMS가 반드시 사라지는 것은 아닙니다. 원본 데이터는 DBMS에서 관리하고 자주 조회하는 결과를 Redis에 보관하는 구성이 가능합니다. 데이터의 원본이 어디인지와 장애 시 어떤 정보를 복구해야 하는지를 먼저 정해야 합니다.

우리 팀은 두 사람 모두 Mini Redis와 Mini DBMS의 학습·구현 전 과정을 경험합니다. 이 저장소는 Redis의 학습과 구현을 다루고, DBMS는 별도 프로젝트로 이어갑니다.

## 스스로 설명해 볼 질문

- 앱 내부 맵과 별도 Redis 서버가 모두 RAM을 쓰는데도 쓰임이 다른 이유는?
- 앱 서버가 두 대가 됐을 때 캐시 사본 관리는 어떻게 달라지는가?
- 어떤 상황에서는 공통 캐시가 오히려 느릴 수 있는가?

## 1분 설명의 예

Redis는 여러 프로그램이 키로 데이터를 읽고 바꾸는 메모리 중심 저장소입니다. 앱 안의 맵도 RAM을 쓰지만, 별도 서버를 두면 여러 앱이 같은 데이터와 만료·삭제 기능을 공유할 수 있습니다. 캐시는 그 활용 방식 중 하나로, 자주 읽는 상품 응답을 재사용하면 원본을 매번 조회하는 일을 줄일 수 있습니다. 대신 네트워크 비용이 생기고, TTL만으로 원본 변경이 즉시 반영되지는 않아 무효화와 실패 처리가 필요합니다. 우리 Mini Redis는 이 중 문자열 저장·조회·삭제와 만료를 직접 만들고 HTTP로 제공하려는 프로젝트입니다.

위 문장은 설명용 예시입니다. 앱 한 대의 로컬 캐시와 앱 여러 대의 공통 저장소를 비교하고, 원본 변경 시 무슨 일이 생기는지 자신의 예로 말할 수 있는지 확인합니다.

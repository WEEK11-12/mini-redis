# 2. 키·값 저장과 캐시 활용

**키는 값을 찾는 이름이고, 값은 그 이름으로 보관하는 데이터**입니다. 상품 ID를 키에 포함하고 상품 응답을 값으로 저장하는 식으로 사용할 수 있습니다.

## 저장·조회·삭제의 의미

아래는 동작을 설명하는 예시이며, 현재 실행 가능한 Mini Redis 명령이나 HTTP API 명세가 아닙니다.

```text
SET product:7 "keyboard" → 저장
GET product:7            → "keyboard"
SET product:7 "mouse"    → 같은 키의 값 교체
GET product:7            → "mouse"
DEL product:7            → 삭제
GET product:7            → 값 없음
```

같은 키를 다시 저장하면 기존 항목을 갱신합니다. 서로 다른 키는 같은 값이라도 별도 항목입니다. 없는 키 조회는 None, 삭제는 bool을 반환하기로 했습니다. HTTP 응답은 [API 규격](../docs/API.md)에 확정한 내용을 따릅니다.

실제 Redis는 문자열 외에도 리스트·집합 등 여러 자료형을 제공합니다. **키를 찾는 해시 테이블**과 **값으로 제공하는 Hash 자료형**은 다른 층의 개념입니다. 이번 Mini Redis가 구현하는 값의 범위는 문자열입니다.

## 캐시는 저장소를 사용하는 방식

캐시를 쓴다는 것은 다시 계산하거나 조회할 결과를 보관해 재사용한다는 뜻입니다. Redis 안에 캐시 전용의 별도 공간을 반드시 만들어야 한다는 뜻은 아닙니다.

캐시를 먼저 확인하고 없으면 원본을 조회하는 흐름을 Cache-aside라고 부릅니다.

```text
앱이 상품 조회를 받음
  → 캐시 조회
      → Hit: 저장된 응답 반환
      → Miss: 원본 조회 → 캐시에 저장 → 응답 반환
```

| 경우 | 의미 | 원본 조회 |
| --- | --- | --- |
| Hit | 재사용할 값이 캐시에 있음 | 생략 가능 |
| Miss | 값이 없거나 만료돼 사용할 수 없음 | 필요 |
| 캐시 미사용 | 처음부터 원본을 조회 | 매번 수행 |

첫 Miss에는 원본 조회와 캐시 저장 비용이 함께 들어갑니다. 이미 채워진 캐시의 Hit와 구분해야 성능을 정직하게 비교할 수 있습니다.

## 원본 변경과 오래된 값

상품 가격이 바뀌어도 캐시에 이전 응답이 남아 있으면 오래된 값을 반환할 수 있습니다. 대표적으로 캐시를 삭제하고 다음 조회에서 다시 채우거나, 캐시 값을 직접 갱신하는 방법을 고려할 수 있습니다.

어느 시점에 삭제·갱신하는지와 작업 실패 시의 처리가 중요합니다. TTL을 짧게 설정했다고 원본 변경이 즉시 반영되지는 않습니다. 여러 요청이 겹치면 삭제 후 오래된 응답이 다시 저장되는 경우도 있어, 정책과 테스트가 필요합니다.

## Mini Redis의 문자열 계약

빈 키·빈 값을 허용하고 공백·줄바꿈 등 원문을 유지합니다. UTF-8 바이트로 키 1 KiB·값 1 MiB까지 받으며 문자열이 아닌 입력을 자동 변환하지 않습니다. Python 문자열은 불변 객체입니다. 이전 C의 NUL 종료 문자열·수동 해제 규칙을 현재 설계로 사용하지 않습니다.

해시 테이블로 키를 찾는 기능과 앱이 응답을 캐싱하는 기능은 분리합니다. 앱은 HTTP API로 저장소를 사용하고 원본 조회·캐시 사용 판단을 맡습니다. 계약의 상세와 남은 극단 입력은 [요구사항](../docs/REQUIREMENTS.md), 테스트는 [TESTING](../docs/TESTING.md)을 따릅니다.

# 4. 만료와 실제 청소의 차이

TTL은 값의 유효기간이다. 만료 시각 이후 값을 반환하지 않는 것과 메모리에서 노드를 실제 제거하는 것은 별개다. 아래는 Mini Redis의 규칙이며 실제 Redis의 모든 TTL 동작과 동일하다는 뜻은 아니다.

## 시간과 덮어쓰기

TTL은 양의 정수 밀리초다. 1500은 1.5초다. 생략은 무기한, null·0·음수·소수·문자열·bool은 잘못된 입력이다. 잘못된 입력은 기존 값·TTL을 바꾸지 않는다.

```text
저장 적용 시점의 단조 시간 + TTL = 만료 시점
현재 단조 시간 < 만료 시점  → 유효
현재 단조 시간 >= 만료 시점 → 만료
```

단조 시간은 컴퓨터의 날짜·시각 조정에 영향을 받지 않는 경과 시간 기준이다. 테스트는 시간 함수를 교체해 경계를 재현한다. TTL 없이 덮어쓰면 기존 TTL 제거, 새 TTL로 덮어쓰면 새 값과 새 만료 시각이다.

## 두 가지 만료 경로

- 접근 검사: 조회할 때 만료됐다면 삭제하고 None을 반환한다. 청소가 늦어도 오래된 값을 주지 않는다.
- 주기적 청소: 조회하지 않는 만료 키도 회수한다. 같은 프로세스의 청소 스레드 하나가 요청과 같은 락을 사용한다.

초기 목표 간격은 100ms다. 회차당 최대 100키 검사·100버킷 방문 중 먼저 도달한 한도에서 멈춘다. 100ms 안에 모든 만료 키가 사라진다는 보장이 아니다. 락 대기·빈 버킷·작업 시간에 따라 늦어질 수 있다.

## 다음 위치 기억하기

```text
5번 버킷: A → B → C → D
                 ↑ 다음 검사 노드
```

고정 순번 대신 버킷 번호와 다음 노드를 기억한다. C를 요청이나 청소가 삭제하면 먼저 D로 커서를 옮긴다. 버킷 끝이면 다음 버킷으로 가고, 리해싱하면 새 테이블 처음부터 다시 시작한다. 락 안에서 삭제와 위치 변경을 함께 한다. Python도 참조가 남으면 삭제한 노드가 살아 있을 수 있으므로 잘못된 커서를 방치하면 안 된다.

반복 확장은 뒤쪽 청소를 지연시킬 수 있다. 구조 변경이 멈추면 전체 순회를 계속하는지 검증한다. 실제 세부 절차는 [설계](../docs/DESIGN.md), 테스트는 [TESTING](../docs/TESTING.md)의 T-10~T-13을 따른다.

## 명시적 무효화

TTL은 시간이 지났다는 이유로, /delete는 사용자가 더 이상 쓰지 않겠다고 판단해서 제거한다. 가격 변경 직후 캐시를 삭제하면 남은 TTL과 무관하게 다음 요청에서 원본을 다시 읽도록 할 수 있다. 원본 갱신·조회·삭제의 순서와 실패 처리는 캐시 데모에서 논의한다.

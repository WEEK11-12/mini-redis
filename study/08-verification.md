# 8. 무엇을 검증해야 하는가

테스트 개수보다 **어떤 실패를 실제로 확인했는지**가 중요합니다. 모든 항목을 부하 테스트로 만들기보다는 작은 입력에서 정확성을 먼저 확인하고, 규모가 커질 때의 위험을 따로 검사합니다.

현재 이 문서의 모든 항목은 **NOT RUN: 실행 전 계획**입니다. 요구 ID·테스트 ID와 합의한 첫 단위는 [TESTING](../docs/TESTING.md)이 기준입니다. 이 문서는 검증 목적과 측정 방법을 설명합니다.

## 테스트를 나누는 기준

| 종류 | 확인하는 것 | 예시 |
| --- | --- | --- |
| 단위 테스트 | 작은 기능의 정확성 | 없는 키 조회, 충돌 체인의 중간 삭제 |
| 기능·통합 테스트 | 외부에서 끝까지 사용하는 흐름 | HTTP 저장 후 조회, 캐시 Miss 뒤 Hit |
| 부하 테스트 | 정한 규모에서의 처리량·지연·실패 | 여러 클라이언트가 일정 비율로 요청 |
| 스트레스 테스트 | 한계에 접근하거나 넘을 때의 동작 | 요청량·본문 크기를 늘렸을 때 안전한 실패 |
| 회귀 테스트 | 수정이 이전 동작을 깨뜨리지 않았는지 | TTL 수정 후 기본 저장·삭제 재확인 |

## 저장 엔진의 검증 순서

| 순서 | 입력·상황 | 기대 결과 |
| --- | --- | --- |
| 1 | 새 키 저장 후 조회 | 같은 값 반환 |
| 1 | 같은 키에 새 값 저장 | 최신 값 반환, 키 개수 유지 |
| 1 | 키 삭제 후 조회 | 없음으로 처리, 다른 키 보존 |
| 2 | 없는 키, 빈 문자열, 긴 문자열 | 합의한 정책에 맞는 결과, 비정상 종료 없음 |
| 3 | 서로 다른 키를 같은 버킷에 배치 | 각각의 값이 구별됨 |
| 3 | 충돌 목록의 첫·중간·끝 삭제 | 남은 항목이 모두 정상 조회됨 |
| 4 | 16개 버킷에 12개 키 저장 후 13번째 신규 키 | 32개 버킷으로 확장, 모든 값 보존 |
| 4 | 12개 키 상태에서 기존 키만 덮어쓰기 | 키 개수와 버킷 수 유지 |
| 5 | 덮어쓰기·삭제·확장 반복 후 종료 | 데이터·키 개수·청소 참조 일관성 유지 |
| 6 | 대량 데이터 삽입·조회·삭제 | 정확성 유지, 규모별 비용과 지연 기록 |

이 표는 개념별 검증 순서입니다. 실제 구현 단위는 TESTING의 U1~U7을 따릅니다. 빈 키·빈 값은 허용하며, 문자열 외 입력은 거부하고 UTF-8 바이트로 키 1 KiB·값 1 MiB 경계를 검사합니다.

충돌 테스트에서는 키가 비슷하게 생겼다는 이유만으로 충돌했다고 판단하면 안 됩니다. 실제 해시값과 버킷 계산 결과를 확인해야 합니다. FNV 자체의 결과는 별도의 알려진 입력·출력과 대조하고, 같은 잘못된 함수로 기대값까지 만들어 검증을 대신하지 않습니다.

## 입력 실패와 메모리 부족 구분

Python이 메모리를 관리해도 잘못된 연결·남은 커서 참조·확장 중 상태 손상은 검사해야 합니다. 입력 오류는 변경 전에 거부하고 기존 값·TTL을 보존합니다. 메모리 고갈이나 리해싱 실패의 복구 보장과 주입 방법은 확장 단위에서 추가 정의하며, 입력 검증 통과로 대신하지 않습니다.

## TTL의 검증

- 만료 직전, 정확한 경계, 만료 직후의 조회
- TTL 없는 저장과 일반 덮어쓰기 시 기존 TTL 제거
- TTL 재설정과 만료 후 재저장
- 접근하지 않은 만료 키의 최종 회수
- 여러 버킷의 키를 검사하는 동안 삭제·확장이 발생하는 상황
- 검사량 제한을 지키면서 만료 검사가 계속 진행되는지

시간원은 단조 시간으로 확정했고, 함수로 전달·교체해 경계를 검사하기로 했습니다. 내부 함수·클래스 이름은 구현 시 정합니다. 실제 대기를 대신한 경계 단위 테스트와 실제 청소 스레드 연동 검증을 구분합니다.

## HTTP와 서버의 검증

저장 엔진이 맞아도 요청 파싱·입력 검사·응답 변환에서 문제가 날 수 있습니다. [API 규격](../docs/API.md)에 합의한 동작을 기준으로 다음 경로를 검사합니다.

- 저장·조회·삭제·만료의 상태 코드와 본문
- 공백·줄바꿈·URL 인코딩과 허용 문자열 경계
- 잘못된 TTL, 과대 본문, 타임아웃과 자원 한도 초과
- 연결 재사용, 분할 도착하는 요청, 중간 연결 종료
- 다수 클라이언트와 같은 키 변경·조회·삭제
- 큰 리해싱이나 만료 회수 중 다른 조회의 성공률과 지연

HTTP 라이브러리가 파싱을 담당해도 실제 연동 테스트가 필요합니다. Flask·Waitress의 기본값과 프로젝트 정책을 구분합니다. Flask 전에 서버가 거부한 요청의 본문·상태는 실제 연결 테스트로 확인합니다.

## 캐싱 실증

데모 앱이 Mini Redis HTTP API를 사용해 원본 API의 응답을 재사용하는 흐름을 검토합니다. 통제 가능한 원본 API를 사용하면 데이터와 지연 조건을 재현하기 쉽습니다. 구체적인 데모 앱과 원본은 미정입니다.

| 비교 대상 | 확인할 경로 |
| --- | --- |
| 캐시 미사용 | 매번 원본 조회 |
| 첫 Miss | 캐시 없음 → 원본 조회 → 캐시 저장 |
| Hit | 저장된 값 반환 → 원본 호출 생략 |
| 만료·무효화 후 | 원본의 새 값이 다시 반영됨 |

응답 내용과 원본 호출 횟수를 확인해야 빠르지만 오래된 데이터를 반환하는 오류를 놓치지 않습니다. Hit만 보여 주거나 캐시를 채우는 시간을 숨기지 않습니다.

## 성능 결과에 함께 남길 조건

데이터 크기, 키 수와 분포, 읽기·쓰기 비율, 동시 클라이언트 수, 반복 횟수, 캐시 초기 상태, 실행 환경과 빌드 옵션을 기록합니다. 워밍업과 실제 측정 구간도 구분합니다.

평균뿐 아니라 응답 시간의 p50·p95·p99, 실패율과 처리량을 함께 살펴봅니다. p99는 측정한 요청의 99%가 그 시간 이하였다는 의미이며, 충분한 표본 없이 정밀한 수치를 주장하지 않습니다. 클라이언트에서 측정한 왕복 시간과 엔진 함수 실행 시간도 구분합니다.

성능 목표 수치와 부하 규모는 아직 확정하지 않았습니다. Python·Waitress나 요청 워커 4개를 선택했다는 이유만으로 빠르다고 결론 내리지 않습니다.

## 실행 결과 기록

각 테스트에 목적 → 사전 상태·입력 → 기대 결과 → 명령·빌드 옵션 → 실제 로그·측정값 → PASS/FAIL/NOT RUN → 미검증 위험을 남깁니다. 실패하면 원인 가설과 수정 전후 결과도 이어서 기록합니다.

사용할 양식은 [협업·검증 기록](../docs/WORKFLOW.md)에 있습니다. 아직 빌드·테스트를 실행하지 않았으므로 여기에 가상의 통과 결과를 채우지 않습니다.
